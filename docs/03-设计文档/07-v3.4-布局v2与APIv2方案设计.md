## 1. 决策前置

| 编号 | 决策 | 结论 |
|---|---|---|
| **V1** | 路线甲（保持 ABI v1 打补丁）/ 乙（v3.4 直接做布局 v2 + API v2） | **乙** |
| **V2** | v3.4 范围 | 语义补齐 + 可靠性与自愈 + 诊断与工具集 |
| **V3** | SylixOS / ARM 目标板验证（G4） | 纳入 v3.4，**不作为发布阻塞**；做不了则标注"未实测"继续发布 |

**选乙的理由（须在评审中确认）**：

1. **当前是改 ABI 最便宜的窗口**：v3.3 发布时确认**无外部使用者**，唯一使用者是 `node-server` 与 `edge-framework`，同一组织内可同步升级。一旦有外部用户，改布局要迁移工具 + 双版本共存 + 客户协调，成本高一个量级。
2. **只需一次迁移**：甲路线要"v3.4 打补丁 → v4.0 改布局"两次变更、两次停机协调，且 v3.4 加的字段在 v4.0 可能又要挪。
3. **v3.3 已把依赖铺垫好**：`rtdbd` 是唯一写者、元数据索引的归属方（决策 D6），`source_timestamp_ns` / `COMM_FAILURE` 已在 v3.3 落地（T5），name→id 索引所需的"集中注册"能力已具备。

**选乙必须同时接受的三条代价**（写入评审记录）：

- 变更量叠加在 v3.3（读写分离）之后，需更严格的分批合入与回归；
- **同一主机上所有进程必须同时升级**，新旧进程不能共享同一段（部署约束，非 SDK 兼容问题）；
- 需要**迁移工具**与明确的停机升级流程。

## 2. 需求：目标与非目标

### 2.1 目标（v3.4 必须交付）

| 编号 | 需求 | 动机 |
|---|---|---|
| **R1** | 段布局 v2：Header 扩展（CRC + flags + 区段偏移）、点位区 / 索引区 / 元数据区 / 心跳区分离 | 支撑索引与元数据；字段整理一次到位 |
| **R2** | **name→id 索引**置于共享内存内，全局一致、支持点位发现 | 关闭 G10；工程配置用点位名，集成方不必各自维护映射层 |
| **R3** | **去单例化**：句柄化 API，同进程可持多个实例 | 关闭"单进程单例"约束；多实例隔离测试、多段场景 |
| **R4** | **元数据区**：EURange（量程）、deadband、描述等冷数据 | 承载此前被推迟的工程量程；与热数据面分离，不放大每次读写路径 |
| **R5** | 语义补齐：`quality` 分层位布局扩展 + `indurtdb_quality_to_status_code()` 纯函数 + 类型扩展（int64 / uint32 / float） | 对齐 OPC UA 三态与 limit 位；类型覆盖工业常用 |
| **R6** | 版本协商与完整性：`version` 不匹配**拒绝挂载**（不静默按新布局解释旧段）+ Header CRC | 关闭"复用旧段被错误解释"的风险 |
| **R7** | 可靠性：修复 issue #19 —— `check_timeouts()` 在热写者自旋下被饿死 | 该缺陷使整轮扫描可能返回 0，属 best-effort 的严苛边界 |
| **R8** | 诊断与工具集：Python 巡检 / 冒烟工具（`tools/`，自带工程结构）、per-point 统计、fd / shm 泄漏检测、覆盖率构建目标 | 用户工程约定第 6 条（工具集）；长稳与可观测 |
| **R9** | 迁移：v1 段 → v2 段离线迁移工具 + 双版本共存验证 | 乙的必备配套 |

### 2.2 非目标（v3.4 不做）

| 项 | 归属 |
|---|---|

## 3. 总体架构

### 3.1 段布局 v2

```
┌──────────────────────────────────────────────────────────┐
│ Header            128B   (v1 为 64B)                      │
│   magic / version=2 / layout_version                      │
│   max_points / max_subscribers / write_seq / owner_pid     │
│   stats.{writes,timeouts} / crc32 / flags                  │
│   off_points / off_index / off_meta / off_subs  (区段偏移) │
│   保留                                                     │
├──────────────────────────────────────────────────────────┤
│ Points            N × 128B   (热数据面，与 v1 点位同尺寸) │
├──────────────────────────────────────────────────────────┤
│ Name Index        B × 8B     (B = roundup_pow2(N*2))      │
│   open-addressing，条目 {hash32, point_id32}              │
├──────────────────────────────────────────────────────────┤
│ Metadata          N × 32B    (冷数据：EURange/deadband)   │
├──────────────────────────────────────────────────────────┤
│ Subscriber 心跳   M × 16B    (不变)                        │
└──────────────────────────────────────────────────────────┘
```

**要点**

- 点位**仍是 128B**、既有字段偏移不变 ⇒ 热数据读写路径的字节布局与 v3.3 一致，性能特征不变，回归可比；
- 索引与元数据是**新增区段**，只在按名查找 / 元数据读写时访问，不进入热路径；
- **零堆分配不变**：索引为定长开放寻址表（预分配，无链指针，无 malloc）；
- 段内偏移由 Header 的 `off_*` 给出，避免"按固定顺序硬算"导致后续再改又要动布局。

### 3.2 name→id 索引

| 项 | 方案 |
|---|---|
| 结构 | 开放寻址（线性探测）+ 墓碑删除 |
| 条目 | `{ uint32 hash; uint32 point_id; }`（8B；`point_id = UINT32_MAX` 表示空槽，`UINT32_MAX-1` 表示墓碑） |
| 桶数 | `B = roundup_pow2(max_points * 2)`（负载因子 ≤ 0.5） |
| 哈希 | FNV-1a 32（纯整数运算，无依赖） |
| 冲突处理 | 比较点位区内 `name[64]`（不重复存字符串，省内存） |
| 并发 | 注册期（初始化 / 配置加载）写，运行期只读；读写均走既有全局 seqlock |
| 查找复杂度 | 期望 O(1)，最坏 O(B)（负载因子受控） |

**为什么不用有序数组 + 二分**：插入需搬移、批量注册 O(N²)；开放寻址插入 O(1) 且定长，更符合"零堆分配 + 注册期集中写"的特点。

### 3.3 元数据区

每点 32B（冷数据，按 `point_id` 直接索引，O(1)）：

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0–7 | `eur_min` | double，工程量程下限 |
| 8–15 | `eur_max` | double，工程量程上限 |
| 16–19 | `deadband` | float，变化阈值（**只存参数，不上送执行**） |
| 20–23 | `flags` | 是否启用量程 / 死区等 |
| 24–31 | 保留 | 后续扩展 |

### 3.4 API v2（去单例化）

```c
typedef struct indurtdb indurtdb_t;        /* 不透明句柄 */

int  indurtdb_h_open(indurtdb_t** out, const char* instance_id,
                     const indurtdb_cfg_t* cfg);
void indurtdb_h_close(indurtdb_t* h);

/* 读写（首参为句柄） */
int indurtdb_h_write_int32(indurtdb_t* h, uint32_t id, int32_t v, uint64_t src_ts);
int indurtdb_h_read_point(indurtdb_t* h, uint32_t id, indurtdb_point_t* out);

/* 新增能力 */
int indurtdb_h_find_by_name(indurtdb_t* h, const char* name, uint32_t* out_id);
int indurtdb_h_get_meta(indurtdb_t* h, uint32_t id, indurtdb_meta_t* out);
int indurtdb_h_set_meta(indurtdb_t* h, uint32_t id, const indurtdb_meta_t* m);
```

**v1 API 的处置（待评审确认，倾向方案 A）**

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（倾向）** | v1 的 26 个全局函数**保留为薄封装**（内部默认句柄），标注 `INDURTDB_DEPRECATED`，编译期可选告警；v3.5 移除 | 既有 node-server 与 22 个测试**无需立即改**，迁移可分阶段；代价是短期内两套 API 并存 |
| B | v1 直接删除，全部调用方一次改完 | 干净，但与 v3.4 其他变更叠加，回归风险集中 |

**命名说明**：C 无重载，v2 必须换名。候选 `indurtdb_h_*`（显式、可机械替换）与 `irt_*`（短，但与内部 `irt_` 前缀冲突）。**倾向 `indurtdb_h_*`**。

### 3.5 `rtdbd` / `indurtdb-client` 的连带变更

| 项 | 影响 |
|---|---|
| 协议 | `RTDBD_PROTO_VERSION` 1 → 2；新增 `OP_FIND_BY_NAME` / `OP_GET_META` / `OP_SET_META` |
| 鉴权 | `SO_PEERCRED` 不变；元数据写入属管控操作，须鉴权 |
| 服务端 | `rtdbd` 成为**元数据的唯一写者**（与 D6 一致），并负责索引注册 |
| 兼容 | 版本不匹配即拒绝（现有行为），**不做新旧混跑** |

## 4. 语义补齐（承 06 文档，§10 决策后并入）

沿用既有方案 v1.1 的结论（`quality` 为权威、`StatusCode` 不进点位）：

- **quality 分层位布局**：bit0–3 基础质量码（现有 0–3 取值不变，新增 UNCERTAIN / NOT_INITIALIZED / OUT_OF_SERVICE / SENSOR_FAILURE / LAST_KNOWN / CONFIG_ERROR）、bit4–5 量程位（None/Low/High/Constant，对齐 OPC UA limit bits）、bit6–7 预留为 0。
- **判定规则**："值是否可用"只看基础码；量程位是与可用性正交的附加信息。
- **`indurtdb_quality_to_status_code()`** 纯函数供北向映射（双向用例覆盖）。
- **类型扩展**：int64 / uint32 / float **复用 `value` union 内已有 32B**，只新增 `INDURTDB_TYPE_*` 枚举与读写 API，布局不变。
- **点位内不再新增字段**（`source_timestamp_ns` 已于 v3.3 落地）；需要的新语义进**元数据区**（R4）。

## 5. 可靠性：issue #19 的修复方案

**问题**：写入者无间隙自旋时，全局单 seqlock 的"偶数窗口"极短，`check_timeouts()` 读重试与 `write_begin` 连续冲突 → **整轮扫描返回 0**（Debug 实测约 40%）。

**方案（分层，按代价从小到大）**

| 层 | 措施 | 代价 |
|---|---|---|
| L1（必做） | **扫描侧让步**：读重试循环连续 N 次失败后 `sched_yield()`；`write_begin` 冲突时有限次重试（默认 3 次）+ 指数退避 | 无布局影响；单次扫描耗时可能略增 |
| L2（必做） | **可观测**：Header 新增 `stats.scan_skipped` 计数（被跳过的点数），使"饿死"可被运维观测而非静默 | 占 Header 保留区 |
| L3（评估） | **分片 seqlock**：按点位分桶多锁，消除全局单点 | 改动大；若 L1+L2 达标则不进 v3.4 |

**验收（TDD 红→绿）**：热写者自旋场景下，连续 N 轮扫描的 `detected` 与"实际超时点数"一致；且 `scan_skipped` 可观测。**先用失败用例复现饿死（红），再改（绿）。**

## 6. 迁移与兼容（乙路线的必备配套）

| 场景 | 行为 |
|---|---|
| 新部署 | 直接建 v2 段 |
| 已有 v1 段 | **拒绝挂载**（`version` 不匹配），返回明确错误码；不静默解释 |
| 需要保留数据 | 离线工具 `tools/irt_migrate`：读 v1 段 → 写 v2 段（点位值 / 质量 / 时间戳 / name 全量搬运，`source_ts` 置 0 或按配置） |
| 升级流程 | 停机 → 迁移（或丢弃重建）→ 全进程同时升级；**不支持新旧进程混跑** |
| 回退 | 重新部署 v3.3 + 清理 `/dev/shm` 段；v2 段对 v3.3 不可读（会被版本协商拒绝） |

> 与用户工程约定第 14 条（SDK 向前兼容）的关系：该约定针对**有外部使用者**的情形。当前已确认无外部使用者、可同步升级，故采用"一次性变更 + 迁移工具"而非"永久兼容层"；**首个对外发布前必须冻结 ABI**，此为明确里程碑。

| 风险 | 触发 | 应对 |

| **Q2** | v2 函数命名 | **`indurtdb_h_*`** | 显式、可机械替换；不与内部 `irt_` 前缀冲突 |
| **Q3** | 索引条目 8B（hash32 + id32）够用？ | **先 32 位哈希 + 负载因子 ≤0.5** | T2 用例覆盖最坏冲突与满负载；实测冲突率过高再升 64 位（条目变 16B） |

| **Q6** | 元数据区 32B/点 够不够 | **够** | v3.4 只放定长字段（EURange / deadband / flags）；描述文本、单位符号等变长内容延后 |
