## 1 现场场景（用户描述，作为设计输入）

- 多台 PLC 设备，每台各运行一个 `rtdbd` 与若干 PLC 服务；服务只连本机 `127.0.0.1` 读写，不感知自己在哪台设备上。
- 每个节点持有全量点表（任意服务都可能在别的设备上备份/迁移），**每个节点都会被本地服务写**，写完同步到其余节点。
- 某设备挂掉 → 其上服务整体迁移到另一台设备，仍连那台的 `127.0.0.1` 继续读写；应用层不携带 epoch、不携带身份、不重放。
- **没有主备概念，没有只读副本，从库不拒写**；所有节点对等可写。

由此得到硬约束：无中心协调者 / 不选主；本地写必须先本地生效（P99 ≤ 10 μs）；每节点可独立启动与崩溃恢复；迁移窗口的陈旧写由 DB 层收敛；PLC 设备时钟不可信，物理时间戳不参与排序。

## 3 技术口径（相对 `12` 号文档的修订）

1. **写者身份与纪元**：每个 PLC 服务有跨迁移稳定的 `service_id`（配置声明、SDK 建连自动携带，应用层无感）。`rtdbd` 为每个 `service_id` 维护 `(epoch, seq)`；写记录带 `service_id/epoch/seq/origin_node`，**不含物理时间戳**。
2. **追平屏障**：某节点上该 `service_id` 出现首个新本地写入连接时（迁移 / 重启 / 重连同一路径），先向可达 peer 查询 `max_epoch` 与最新点值，追平后分配 `epoch = max_seen + 1` 再放行写入。
3. **陈旧写隔离**：收到 `epoch < 本地当前 epoch` 的同步帧整帧丢弃并记 warn；旧节点在途写、其它节点转发的残留帧由同一条规则挡住。
4. **每 origin 一条增量流**：不做全局 LSN / `base_lsn`。帧带 `(origin_node, boot_id, offset)`；`offset` 为 `rtdbd` **进程内**单调计数，只给本地原生写发号，远端重放不占号；接收端按 origin 维护已应用 offset 向量。**不使用** `hdr->stats.writes`（远端重放会抬高它、造成序号空洞，且重启语义需重定义）。
5. **值变化记录**：新增协议层 `sync_rec_t`（point_id + 值 + origin 序号），挂到 `rtdbd` 写路径（`outq_push_notify` 同层），不碰已退役的 v1 `irt_sub_notify`；`irt_delta_rec_t`（80B）只管结构变更，两者共用同一序号空间、结构先于值。
6. **快照为无停顿流式**：开始时记录各 origin 已应用 offset 边界向量；用 seqlock 读侧重试逐点分页扫出 `id + 128B point` 帧；扫描期间写继续本地生效并进固定大小 backlog；快照帧发完先重放 backlog 再切增量。不 fork、不暂停写、不整段加载。
   > **纠正 `12` 号文档 §4.2 的硬错误**：所谓「`irt_point_manager` 已有基线文件格式，快照格式直接对齐复用」不成立——`irt_point_manager.h` 只有 `irt_pm_read/peek/write_count/check_timeouts`，`irt_delta` 只是 80B 结构变更日志。快照格式必须新定义，§4.2 与 §10(6) 需重写。
7. **错误路径**：`epoch` 落后 → 丢弃 + warn；`boot_id` 变化 / lag 超限 / 快照期 backlog 溢出 → 转全量；断链指数退避（1/2/4/8/16/30s）；`WAIT` 超时返回实际 ack 数并告警，不回滚、不阻塞本地控制回路。
8. **分裂脑边界（明示的取舍）**：若旧节点未真死而是网络分区，两侧可能同时自认活动写者。不做选主：本地写仍各自生效，靠 `(epoch, node_id)` 字典序定胜者，链路恢复后由全量快照收敛，期间两侧读己写成立。这是为保本地可用性接受的短暂分歧，不是无仲裁的自由合并。

## 4 冻结的配置默认值（6 节点 / 10 万点 / 1 万 ops/s）

```yaml
sync:
  enabled: false              # 默认关闭；删去 sync: 段即回退 v3.11 行为
  node_id: <集群内唯一>
  service_ids: [<本节点可能承载的 PLC 服务>]
  transport: vsoa                # 同机 ipc 模式 | 跨机网络模式，统一 VSOA 入口
  listen: <VSOA 端点>                 # 双栈前端之一；UDS 路径仍由 --socket 指定
  peers: []                       # 静态种子（可选）；2026-11-06 新需求：集群成员事先不可知，
                                  # 须支持运行时下发对端 IP。接口形态见 §8.3 第 6 题，待裁决
  snapshot:
    page_points: 1024             # 100k / 1024 ≈ 98 帧，单帧 ~128 KB
  delta:
    flush_ms: 20                  # 1 万 ops/s → 约 200 条/批 ≈ 25 KB/帧
    backlog_records: 65536        # 约 8 MB/origin，5 origin ≤ 40 MB/节点
    lag_fullsync: 65536           # 约 6.5 s 断链即转全量，不扩缓冲硬扛
  wait:
    default_acks: 1
    default_timeout_ms: 50
  reconnect:
    backoff_max_s: 30
```

**同机多实例前置必修**：`sock_path` 改为实例名派生、退出只 unlink 自己（`rtdbd.c:2003` 目前为固定 `/run/indurtdb/default.sock`）；`rtdbd_conf` 真正解析 `sync:`（当前遇未知键静默忽略）。

## 5 冻结的验收门禁（可证伪，评审通过后方可上调）

| 编号 | 判据 | 冻结阈值 |
|---|---|---|
| T1 | 开 sync（默认异步、不调 WAIT）vs 关 sync 的本地写 TPS 损耗 | **≤ 5%**（10 万点 / 1 万 ops/s / 6 节点） |
| T2 | 本地写 P99 不退化；写后对端可见延迟 p99 | **≤ 10 μs**；**≤ 100 ms**（20 ms flush + 千兆跨机） |
| T3 | 全量（10 万点）端到端墙钟时间，且发送/接收端 RSS 增量 | **≤ 10 s**；**≤ 64 MB**（流式、不 OOM）。字节口径待 POC 定稿：点值原始量 `10 万 × 132 B ≈ 13.2 MB`，用户给的「约 20 MB」为含点位定义/元数据/帧头的工程估计，T3 以实测产物字节数为准并回填此处 |
| T4 | 注入 1 s / 6 s / 30 s 三档断网，转全量行为须可区分（原「30 s → 100%」近乎恒真，已按 §9.4 修订） | **1 s → 续增量不转全量**；**30 s → 转全量 100%**；恢复后逐点 diff = 0，收敛 ≤ T3 + 10 s |
| T5 | 迁移陈旧写隔离（**按 §8.3-1 重写，2026-11-07**）：PLC 服务经 **VSOA loopback** 作为主写入口，握手分配 `epoch`；A 挂 → 服务迁 B 并以新 `epoch` 建连 → B 写 1000 条；同时注入 A 的 200 条**旧 epoch 在途帧**（经 `/sync/delta` 复制通道到达，非 UDS） | B 侧新写 **1000/1000 保留**；旧 epoch 帧 **200/200 丢弃**（applier 判 `epoch < 当前`）；6 节点最终一致。**UDS 明示不参与纪元隔离**，故旧帧不注入 UDS；T5 的判据适用于 VSOA 前端 |

集成用例（须注册进 ctest）：IR1 全量补齐（新节点加入 → diff=0）/ IR2 增量一致（1 万 ops/s × 60 s → 6 节点最终一致）/ IR3 断链恢复（offset 命中 backlog 续增量，未命中转全量）/ IR4 lag 兜底（30 s 拔线）/ IR5 迁移陈旧写隔离（T5 场景）/ IR6 `WAIT` 语义（超时不回滚、返回实际 ack 数、有 warn）/ **IR7 分区收敛**（A 未真死 + 分区 + 同 epoch 双写 → 恢复后 6 节点终态一致且等于字典序最大节点快照）。**回归基线 42 个 ctest（29 单元 + 12 集成 + 1 门禁），gtest 层面 381 个**，详见 §9.4。

**门禁结论**：IR1–IR6 全绿 + T1/T3 实测数字落库 + 零警告构建 + 全量 ctest，方可进入版本合入；数值上调须经方案评审留痕，禁止实现者自改。

- **现有对外协议事实**：`rtdbd` 目前只有 `AF_UNIX/SOCK_STREAM` 上的自研二进制帧协议（`RTDBD_MAGIC "RBD1"` / `RTDBD_PROTO_VERSION 3` / 22 个 opcode），无 TCP、无 VSOA、无 HTTP 监听；PLC 服务与 `irtcli` 走这条 UDS 通道。**回归纪律**：现有 42 个 ctest 必须全绿且 UDS 侧行为零变化，VSOA 侧另立用例与性能基线，T2/T3 按 VSOA 实测重校准。
> **「UDS 侧行为零变化」适用范围（复评硬条件 2，2026-11-07 补）**：指**既有 22 个 opcode 的帧格式、语义、错误码与 `libindurtdb.a` ABI 一字不改**，且 42 个既有 ctest 全绿。它**不禁止**纯可加项：尾部追加 `OP_SET_PEERS(23)` / `OP_GET_PEERS(24)`（§8.3-6，旧客户端无感知）。同时按 §8.3-1，**UDS 明示不参与 `epoch` 纪元隔离、不参与集群同步可见性**（现场主写入口为 VSOA loopback），因此 T5 的陈旧帧隔离判据不适用于 UDS 路径；「UDS 行为零变化」不得被读作「UDS 也须具备纪元隔离能力」。D9 表述统一为：**D9 字面不变 = 既有 22 个 opcode 与静态库 ABI 零改动；允许尾部可加 23/24**；§8.3-1「D9 字面不变」与 §9.1「尾部可加」按此合并，不再并存两种表述。

## 7 v3.12 首批 VSOA 镜像清单与 dispatch 拆分

### 7.1 首批镜像（10 组能力 / 13 个 opcode）

| 能力组 | VSOA URL（`/indurtdb/v1/…`） | opcode | VSOA 机制 |
|---|---|---|---|
| 探活 | `/ping` | 1 `PING` | RPC |
| 单点写 | `/point/write` | 2 `WRITE` | RPC |
| 批量写 | `/point/batch_write` | 20 `BATCH_WRITE` | RPC |
| 单点读 | `/point/get` | 10 `GET` | RPC |
| 批量读 | `/point/batch_read` | 19 `BATCH_READ` | RPC |
| 订阅 | `/subscription/add`、`/remove`、`/set` | 4/5/18 | RPC |
| 变更推送 | `/notify` | 6 `NOTIFY` | **`cli_datagram` 逐连接定向**（per-conn RBE 门控） |
| 快照完成屏障 | `/snapshot_done` | 22 | **`cli_datagram` 定向**，仅 `caps_negotiated` 的 session |
| 能力与分区 | `/caps`、`/select` | 21/17 | RPC |
| 健康 | `/health` | 16 `HEALTH` | RPC |

**我额外纳入的两个 opcode（已裁定）**：`SELECT`(17) 是 v3.9 起分区命名空间的连接级前置，PLC 服务按 `(partition, name)` 定位点位，缺了它数据面不可用；`SNAPSHOT_DONE`(22) 是 `SET_SUBS` 快照流的完成屏障，与订阅能力不可分。因此「10 组」映射到 13 个 URL。

**首批不镜像（仍走 UDS，共 9 个）**：`AUDIT_DUMP`(3)、`FIND_BY_NAME`(7)、`GET_META`/`SET_META`(8/9)、`LIST`(11)、点位 CRUD(12/13/14)、`GET_LOG`(15)。理由：均为运维/管控/监控台能力，PLC 服务数据面不依赖；v3.13 或客户端迁移需要时按同一 dispatch 层追加 URL 即可，不需改协议骨架。

> **`SELECT` 与 `FIND_BY_NAME(7)` 取舍澄清（复评硬条件 2，2026-11-07 补）**：首签曾指出「纳入 `SELECT(17)` 的理由是 PLC 按 `(partition,name)` 定位点位，却又排除 `FIND_BY_NAME(7)`」自相矛盾。裁定：**两者用途不同，取舍成立**。`SELECT(17)` 是**连接级会话状态**——设置当前连接的 `partition`，影响后续所有按 `point_id` 的读写与订阅的命名空间解析，无独立返回值，是数据面前置；`FIND_BY_NAME(7)` 是**单次名称→id 查询**，返回 `point_id`，属于点表检索/运维能力。v3.12 的 PLC 服务在部署期由编排系统下发 `point_id`（或经本地点表索引 `irt_index` 解析），**运行时不需要跨进程按名查 id**，故 `FIND_BY_NAME` 留在 UDS 侧、不进首批。若后续出现「VSOA 客户端必须按名定位」的现场需求，按同一 dispatch 层追加 `/point/find_by_name` URL 即可，不需改协议骨架；在此之前，§7.1 的 `SELECT` 纳入理由按本段理解，不再解释为「按名查 id」。

**节点间同步通道（与客户端 URL 分离，已按 §9.3 重裁）**：`/sync/hello`（握手与摘要校验）、`/sync/snapshot`（**分页 RPC**，约 160 帧 ×128KB）、`/sync/delta`（**RPC 批次 + reply 即 ack**）、`/sync/wait`（WAIT 查询）、`/sync/peers/{set,get}`（运行时成员配置）。与 `RTDBD_OP_*` 私有 opcode 空间不复用；UDS 侧对应 `OP_SET_PEERS(23)` / `OP_GET_PEERS(24)`。

### 7.2 状态与载荷约定

- `vsoa_payload_t.data` 直放现有定长 POD（`rtdbd_write_req_t` 24B、`rtdbd_get_resp_t` 64B…），零序列化；`param` 放 `service_id / epoch / origin / offset / WAIT` 等 JSON 元数据。
- 响应 status 用**自定义区间** `0x80 + RTDBD_ST_*`（7 个状态码无损映射），保留 `VSOA_STATUS_*` 给传输层错误；禁止把 `NOT_FOUND` 硬塞成 `INVALID_URL` 造成语义丢失。
- `CAPS` 响应新增 VSOA 侧能力位；UDS 侧 `rtdbd_caps_t` 布局不变（flags 尾部追加，二进制兼容须走 ABI 评审）。

### 7.3 dispatch 拆分（最大重构面）

```
UDS 前端:   recv_all(fd)  ─┐
                           ├─→ rtdbd_dispatch(opcode, req_buf, resp_buf, cx) ─→ op_* 业务语义 ─→ SHM
VSOA 前端:  listener cb  ─┘        （与 fd / socket / VSOA 完全无关）
```

- 新增 `rtdbd_dispatch.c/h`：`int rtdbd_dispatch(uint16_t opcode, const uint8_t* req, size_t req_len, uint8_t* resp, size_t cap, size_t* out_len, rtdbd_ctx_t* cx)`。
- 现有 `op_*(int fd, rtdbd_ctx_t*)` 退化为 UDS 薄适配：`recv_all` → dispatch → `send_all`，**函数签名与行为对既有调用不变**。
- 新增 `vsoa_adapter.c`：URL→opcode 表、`payload.data`→req buffer、`cli_reply` 回填 status + POD；不复制业务逻辑。
- 推送侧抽出 `notify_sink_t`（UDS 帧 / VSOA `cli_datagram` 定向两种实现）；按订阅者的 RBE 门控状态仍留 `rtdbd` 进程内存，**不进共享内存**；`role=sync_peer` 不得订阅 NOTIFY。
- 不变式守护：dispatch 层不得出现 fd/socket/VSOA 符号（**新增 `scripts/check_dispatch_boundary.py` 符号级 checker** 并挂进 `check_all.sh`；`check_arch_layers.py` 另补 `libvsoa/` ring 映射）；写权威仍唯一收敛在 `rtdbd`；单线程零锁（§8.3-3）。

### 8.1 六组方案级硬伤（评审原文归纳）

1. **D3/D5/D8 与 D9 互斥**：`service_id + epoch`、`WAIT` / `indurtdb_h_wait_sync()` 都缺 UDS 承载（`rtdbd_req_hdr_t` 仅 12B、无握手帧、`rtdbd_conn_t` 只有 pid/uid），而 D9 冻结「UDS 22 opcode 与静态库 ABI 完全不变」。现场主写入口是 UDS，迁移屏障与陈旧写隔离对它形同虚设，T5「200/200 丢弃」在真实链路不可复现。
2. **传输语义互斥**：`quick_datagram` 在 VSOA 头文件明确「reliability are not strict」且为 UDP（上限 65507B），与 per-origin 连续 offset、应用级 ack、`WAIT` 的 N-1 确认互斥；丢帧即 offset 空洞，IR2 直接被证伪。
3. **并发模型未定义**：`rtdbd` 现为单线程 `poll(fds, nfds, 500)`、全树无线程、全局状态无锁；VSOA 要求 `select` 事件循环且重连/关闭只能在事件循环内调用、`stream_accept` 阻塞。两套循环如何合并、`rtdbd_conn_t` 的连接级状态（partition、订阅/RBE、CAPS 位、SET_SUBS 快照态）如何抽象，全篇未给；合并进单线程会卡住 UDS 控制回路，起线程则破坏「读路径不引入锁 / 写权威唯一」。
4. **跨机鉴权绕过**：首批含 `WRITE`/`BATCH_WRITE`，UDS 走 `SO_PEERCRED → irt_policy_allows(uid, partition, id)` deny-by-default；VSOA 只有全局 `passwd` + `bool authed`（仅挡 publish 订阅），无 uid/partition 可传，跨机客户端可绕过按点鉴权写任意点位。
5. **推送语义互斥**：`NOTIFY`/`SNAPSHOT_DONE` 在 UDS 侧是 per-conn RBE 门控 + 定向入队（后者仅对发过 `CAPS` 的连接），`publish` 是 URL 广播，无法做 per-client 门控，「两前端语义等价」不成立。

### 9.2 端到端链路

```
PLC 服务(本机 127.0.0.1)
   │ VSOA loopback，建连 /hello 带 service_id+token → 分配 (uid,partition,service_id,role,epoch)
   ▼
rtdbd 单线程 poll 主循环（UDS + VSOA server/client 同一事件循环，零线程零锁）
   │ 写请求 → irt_policy_allows(uid,partition,id)（role=plc，deny by default）
   ▼
写权威落 SHM → sync_rec_t(service_id, epoch, origin_node, boot_id, offset) 入每 peer 流
   │ 每 20ms 一批（约 200 条 / ≤25KB）→ /sync/delta 异步 RPC(TCP) → 对端 cli_reply(applied_offset)
   │   reply = ack：派生 offset 水位 / lag / WAIT 的 N-1 计数
   ▼
对端 applier（role=sync_peer，仅 /sync/* URL，不进 op_write）
   │ 接收侧按 origin offset 应用；快照期 snapshot_epoch 原子切换 + backlog 去重重放
   ▼
变更通知：逐连接 RBE 门控 → cli_datagram 定向（NOTIFY / SNAPSHOT_DONE），不广播、不走 quick

异常：可达成员 < ⌈N/2⌉ → 本地写仍生效、标记 degraded、留有界 backlog
      → 恢复后由 (epoch,node_id) 字典序最大可达节点发全量快照，一次定稿
```

### 9.3 通道与 URL 总表

| 类别 | URL / opcode | 承载 | 备注 |
|---|---|---|---|
| 客户端数据面（首批 13 个） | `/indurtdb/v1/{ping, point/write, point/batch_write, point/get, point/batch_read, subscription/add, subscription/remove, subscription/set, caps, select, health}` + 两个推送 URL | RPC(TCP) / `cli_datagram` 定向 | `vsoa_payload_t.data` 放定长 POD，`param` 放元数据；status 用 `0x80 + RTDBD_ST_*`（待 POC 验证透传） |

| 节点间同步 | `/sync/hello`、`/sync/snapshot`（**分页 RPC**，约 160 帧 ×128KB）、`/sync/delta`（**RPC 批次 + reply 即 ack**） | RPC(TCP) | 不用 stream、不用 quick channel |
| 禁止项 | `publish` / `quick_publish` / `quick_datagram` 承载增量、快照、ack、握手、NOTIFY | — | quick 是 UDP 且「reliability not strict」 |

**跨机 POD 编解码约定（冻结，评审整改条件 5；2026-11-07 回填 P2 取证结论）**：`vsoa_payload_t.data` 只放定长 POD，字段全为定宽整数、无指针/变长；**编码 = 本机自然字节序（现场目标架构同为小端）+ 自然对齐，零序列化、不做 `htonl`/转换**；每个 POD 的 `sizeof` 与字段 `offsetof` 由实现侧 `_Static_assert` 编译期锁死（P2 参考形态：24B、offsets `[0,4,5,8,16]`）。这是**同构节点约定**：若未来引入大端或不同对齐规则的架构，须另立显式编解码并升协议版本，不得静默混传。证据：`docs/08-验证记录/v3.12-T0-VSOA通道取证.md` §4b（`PASS=1 FAIL=0`）；真实 arm/aarch64 roundtrip 为现场项。

**事件循环调度顺序（冻结，评审整改条件 3；2026-11-07 回填 P5 取证结论）**：单线程合并 `poll` 主循环内，**本地 UDS 写必须先于 VSOA reply 批处理被服务**（local-first），再辅以「每轮预算」限制单轮 `*_input_fds()` 处理的 reply/快照页数，二者共同守住 T2 的 UDS 写 P99。P5 实测：`vsoa-first` 下满负载 reply 把本地写调度 p99 推到 **12.6 μs（超过 10 μs 预算）**，`local-first` 下仅 **0.93 μs**（详见证据文档 §5b）。因此「本地优先」不是实现细节偏好，而是**冻结的调度约束**，实现与评审均不得改为 VSOA 优先。
