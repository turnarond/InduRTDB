逐维结论：

- **架构兼容**：分层方向现状合规（38 文件 0 违规），但守卫**不覆盖 VSOA 头**（未归类即忽略），13 号 §7.3「给 `check_arch_layers.py` 新增一条分层边」无法表达「dispatch 层不得出现 fd/socket/VSOA 符号」这类符号级约束；写权威唯一收敛在 `op_write` 成立，读路径 `irt_pm_read/peek` seqlock 无锁成立；但 `rtdbd_dispatch` 拆分**会破坏现有语义**——`rtdbd_ctx_t` 直接持有 `rtdbd_conn_t*`，SELECT 的 `conn->partition`、订阅表、CAPS 协商位、SET_SUBS 快照状态全在连接对象上，且 `op_*` 自带 `recv_all/send_all(fd)` 与多次分帧发送（:983-984, :1079, :1094-1095, :1159-1160），「UDS 薄适配 = recv_all → dispatch → send_all」无法保持「函数签名与行为对既有调用不变」；VSOA 的 select 事件循环与现有 `poll(500ms)` 单线程主循环如何共存、全无锁全局状态（`g_stats/conns/outq/policy`）在双线程下如何保持「读路径不引入锁」，13 号全篇未定义。
- **正确性**：`service_id + epoch` 追平屏障**挡不住 UDS 侧的陈旧写**（详见风险点 1）；「向可达 peer 查 max_epoch」在分区下会产生**相同 epoch**，而 §3.3 只丢弃 `epoch < 本地`、§3.8 又用 `(epoch,node_id)` 字典序，与 §3.4 的 per-origin offset 分流无统一收敛规则，T5/IR1–IR6 无分区/脑裂用例；per-origin `(boot_id, offset)` 依赖连续不丢帧，缺 `boot_id` 生成/持久化定义、缺快照期间接收端 offset 向量原子切换与「快照→backlog→增量」跨通道屏障定义；按服务分区写的前提「同一时刻每点位只有一个逻辑写者」无配置校验或运行时检测，§4 `service_ids` 是节点级列表，删掉 LWW 后稳态双写者无任何仲裁。分裂脑取舍本身可作为明确取舍接受，但 13 号未给出收敛终态定义与验收证据，**当前不可判为可接受**。
- **VSOA 接入**：`.data` 放定长 POD 机制可行，但**跨机字节序/对齐未冻结**（SDK 同时提供 arm/aarch64/x86_64 三套包，而 `RTDBD_STATIC_ASSERT(sizeof==64)` 只是本机编译期断言）；20MB 快照走 stream/tunid 的 API 真实存在，但 `stream_accept` 阻塞语义 + 事件循环合并未定；跨机认证只有全局 `passwd` + `bool authed`，**无 uid→`irt_policy_allows` 映射**而首批镜像含 WRITE/BATCH_WRITE；`quick_datagram` 明确「reliability not strict」且为 UDP，与连续 offset 及 WAIT ack 语义冲突；`0x80 + RTDBD_ST_OK = 0x80` 与 VSOA「0 = success」约定冲突，需 POC 验证中间层不丢弃 payload。
- **7×24 稳定性**：backlog/outq 有界方向正确，但 `backlog_records` 与 `lag_fullsync` 同为 65536 无余量；VSOA 每连接 `vsoa_recv_t` 256KB 常驻未计入 T3 的「RSS ≤ 64 MB」；重连后 publish 订阅须重建且 reconnect 只能在 event loop 调用；`boot_id` 若随进程重启变化，滚动重启会触发 5 peer × 20MB 全量风暴；「每节点独立启动与崩溃恢复」在**无点值持久化**前提下缺冷启动权威数据源定义。

## 风险点

- 【正确性·方案级】触发条件：PLC 服务全部走本机 UDS（13 号 §6 自述），而 D9 冻结「UDS 侧 22 个 opcode 与 `libindurtdb.a` ABI 完全不变」、D8 冻结旧 55 个 v2 函数签名不变；`rtdbd_req_hdr_t` 仅 12B（magic/version/opcode/payload_len），`rtdbd_conn_t` 只有 `peer_pid/peer_uid`，`libindurtdb.a` 建连无握手帧可携带 `service_id`。影响：D3 的 `service_id + epoch` 既无法进入 UDS 写路径，迁移窗口从 UDS 进来的本地写也拿不到 epoch，§3.2 追平屏障与 §3.3 陈旧写丢弃对现场主写入口形同虚设，T5「200/200 丢弃」在真实链路上不可复现；D5 + D8 的 `indurtdb_h_wait_sync()` 同样缺 UDS 承载 opcode，WAIT 无法返回「实际 ack 数」。这是 D3/D5/D8 与 D9 的互斥，不是实现细节补齐可覆盖。
- 【VSOA·传输与正确性·方案级】触发条件：`/sync/delta` 按 §7.1 走 `quick_datagram`，而 `vsoa_server.h:79-81` / `vsoa_client.h:74-76` 明确 quick 通道「reliability are not strict」、`VSOA_MAX_QPACKET_LENGTH 65507` 为 UDP 上限；同时 §3.4 的 per-origin `(boot_id, offset)` 是「进程内单调计数 + 接收端已应用 offset 向量」的连续流语义，D5 又要求等 N-1 个 ack。影响：任一帧丢失即产生 offset 空洞，方案未定义空洞检测、重传或降级规则——不处理则 IR2「1 万 ops/s × 60 s → 6 节点最终一致」被直接证伪（丢写永久丢失），一律转全量则在 6 节点 × 5 出口的 UDP 丢包率下 T1（≤5%）/T2（p99 ≤100 ms）不可达；quick 通道无回执路径，WAIT 的 ack 来源与计数单位无定义。「高频增量 → quick_datagram」与「连续 offset + WAIT ack」语义冲突。
- 【架构·方案级】触发条件：`rtdbd` 现为单线程 `poll(fds, nfds, 500)` 主循环、全树无 `pthread`、`g_stats/conns/outq/policy` 全无锁；VSOA 要求 `vsoa_server_fds/input_fds` 的 select 事件循环，且 `vsoa_client.h:65-68` 规定重连只能在该事件循环内调用、不能回调内调用，`vsoa_server_stream_accept` 为阻塞等待。影响：13 号 §7.3 只画了「UDS 前端 / VSOA 前端 → dispatch」的箭头，未给两套事件循环的合并方式；合并进单线程则阻塞式 stream accept 会卡住 UDS 控制回路（T2 P99 ≤10 μs 失效），起独立线程则现有全无锁全局状态被并发访问，直接违背「读路径不引入锁 / 写权威唯一」不变式。双栈落地路径缺失，`rtdbd_dispatch` 拆分与连接级状态（`conn->partition`、订阅表、CAPS 协商位、SET_SUBS 快照状态）抽象均未设计。
- 【安全·方案级】触发条件：首批 13 个镜像 opcode 含 `WRITE(2)` / `BATCH_WRITE(20)`，而 UDS 侧 `op_write:1030-1040` 与 `point_subscribable:872-875` 走 `SO_PEERCRED` → `irt_policy_allows(uid, partition, id)` deny-by-default；VSOA 侧仅有 `vsoa_server_passwd`（单一全局口令）与 `vsoa_server_cli_authed`（`bool`，注释明确只挡 publish 订阅推送），13 号 §6 自述「跨机认证口径待定」。影响：VSOA 前端若复用同一 dispatch，既无 uid 也无 partition 可传给 `irt_policy_allows`，跨机客户端可绕过按点鉴权写任意点位；`service_id` 与 VSOA 建连的 `passwd/info` 之间也无绑定定义，§3.1 的写者身份模型在跨机侧落空。
- 【VSOA 映射·方案级】触发条件：`NOTIFY(6)` 在 `rtdbd.c:575-583` 由 `rtdbd_subtab_decide(&c->sub, …)` 做**每连接** RBE 死区门控后 `outq_push_notify(c, &nt)` 定向入队；`SNAPSHOT_DONE(22)` 按 CHANGELOG「仅对发送过 `CAPS` 的连接发送」；§7.1 却把两者映射为 `publish` / `quick_publish`（广播给该 URL 的所有订阅者）。影响：广播一次只能带一个 payload，无法 per-client 门控，7×24 高频下会向所有客户端灌全量变更或让特定客户端收到不属于自己的快照完成屏障，「UDS 侧行为零变化 / 两前端语义等价」不成立；应改为遍历 `vsoa_server_cli_array` + `cli_is_subscribed` 定向 `cli_datagram/cli_quick_datagram`，或显式降级 RBE 并重裁 D10。
- 【正确性·设计缺口】触发条件：§3.2 追平屏障查询的是「**可达** peer」的 `max_epoch`，§3.8 承认 A 未真死而是网络分区；§3.3 丢弃条件仅 `epoch < 本地当前 epoch`；T5 只注入「A 的 200 条**旧 epoch** 在途帧」，IR1–IR6 无分区/脑裂用例。影响：分区下 B 查到的 `max_seen` 可能不含 A 的 epoch，`epoch = max_seen+1` 与 A 侧相同，等值帧整帧通过、两侧互覆盖；`(epoch,node_id)` 字典序定胜者与 per-origin offset 分流、全量快照收敛三套规则未统一成可判定的终态，「6 节点最终一致」无定义、无证据，分裂脑取舍不能判为可接受。
- 【正确性·设计缺口】触发条件：D3「同一时刻每点位只有一个逻辑写者」只是假设，§4 `service_ids` 是**节点级**「本节点可能承载的 PLC 服务」列表，无点位→service_id 映射、无唯一活跃性校验；12 号 §4.10 的 LWW 仲裁被 13 号删除后未补等价机制。影响：两个不同 service_id 的服务写同一 `point_id`（如采集服务与报警确认服务）属现场常态，稳态即产生双写者，per-origin offset 按 origin 分别应用、后到者覆盖，无收敛判据与告警，IR2 的「最终一致」缺乏定义。
- 【7×24·设计缺口】触发条件：§3.4 的 offset 是「进程内单调计数、不落盘」，`boot_id` 变化即转全量，但 `boot_id` 的生成与持久化位置未定义（全树 grep 无点值持久化，仅 `irt_delta` 存结构变更）；§4 `backlog_records: 65536` 与 `lag_fullsync: 65536` 数值相同；VSOA `vsoa_recv_t` 每连接内嵌 256KB 缓冲。影响：`boot_id` 若随重启变化，单节点滚动重启即触发 5 peer × 20MB 全量，形成全量风暴；backlog 满与转全量阈值重合，§3.6「快照帧发完先重放 backlog 再切增量」无余量；T3 的「RSS 增量 ≤64 MB」未计入 VSOA 库自身 per-connection 常驻内存；全集群冷启动无权威值来源，「每节点独立启动与崩溃恢复」无法成立。
- 【测试可实施性·门禁基线错误】触发条件：13 号 §5/§6/§7.4 与变更卡四处把回归基线写为「现有 **37** 个 ctest 全绿」，实测 `ctest --test-dir build -N` 为 **Total Tests: 42**（多出的含 `test_rtdbd_config`、`test_rtdbd_backpressure`、`test_rtdbd_delta`，恰是本特性相关的配置/背压/delta 回归面）。影响：按「37 全绿」验收会漏测 5 个用例或复用旧 build 产物，冻结门禁基线不可复现；`check_all.sh --quick` 明确 `[SKIP] canary` 且复用既有产物，不能作为版本合入证据（变更卡声称的 `bash scripts/check_all.sh` 全量证据 `build/check-all-20261106-164405.log` 需另行核对）。
- 【测试可实施性·判据失真】触发条件：T3 的「20 MB 全量（10 万点）」对比 §4 `page_points: 1024` 与 `id + 128B point` 帧（10 万 × 132B ≈ 12.8MB）不自洽；T4「断网 30 s」相对 §4「约 6.5 s 断链即转全量」使「触发率 100%」近乎恒真；T2「UDS 写 P99 ≤10 μs 不退化」未给基线数据来源；首批表格 10 行能力组而 D10/§7.1/§7.4/变更卡四处写「9 组」，`SELECT(17)` 纳入理由与排除 `FIND_BY_NAME(7)` 矛盾。影响：T3 的 ≤10 s / ≤64 MB 与 harness「覆盖 9 组能力」失去可证伪性；阈值已冻结且「禁止实现者自改、上调须方案评审留痕」，实测不达标将无出口。

## 结论与整改

返工（方案级硬伤，需修改设计裁决后重新提交第二签；不是实现阶段补细节可覆盖）。原因归纳为六组互斥/未定义项：① D3 的 `service_id + epoch`、D5/D8 的 `WAIT` 与 `indurtdb_h_wait_sync()` 均缺 UDS 承载，与 D9「UDS 22 opcode 及 `libindurtdb.a` ABI 完全不变」直接互斥，导致现场主写入口不受迁移屏障保护；② `quick_datagram` 的「不保证可靠、UDP、无回执」与 per-origin 连续 offset + WAIT ack 互斥，IR2/T1/T2 无可成立的传输基础；③ VSOA select 事件循环与 `rtdbd` 单线程 `poll` 主循环合并方案、`rtdbd_ctx_t` 连接级状态抽象缺失，「写权威唯一 / 读路径无锁 / dispatch 与传输无关」三条不变式无法同时保持；④ VSOA 侧无 uid/partition 凭据而首批含 WRITE，跨机写鉴权绕过 `irt_policy_allows` deny-by-default；⑤ `publish` 广播与 NOTIFY/SNAPSHOT_DONE 的 per-conn RBE/定向语义互斥；⑥ 分裂脑收敛终态、稳态双写者仲裁、`boot_id` 与冷启动权威源、快照→backlog→增量跨通道屏障均无定义，而 T1–T5/IR1–IR6 已冻结阈值且禁止实现者自改。

整改条件（须先改 13 号裁决与变更卡，再产出实现计划，不得据此开工写代码）：

1. 重新裁决 D9 边界：明确 `service_id/epoch/WAIT` 究竟「允许 UDS 协议加 1 个可加 opcode 或复用 `rtdbd_write_req_t.source_ts_ns` 保留位」还是「仅 VSOA 前端享有、UDS 侧明示不参与 epoch 隔离」。二选一必须写死，并同步修正 T5 场景与「UDS 侧行为零变化」的适用范围。
2. 重裁 §6/§7.1 传输：`/sync/delta` 改走可靠通道（`cli_datagram` over TCP 或 RPC + 应用级 ack/重传），或保留 quick 但补「offset 空洞检测 → 定向补帧 → 超阈值转全量」的完整规则与 `WAIT` ack 的数据面协议；`quick_publish` 仅用于可丢的通知类，不得承载同步增量。同步给出 `wait.default_acks=1` / `default_timeout_ms=50` 与 6 节点 × 20ms flush 的时延预算是否可达。
