## 1 纪律边界（先立规矩，再谈实现）

### 1.1 开工禁令的解除时机（M0，须用户拍板）

§6 原文「`release_gate.py` 放行前不得开工写代码」与「B 段须写代码后填数」存在张力。本计划将禁令解释为两层：

- **写代码（在专用实现分支做 rtdbd / tests 开发）**：方案已批准、硬条件已闭环，B 段实现天然需要写代码。但为避免首签「实现者自说自话」重演，**M0 需用户明确拍板解除 working-tree 实现禁令**，并确认实现分支策略。
- **合入主线 / 打 tag / 发布**：无论是否写代码，**在 `release_gate.py --conditions` 放行前严禁**。这是硬纪律，不随 M0 解除。

> **M0 决策项（交由用户）**：① 是否正式解除「在分支上写 B 段实现代码」的禁令；② 实现分支策略（如 `feature/v3.12-impl` 从 `release/3.10` 拉出，或由用户指定）；③ 是否沿用现有 working-tree 上的未提交改动（`vsoa/` 已忽略、12 号 DRAFT 保留）。

### 1.2 TDD 深度（强制）

- `tdd:深`：跨模块 + 新协议 + 并发 + 对外契约。**先写 RED 用例看到失败，再写实现 GREEN**；RED 命令与输出须落盘为证据（`docs/08-验证记录/...`），**post-hoc green 不算**。
- 新增/修改的 ctest 集成用例须先有 RED（如「6 节点未连通时 `IR7_PartitionConverge` 失败」），再实现；不得先写实现再补「必然通过」的测试。

### 1.3 阈值冻结纪律

- §9.4：「POC 数字落库前不得把 T1–T5 视为最终冻结值」。B 段 `fields` 填的实测值须为真机/真网取证，禁止实现者自调阈值让测试通过。
- 数值上调（放宽判据）须经方案评审留痕，禁止实现者自改。

### 1.4 提交与发布纪律

- 仓库约定「禁止直接 commit / push，提交需用户确认」。本计划所有改动（含 B 段落库、12 号 DRAFT）须由用户确认后精简聚合提交；不自动提交、不打 tag。

## 4 风险与缓解

- **内存池符号**：`vsoa_*_pool_config` 发布库未导出（§9.4 取证），T3 RSS 预算按默认每连接 256 KB 常驻（6 peer ≈ 1.5 MB）。M1 严禁链接该符号。
- **6 节点编排成本**：需本机/CI 多进程拓扑；M2 先验证单机多进程可跑，再上真机。
- **阈值冻结**：B 段 `fields` 必须真取证，M5 不得调阈值讨好测试；数值上调须经评审。
- **epoch 双写安全**：A 未真死 + 分区 + 同 epoch 双写（IR7）是最高风险路径，M3 的 `IR7_PartitionConverge` 须先 RED（构造双写冲突看是否收敛），再实现 `terminal_hash == dict_max_snapshot_match`。
- **post-hoc green**：M3/M5 严禁「先实现后补通过测试」；RED 证据是交付门禁项（§10.2 纪律）。
