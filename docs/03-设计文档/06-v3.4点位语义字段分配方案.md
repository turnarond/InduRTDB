# v3.4 点位语义字段分配方案

**版本：1.0（草稿，待评审）**
**日期：2026-09-23**
**基线：v3.1.0**
**状态：方案准备（v3.3 架构评审进行中，本方案不阻塞、先备料）**

> 本文解决一个具体约束题：**在不改变 128B 点位布局、不动 ABI 的前提下，v3.4 的工业语义扩展能塞下什么、不能塞下什么，以及不该塞什么。**
> 相关：[`05-读写分离与双通道架构设计.md`](./05-读写分离与双通道架构设计.md)、[`../06-开发规划/08-功能评审与下一步规划.md`](../06-开发规划/08-功能评审与下一步规划.md)。

---

## 1. 结论摘要

| 项 | 结论 |
|---|---|
| 点位可用空间 | 19B（`padding[19]` @ offset 109） |
| Header 可用空间 | **20B**（offset 44–63，此前未被识别） |
| v3.4 可容纳 | **SourceTimestamp（8B） + OPC UA StatusCode（4B）**，用 12B，余 7B 保留 |
| v3.4 可容纳（类型） | int64 / uint32 / float —— 复用 `value` union 内已有 32B，不改布局 |
| **不该放进点位** | **deadband（死区）与 EURange（量程）** —— 按 OT/IT 分界它们属于**配置/上送策略**，不是数据本身语义（见 §4） |
| ABI 影响 | **无**。`sizeof == 128` 不变、既有字段偏移不变、共享内存 stride 不变 |
| 兼容性做法 | 新字段以 **0 表示"未提供/沿用旧行为"**，老段新读、新段老读均正确（见 §6） |

## 2. 现状：精确布局盘点

### 2.1 点位 `indurtdb_point_t`（128B，`packed, aligned(128)`）

| 偏移 | 字段 | 类型 | 大小 |
|---|---|---|---|
| 0–31 | `value` | union{ bool / int32 / double / char[32] } | 32 |
| 32–39 | `timestamp_ns` | `uint64_t` | 8 |
| 40 | `type` | `uint8_t` | 1 |
| 41 | `quality` | `uint8_t` | 1 |
| 42–43 | `unit` | `uint16_t` | 2 |
| 44 | `access` | `uint8_t` | 1 |
| 45–108 | `name` | `char[64]` | 64 |
| **109–127** | **`padding[19]`** | — | **19（可用）** |

### 2.2 Header `irt_header_t`（64B）

实际偏移（依 `src/internal/irt_types.h`）：`magic`0 / `version`4 / `max_points`8 / `max_subscribers`12 / `write_seq`16 / `owner_pid`24 / `stats.writes`28 / `stats.timeouts`36 / **空闲 44–63（20B）**。

> LLD 原表缺少 `owner_pid` 且 stats 偏移有误，已于 2026-09-23 修正。

### 2.3 现有测试对 padding 的约束（关键前置）

| 测试 | 是否校验 padding | 结论 |
|---|---|---|
| `test_c_layout_seqlock.cpp::PointFieldOffsets` | **否**（只断言到 `name`@45） | 拆分 padding 不破坏 |
| `test_c_layout_seqlock.cpp::SizesMatchV2` | 只断言 `sizeof == 128` | 保持不变即可 |
| `test_c_multi_process.cpp::RawLayoutRegression` | 只校验 `value`@0、`type`@40、`quality`@41 | 不破坏 |

**结论：拆分 `padding[19]` 为具名字段，现有测试全部不受影响。**

## 3. 字段需求与空间账

| 需求 | 类型 | 大小 | 是否放得下 |
|---|---|---|---|
| SourceTimestamp（采集时刻） | `uint64_t` | 8 | ✅ |
| OPC UA StatusCode | `uint32_t` | 4 | ✅ |
| deadband（变化阈值） | float/double | 4 / 8 | 技术上可，**但不该放**（§4） |
| EURange（工程量程 min/max） | 2×double | 16 | ❌ 放不下，且不该放 |

---

## 4. 职责辨析：deadband 与 EURange 不该放进点位

按 D6 的 **OT / IT 分界**：

| 项 | 性质 | 归属 |
|---|---|---|
| SourceTimestamp、StatusCode | **数据本身的语义**（这个值何时采的、可信度如何） | ✅ 点位内（OT 面实时数据） |
| deadband / RBE | **上送策略**（变化多少才上报） | ❌ node-server 采集配置（IT 面） |
| EURange / 工程单位量程 | **元数据**（点位如何解释与展示） | ❌ `rtdbd` 元数据区（v4.0 的 name→id 索引一并承载） |

理由：点位结构是**热数据面**，每点 128B × 数万点，任何字段都会放大到整段内存并进入每次读写路径；而死区、量程是**注册期确定、运行期只读**的冷元数据。把它们塞进热路径会浪费内存带宽且混淆职责。

**因此 v3.4 点位内只加 SourceTimestamp 与 StatusCode 两项。**

## 5. 推荐字段布局

```c
typedef struct {
    union { bool b; int32_t i; double d; char str[32]; } value;  /* 0–31   */
    uint64_t timestamp_ns;        /* 32–39  入库时刻（ServerTimestamp） */
    uint8_t  type;                /* 40      */
    uint8_t  quality;             /* 41     兼容视图，由 status_code 派生 */
    uint16_t unit;                /* 42–43   */
    uint8_t  access;              /* 44      */
    char     name[64];            /* 45–108  */
    uint8_t  padding[3];          /* 109–111 保持 8B 对齐前导 */
    uint64_t source_timestamp_ns; /* 112–119 新增：采集时刻（SourceTimestamp） */
    uint32_t status_code;         /* 120–123 新增：OPC UA StatusCode */
    uint8_t  reserved[4];         /* 124–127 保留 */
} __attribute__((packed, aligned(128))) indurtdb_point_t;
```

**对齐考虑**：`source_timestamp_ns` 落在 112（8B 对齐）、`status_code` 落在 120（4B 对齐）。结构体虽为 `packed`，但新字段需要被直接读写（超时检测、质量判定），保持自然对齐可避免 ARM 上的非对齐 64 位访问风险。

**`quality` 与 `status_code` 的关系**（避免双真相源）：

- `status_code` 为**权威**，采用 OPC UA StatusCode 编码（severity 位 + limit 位 + subcode）。
- `quality` 降级为**兼容视图**，写入时由 `status_code` 按映射表派生；老读者继续读 `quality`，行为不变。
- 映射规则需在实现时明确定义（Good / Bad / Uncertain→? / TIMEOUT / SUBSTITUTED 的双向映射），并写测试。

### 5.1 备选方案对比

| 方案 | SourceTS | StatusCode | deadband | 用量 | 评价 |
|---|---|---|---|---|---|
| **A（推荐）** | u64 | u32（完整） | — | 12B | 职责干净，余 7B |
| B | u64 | u16（简码） | float 4B | 14B | 状态码不完整 + 职责错位 |
| C | u64 | u32 | double 8B | 20B | **超 19B，不可行** |

## 6. 兼容性分析（对应 SDK 向前兼容要求）

| 场景 | 行为 | 正确性 |
|---|---|---|
| 新进程读**老段** | `source_timestamp_ns`=0、`status_code`=0 | ✅ 语义定义为"未提供"，退化为旧行为 |
| 老进程读**新段** | 忽略新字段，读 `quality` | ✅ `quality` 由新进程同步派生，值正确 |
| 老进程写新段 | 只写旧字段，新字段保持原值 | ⚠️ 新字段可能残留旧值 → 需在文档声明：老 SDK 与新 SDK 混用期间，新字段不可信 |
| 静态断言 | `sizeof == 128`、既有字段偏移断言 | ✅ 全部保持 |

**必须定义的 0 值语义**：

- `source_timestamp_ns == 0` ⇒ 未提供源时间戳，等同 `timestamp_ns`
- `status_code == 0` ⇒ OPC UA `Good`，等价 `INDURTDB_QUALITY_GOOD`
- `reserved` 保持全 0

> 混用场景（老 SDK 写 / 新 SDK 读）无法完全避免字段残留，应在 SDK 手册明确声明，并建议升级时全量重建段或由 `rtdbd` 统一重写（v3.3 之后 `rtdbd` 是唯一写者，该问题自然消失）。

## 7. 其余 v3.4 项的可行性

| 项 | 可行性 |
|---|---|
| 类型扩展 int64 / uint32 / float | ✅ 复用 `value` union 内 32B，仅新增 `INDURTDB_TYPE_*` 枚举与 API，布局不变 |
| blob | ⚠️ 只能内联 ≤31B（`value` 空间），跨进程不能放指针。更大 blob 需 v4.0 元数据区 |
| Header CRC | ✅ 放 Header 空闲区（44–63）：`crc32`@44（4B）+ `flags`@48（4B）+ 保留 12B |
| 版本协商 | ✅ `version` 字段已存在，需补充"版本不匹配时的行为"定义与测试 |
