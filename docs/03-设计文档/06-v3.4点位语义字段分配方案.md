# v3.4 点位语义字段分配方案

**版本：1.1（2026-09-23 修订）**
**日期：2026-09-23**
**基线：v3.1.0**
**状态：方案准备（v3.3 架构评审进行中，本方案不阻塞、先备料）**

> 本文解决一个具体约束题：**在不改变 128B 点位布局、不动 ABI 的前提下，v3.4 的工业语义扩展能塞下什么、不该塞什么。**
> 相关：[`05-读写分离与双通道架构设计.md`](./05-读写分离与双通道架构设计.md)、[`../06-开发规划/08-功能评审与下一步规划.md`](../06-开发规划/08-功能评审与下一步规划.md)。

---

## 0. 修订说明（v1.0 → v1.1）

v1.0 曾提议以 **OPC UA `StatusCode` 为权威**、`quality` 降为其派生视图。**该提议已被否决**，理由：

1. **混淆了领域模型与协议编码**：`StatusCode` 是过载的——既表达数据质量（`BadSensorFailure`），也表达操作结果（`BadInvalidArgument`、`BadNotFound`）。拿它当数据质量的权威模型不合适。
2. **工业现场以 `quality` 为主概念**：OPC DA 的经典 `Quality`、PI / Historian 的 `Good / Questionable / Bad`，工程师的思维模型就是"这个点质量好不好"。`StatusCode` 只是 UA 的一种编码方式。
3. **违反 OT / IT 分界（决策 D6）**：协议编码属于北向适配，是 IT 面的职责，不该进入热数据面。

**v1.1 改为：`quality` 为权威并扩展取值；`StatusCode` 不进点位，改由纯函数在北向映射时现算。**

---

## 1. 结论摘要

| 项 | 结论 |
|---|---|
| 点位可用空间 | 19B（`padding[19]` @ offset 109） |
| Header 可用空间 | 20B（offset 44–63，供 v3.4 CRC / flags） |
| **v3.4 点位内实际新增** | **仅 `SourceTimestamp`（8B）**，用 8/19，余 11B 保留 |
| **quality 扩展** | **不新增字段**。现有 `uint8_t` 只用 4 个值，改为分层位布局（基础码 4bit + 量程位 2bit + 预留 2bit） |
| **StatusCode** | **不进点位**，提供纯函数 `indurtdb_quality_to_status_code()` 供北向映射 |
| 类型扩展 | int64 / uint32 / float 复用 `value` union 内已有 32B，布局不变 |
| **不该放进点位** | **deadband（上送策略）与 EURange（元数据）**，见 §4 |
| ABI 影响 | **无**：`sizeof == 128` 不变、既有字段偏移不变、stride 不变 |

## 2. 现状：精确布局盘点

### 2.1 点位 `indurtdb_point_t`（128B，`packed, aligned(128)`）

| 偏移 | 字段 | 类型 | 大小 |
|---|---|---|---|
| 0–31 | `value` | union{ bool / int32 / double / char[32] } | 32 |
| 32–39 | `timestamp_ns` | `uint64_t` | 8 |
| 40 | `type` | `uint8_t` | 1 |
| **41** | **`quality`** | **`uint8_t`** | **1（本次扩展取值）** |
| 42–43 | `unit` | `uint16_t` | 2 |
| 44 | `access` | `uint8_t` | 1 |
| 45–108 | `name` | `char[64]` | 64 |
| **109–127** | **`padding[19]`** | — | **19（可用）** |

### 2.2 Header `irt_header_t`（64B）

实际偏移（依 `src/internal/irt_types.h`）：`magic`0 / `version`4 / `max_points`8 / `max_subscribers`12 / `write_seq`16 / `owner_pid`24 / `stats.writes`28 / `stats.timeouts`36 / **空闲 44–63（20B）**。

> LLD 原表缺少 `owner_pid` 且 stats 偏移有误，已于 2026-09-23 修正。

### 2.3 现有测试对 padding 的约束（关键前置）

| 测试 | 是否校验 padding | 结论 |
|---|---|---|
| `test_c_layout_seqlock.cpp::PointFieldOffsets` | **否**（只断言到 `name`@45） | 拆分 padding 不破坏 |
| `test_c_layout_seqlock.cpp::SizesMatchV2` | 只断言 `sizeof == 128` | 保持不变即可 |
| `test_c_multi_process.cpp::RawLayoutRegression` | 只校验 `value`@0、`type`@40、`quality`@41 | 不破坏 |

**结论：改动 `padding` 区域与 `quality` 取值，现有测试全部不受影响。**

## 3. quality 取值扩展方案（v3.4 核心）

### 3.1 位布局

```
bit   7  6   5  4   3  2  1  0
     [预留2] [limit2] [基础质量码 4bit]
```

| 段 | 位 | 含义 |
|---|---|---|
| 基础质量码 | bit 0–3 | 16 种，**现有 0–3 取值保持不变** |
| 量程位 limit | bit 4–5 | `00` 无 / `01` Low / `10` High / `11` Constant（对齐 OPC UA limit bits 语义） |
| 预留 | bit 6–7 | 必须为 0 |

### 3.2 基础质量码表

| 值 | 名称 | 状态 | 说明 |
|---|---|---|---|
| 0 | `GOOD` | 现有 | 值可信 |
| 1 | `BAD` | 现有 | 值不可信 |
| 2 | `TIMEOUT` | 现有 | 超过 `check_timeouts` 阈值未更新 |
| 3 | `SUBSTITUTED` | 现有 | 人工置值/替代值 |
| 4 | `UNCERTAIN` | **新增** | 值可能可信但精度存疑（对齐 OPC UA 三态） |
| 5 | `NOT_INITIALIZED` | **新增** | 点位从未写入 |
| 6 | `OUT_OF_SERVICE` | **新增** | 点位停用，值不更新 |
| 7 | `COMM_FAILURE` | **新增** | 采集链路中断 |
| 8 | `SENSOR_FAILURE` | **新增** | 传感器故障 |
| 9 | `LAST_KNOWN` | **新增** | 保留最后已知值（通信中断后） |
| 10 | `CONFIG_ERROR` | **新增** | 配置错误（类型/量程非法） |
| 11–15 | 预留 | — | 后续扩展 |

### 3.3 访问宏

```c
#define INDURTDB_QUALITY_BASE(q)   ((uint8_t)((q) & 0x0Fu))
#define INDURTDB_QUALITY_LIMIT(q)  ((uint8_t)(((q) >> 4) & 0x03u))
#define INDURTDB_QUALITY_MAKE(base, limit) \
        ((uint8_t)(((base) & 0x0Fu) | (((limit) & 0x03u) << 4)))

#define INDURTDB_LIMIT_NONE     0u
#define INDURTDB_LIMIT_LOW      1u
#define INDURTDB_LIMIT_HIGH     2u
#define INDURTDB_LIMIT_CONSTANT 3u
```

判定规则：**"值是否可用"只看基础码**；量程位是与可用性正交的附加信息（`GOOD | HIGH` 表示值有效但超量程高限）。

```c
static inline bool indurtdb_quality_is_good(uint8_t q) {
    return INDURTDB_QUALITY_BASE(q) == INDURTDB_QUALITY_GOOD;
}
```

### 3.4 OPC UA 对接：纯函数映射，不占内存

协议编码属于 IT 面（决策 D6）。库内仅提供**纯函数**供北向/OPC UA Server 调用：

```c
uint32_t indurtdb_quality_to_status_code(uint8_t quality);
```

| InduRTDB | OPC UA StatusCode |
|---|---|
| `GOOD` | `0x00000000`（Good） |
| `UNCERTAIN` | `0x40000000`（Uncertain） |
| `BAD` | `0x80000000`（Bad） |
| limit Low | `| 0x00000100` |
| limit High | `| 0x00000200` |
| limit Constant | `| 0x00000400` |
| `SENSOR_FAILURE` | `BadSensorFailure` |
| `COMM_FAILURE` | `BadCommunicationError` |
| `OUT_OF_SERVICE` | `BadOutOfService` |
| `LAST_KNOWN` | `UncertainLastUsableValue` |
| `SUBSTITUTED` | `GoodLocalOverride \| 0x00000400` |

映射表须有单测覆盖（双向：quality → StatusCode，StatusCode → quality 的降级路径）。

## 4. 职责辨析：不该放进点位的两项

按 D6 的 **OT / IT 分界**：

| 项 | 性质 | 归属 |
|---|---|---|
| `timestamp_ns` / `source_timestamp_ns` / `quality` | **数据本身的语义** | ✅ 点位内（OT 面实时数据） |
| OPC UA `StatusCode` | **协议编码** | ❌ 北向适配（IT 面），用纯函数现算 |
| deadband / RBE | **上送策略**（变化多少才上报） | ❌ node-server 采集配置 |
| EURange / 量程 | **元数据**（如何解释与展示） | ❌ v4.0 `rtdbd` 元数据区（与 name→id 索引一并承载） |

点位结构是**热数据面**，每点 128B × 数万点，任何字段都会放大到整段内存并进入每次读写路径；死区与量程是**注册期确定、运行期只读**的冷数据。

## 5. 字段布局（v3.4 点位内实际改动）

```c
typedef struct {
    union { bool b; int32_t i; double d; char str[32]; } value;  /* 0–31   */
    uint64_t timestamp_ns;        /* 32–39  入库时刻（ServerTimestamp） */
    uint8_t  type;                /* 40      */
    uint8_t  quality;             /* 41     权威质量；v3.4 起按 §3 分层位布局 */
    uint16_t unit;                /* 42–43   */
    uint8_t  access;              /* 44      */
    char     name[64];            /* 45–108  */
    uint8_t  padding[3];          /* 109–111 保持 8B 对齐前导 */
    uint64_t source_timestamp_ns; /* 112–119 新增：采集时刻（SourceTimestamp） */
    uint8_t  reserved[8];         /* 120–127 保留 */
} __attribute__((packed, aligned(128))) indurtdb_point_t;
```

**对齐**：`source_timestamp_ns` 落在 112（8B 对齐），避免 ARM 上非对齐 64 位访问风险。
**用量**：8/19B，余 11B（远比 v1.0 的 12B + 双字段方案干净）。

## 6. 兼容性分析

### 6.1 前提：当前无外部使用者（2026-09-23 确认）

> **InduRTDB 当前处于开发节点，唯一使用者是 `node-server` 与总体框架 `edge-framework`，均在同一组织内，可同步升级。没有需要支持的外部/存量 SDK。**

由此得出：**本节之前的"老 SDK 混用"顾虑不成立**，不需要为兼容而保留降级路径或兼容模式。设计可直奔目标形态。

### 6.2 但有三条不能放松

| # | 约束 | 原因 |
|---|---|---|
| 1 | **同一主机上所有进程必须同时升级** | 共享内存布局一旦变更，新旧进程不能混跑（不是 SDK 兼容问题，是部署约束）。host 进程与容器进程需协调升级顺序与停机窗口 |
| 2 | **首个对外发布前必须冻结 ABI** | 一旦有外部用户，再改布局就要迁移工具 + 双版本共存。**当前窗口是改布局成本最低的时候** |
| 3 | **静态断言与偏移锁定不能省** | 即使只有内部使用者，布局回归测试仍是防"手滑改坏"的唯一手段 |

### 6.3 场景矩阵（在"可同步升级"前提下）

| 场景 | 行为 | 正确性 |
|---|---|---|
| 升级后重建段 | 新布局，`source_timestamp_ns` 初始化为 0 | ✅ |
| 复用已有段（未清理 `/dev/shm`） | 旧字节被按新布局解释 | ❌ **必须避免**：升级流程需显式清理段或做版本协商拒绝挂载 |
| 静态断言 | `sizeof == 128`、既有偏移断言 | ✅ |

**必须约定的 0 值语义**：

- `source_timestamp_ns == 0` ⇒ 未提供源时间戳，等同 `timestamp_ns`
- `quality` 高 4 位为 0 ⇒ 无量程限制
- **版本协商（v3.4 任务）**：`irt_header_t.version` 不匹配时**拒绝挂载**并返回明确错误，不得静默按新布局解释旧段

> 删除了 v1.1 之前的"老 SDK 兼容模式"设计——在已确认无外部使用者后，该设计属于为不存在的问题增加复杂度（YAGNI）。

## 10. 【待决策】是否趁无外部使用者的窗口，把布局变更一次性做完？

当前 v3.4 计划在**保持 ABI v1** 的前提下"打补丁"（复用 padding）；v4.0 才做布局 v2（name→id 索引、去单例化、容量扩容）。

在"无外部使用者、可同步升级"的前提下，存在另一种更经济的路线：

| 路线 | 做法 | 代价 | 收益 |
|---|---|---|---|
| **甲（现行）** | v3.4 打补丁保持 ABI v1 → v4.0 再改布局 v2 | **两次变更、两次迁移协调**；v3.4 加的字段可能在 v4.0 又要挪 | 风险分散 |
| **乙（建议评估）** | v3.4 直接做**布局 v2 + API v2**：字段整理 + name→id 索引 + 去单例化（句柄化 API）+ 元数据区 | 一次变更较大，但只需一次迁移 | **只有一次迁移成本**；产品化发布时 ABI 已定稿 |

**支持乙的理由**：现在改零成本；等有外部使用者后，改布局要迁移工具 + 双版本共存 + 客户协调，成本高一个量级。**当前窗口是改 ABI 最便宜的时候。**

**支持甲的理由**：v3.3 已是架构大变更（读写分离），紧接 v3.4 再改布局会叠加风险；且 name→id 索引设计上依赖 v3.3 的 `rtdbd`（元数据区归属、唯一写者），顺序上 v3.3 需先落地。

**建议**：不急于定，等 v3.3 架构评审结论出来后再评估。但**必须在首个对外发布前完成布局定稿**，并把"ABI 冻结时点"作为一个明确的里程碑写进路线图。
