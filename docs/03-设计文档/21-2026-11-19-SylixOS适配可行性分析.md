## 0 结论摘要

**技术上可行，但不是「开箱即用」：核心库在 SylixOS 上处于「纸面可构建、代码未验证」的技术债占位状态；VSOA SDK 官方支持 SylixOS、障碍最小；真正的移植面集中在 rtdbd 的 Linux 专有调用与共享内存持久性语义。**

| 层次 | 成熟度判定 | 主要障碍 | 优先级 |
|---|---|---|---|
| libvsoa 1.9.1 SDK | ✅ 官方支持 SylixOS、11 架构预编译库齐备（**仅指 SDK，非 InduRTDB 产品支持**） | 仅当 PLC 架构不在预编译列表时需重编 SDK | 低 |
| 核心库 `libindurtdb.a` | ⚠️ 纸面可构建、从未在目标板验证；ABI 静态断言待目标架构验证 | OSAL 是 POSIX 逐行拷贝；`__atomic_*`/`kill(pid,0)`/裸文件 I/O 未间接化；32/64 位对齐与大端字节序（§3.6） | 中 |
| rtdbd 写权威进程 | ❌ Linux-only，CMake 整体排除 | `SO_PEERCRED` 鉴权、`/proc/self/exe` supervisor、`poll`+`fd_set`、`/run/indurtdb` UDS 路径 | 高 |
| client / 监控台 | ❌ client Linux-only；监控台跑外部 PC | client 强依赖 UDS；监控台与 rtdbd 之间是 UDS 通道 | 中 |
| 集群语义（epoch/增量/重启） | ⚠️ 平台无关设计可直接继承，SylixOS 行为待验证 | 共享内存整机重启持久性、`CLOCK_MONOTONIC_RAW`（OSAL 未用、BSP 待证实）、跨机时钟同步 | 高（验收前置） |

**一句话**：SDK 不是瓶颈，核心库是「验证债」而非「实现债」，rtdbd 的 Linux 专有依赖才是真正需要改造的部分；在所有移植完成前，B 段 F2/F3a/F4 真值仍不可得，发布门维持 FAIL 8。

## 2 现状盘点（基于只读调研，逐项带证据）

### 2.1 OSAL 抽象层：只有时间 + 共享内存两类

`src/osal/` 仅 4 个文件：`irt_osal.h`（48 行）、`posix/irt_osal_posix.c`（109 行）、`sylixos/irt_osal_sylixos.c`（116 行）、`tests/unit/test_c_osal.cpp`。头文件仅导出 **7 个函数**（`irt_osal.h:20-42`）：

| 类别 | 函数 | SylixOS 实现判定 |
|---|---|---|
| 时间 | `irt_time_now_ns` / `irt_time_realtime_ns` / `irt_time_sleep_ns` | 完整实现；唯一实质差异是单调时钟 ID：POSIX 用 `CLOCK_MONOTONIC_RAW`（`posix:22`），SylixOS 用 `CLOCK_MONOTONIC`（`sylixos:29`） |
| 共享内存 | `irt_shm_os_map` / `irt_shm_os_unmap` / `irt_shm_os_is_owner` / `irt_shm_os_claim_ownership` | 完整实现，直接复用 `shm_open`/`mmap`/`munmap` 等 POSIX 调用（`sylixos:56-116`） |

**关键事实**：

1. OSAL **没有**抽象 sem / thread / mutex / atomic / socket / 进程管理——本文不沿用「OSAL 已全面抽象」的错误前提。
2. SylixOS 实现是 POSIX 实现的**逐行拷贝**（仅时钟 ID 一处差异），两份文件 `#include` 集合完全相同，**没有调用任何 SylixOS 原生 API**（如 `shmCreate`/`SylixOS.h`）。与设计文档 `01-概要设计文档.md:179` 曾规划的 `shmCreate + mmap` 不符。
3. 无任何证据表明 SylixOS 实现被编译/运行过：CI 仅 `ubuntu-latest`（`.github/workflows/ci.yml:24-30`），SylixOS 下 `tests` 被 CMake 排除（`CMakeLists.txt:148`），文档反复记「从未在目标板验证」（`07-部署运维/README.md:71`、`08-功能评审与下一步规划.md:235`）。

**判断**：核心库的 OSAL 是「验证债」——代码齐全但未经交叉编译与目标板实测，不是「实现缺失」。

### 2.2 CMake 构建：核心库可编、其余全被 Linux guard 排除

根 `CMakeLists.txt` 的平台分支（`:16-24`）：Linux 追加 `-D_GNU_SOURCE -DINDURTDB_OS_LINUX` 并用 posix OSAL；SylixOS 追加 `-DINDURTDB_OS_SYLIXOS`（**无** `-D_GNU_SOURCE`）并用 sylixos OSAL；其他平台 FATAL_ERROR。

| Target | 位置 | SylixOS 下 |
|---|---|---|
| `indurtdb` 静态库 | `:97` | ✅ 构建（核心源 + `${IRT_OSAL_SRC}`，`:26-36`） |
| `rtdbd` / `indurtdb-client` / `irt_diag` / `tests` / `examples` | `:109-155`（均 `if Linux`） | ❌ 全部跳过 |
| `target_link_libraries(indurtdb PUBLIC rt pthread)` | `:103-105` | ❌ 仅 Linux 链接 |
| VSOA 探测块 | `:68-93`（`if ENABLE_VSOA AND Linux`） | ❌ 整体跳过；即便显式 `-DINDURTDB_ENABLE_VSOA=ON` 也静默无效，`VSOA_LIB_SUBDIR` 默认 `lib/linux/x86_64`（`:67`）永不被校验 |

**交叉工具链**：全仓 `*.cmake` **0 个**、`*toolchain*` **0 个**；`cmake/` 仅两个安装模板（`InduRTDBConfig.cmake.in`、`indurtdb.pc.in`）。素材来源于外部：

- `08-功能评审与下一步规划.md:320`：本仓无 toolchain 文件与 SylixOS 头路径；外部已验证素材 `ko_middleware/sylixos-middleware_bak/sylixos.toolchain.cmake`（502 行，接受 `CMAKE_SYLIXOS_BASE_PATH`），并记坑：base 顶层须同时有 `config.mk` 与 `libsylixos/`。

### 2.3 核心库的 Linux/POSIX 直接依赖

已被 OSAL 间接化：`shm_open`/`mmap`/`ftruncate`/`clock_gettime`/`nanosleep` 在 `src/core|api|internal` 无直接调用（`irt_shm.c:86,160` 经 OSAL）。未被封装的核心库直接使用：

- `getpid()` / `kill(pid,0)`：`irt_shm.c:98,138-141`（owner 记录与崩溃存活探测）、`indurtdb.c:84,469,987`。`kill(pid,0)` 是崩溃自愈的关键路径，SylixOS 需确认语义。
- `__atomic_*` builtins：`irt_shm.c`、`irt_point_manager.c`、`irt_index.c`、`internal/irt_seqlock.h`、`api/indurtdb.c` 大量使用。`CODEBUDDY.md:156` 明确「只用 `__atomic_*`，禁用 `stdatomic.h`（SylixOS 支持不完整）」——这是有意为之的 SylixOS 友好设计。
- 裸文件 I/O：`irt_delta.c:20,40` 的 `open`/`close`、`indurtdb.c:117,642` 的 `close(fd)`、`irt_config.c` 的 `fopen`/`fclose`（C 标准 IO，无平台风险）。

`/dev/shm` **未在核心 C 代码硬编码**：实际是 `IRT_SHM_PREFIX "/indurtdb_"`（`irt_shm.h:16`）+ `snprintf`（`irt_shm.c:82-86`），交给 OSAL。但 POSIX shm 名字空间假设是硬编码的，且 `13` 号 `:202` 以 Linux `/dev/shm` 语义区分「进程重启段仍在 / 整机重启段丢失」——这一点在 SylixOS 上必须验证（见 §3.4）。

### 2.4 VSOA SDK：官方支持 SylixOS，障碍最小

外部 SDK `/home/yanchaodong/work/acoinfo/vsoa_framework`（libvsoa 1.9.1，以宏 `VSOA_LIB_VERSION` 为准）：

- 存在独立 `lib/sylixos/` 产物树，覆盖 **11 个架构**（`aarch64 / arm / csky / loongarch64 / mips / mips64 / powerpc / riscv / sparc / x86 / x86_64`），对照 `lib/linux/` 仅 5 个——SylixOS 覆盖反而更广。
- 构建体系显式支持：`BUILD_AND_INSTALL.md:56-64`（`-DCMAKE_TOOLCHAIN_FILE=.../sylixos.cmake`）、`:182-187`（`package-sdk.py --os sylixos`）；`config.mk:7,23-25`（`SYLIXOS_BASE_PATH`）。
- 平台头 `include/libvsoa/vsoa_platform.h:59-61,67-73` 对 `SYLIXOS` 有条件编译（eventfd、`VSOA_HAS_SIN_LEN` 等）。仓内 1.8.0 只读参考副本同样已适配（`vsoa/vsoa/libs/libvsoa/vsoa_platform.h:59,67,71` 等）。
- rtdbd 所需全部库在 `lib/sylixos/aarch64/` 齐备（`libvsoa-server.so`、`libvsoa-client.so`、`libvsoa-json.so`、`vsoa.so` 等）。

**判断**：SDK 本身不是瓶颈（此处的 ✅ 仅指 libvsoa SDK，非 InduRTDB 产品平台支持——后者仍为「未验证、不支持生产部署」，见 `07-部署运维/README.md:71`）。仅当目标 PLC 架构不在 11 个预编译列表内、或需用指定 SylixOS Base 重编时，SDK 侧重编工程量落在 `config.mk` / `CMakeLists.txt` / `scripts/package-sdk.py` / `vsoa_platform.h`——属「重编/补架构」，非「新增 SylixOS 支持」。

**仓内探测门禁的 SylixOS 化（不可漏算）**：即便 SDK 现成，仓内 `scripts/check_vsoa_sdk.py:18` 把库路径硬编码为 `lib/linux/x86_64`，`:76-82` 的 argparse 无 `--os/--arch/--lib-subdir` 参数；`CMakeLists.txt:76-83` 调用时只传 `--root`/`--json`，未透传 `:67` 的 `VSOA_LIB_SUBDIR`。因此现状下该脚本**无法**探测 `lib/sylixos/<arch>`。SylixOS 接入必须同时改造：① 脚本增平台/架构参数并指向 `lib/sylixos/<arch>`；② CMake 在 SylixOS 分支透传 `VSOA_LIB_SUBDIR` 与架构。这项工程量属仓内 CMake/脚本改造（详见 §3.2、§5 G0）。仓内 `vsoa/` 1.8.0 只读副本不动（F5 纪律）。

### 2.5 rtdbd 的 Linux 专有依赖：真正的主战场

| 依赖 | 证据 | SylixOS 可替代性 | 风险 |
|---|---|---|---|
| `SO_PEERCRED` / `struct ucred` 鉴权 | `rtdbd.c:794-800` | Linux 专有，SylixOS 未必有等价凭据机制 | **UDS 启用时最高**；若裁撤 UDS 写通道则降为中（`rtdbd_authz.c:15-36`、`rtdbd_dispatch.h:95,114` 证实 VSOA 侧鉴权不依赖它，见 §3.3） |
| `/proc/self/exe` + `fork`/`execv`/`waitpid`/`kill` supervisor | `rtdbd.c:1916-2014,1963,1992` | `/proc/self/exe` 语义待验证 | 高——但 supervisor 是可选模式（`-S`），现场可禁用规避 |
| `poll` + `fd_set`（`FD_SETSIZE`）主循环 | `rtdbd.c:2680-2735`、`vsoa_adapter.c:633-646` | POSIX poll 通常有；`FD_SETSIZE` 上限待验证 | 中 |
| UDS `/run/indurtdb/default.sock`（`AF_UNIX`，非 abstract、非 `/tmp`） | `rtdbd.c:2204,2596-2613` | SylixOS 通常有 AF_UNIX；`/run/indurtdb` 是否存在/可写待确认 | 中 |
| `clock_gettime(CLOCK_MONOTONIC/REALTIME)` 直接调用 | `rtdbd.c:161,208`、`stats.c:19`、`logbuf.c:24` | 未走 OSAL；SylixOS libc 需提供 | 低-中 |

**重要缓解事实**：主写入口已切到 **VSOA loopback**（`vsoa_adapter.c:606-630`，server 绑定 `INADDR_LOOPBACK` 于 `:615`），VSOA 侧 NOTIFY 用 per-client 定向 `vsoa_server_cli_datagram`（`:261`），鉴权来源判据已抽成传输无关纯函数（`rtdbd_authz.c:11-13,24-26,66-76`）。即：Linux 专有依赖集中在 **legacy UDS 通道与 supervisor**，核心写/同步/通知路径已具备平台可移植的基础。

`client/` 强依赖 UDS（`client.c:177-190`、`irtcli_main.c:22`），且 `13` 号 `:32,100` 明确 UDS opcode 与 `libindurtdb.a` ABI 一字不改——client 是 ABI 冻结的 legacy 通道，SylixOS 上要么保留等价 UDS 路径，要么不在设备上使用 client（用 VSOA 入口替代）。监控台 `tools/rtdb-monitor` 是跑在外部 PC 的 Python/FastAPI + Vue（`README.md:4-17`），但其与 rtdbd 之间是 UDS（`rtdb_client.py:230-232`），若设备上 rtdbd 不暴露同路径 UDS，监控链路会断——需另设 VSOA 侧管理通道或部署代理。

## 3 可行性分层结论

### 3.1 核心库：可编、需验证，非实现阻塞

CMake 已有 SylixOS 分支且 OSAL 函数齐全，无空壳/TODO/ENOSYS。目标板验证前的最小动作是：引入外部 toolchain 文件 + 交叉编译 `libindurtdb.a` + 在板上跑基础读写/多进程/soak。风险点是 `__atomic_*` on target、`kill(pid,0)`、共享内存语义。

> **2026-11-19 实测更新**：`__atomic_*` 风险已实证并闭环——G1 发现非对齐 64 位 `fetch_add`（`stats`@28/36）在 SylixOS 触发 `__aarch64_ldadd8_relax` 内核异常，经变更卡 `v3.12-SylixOS-atomic64-alignment修复.md` 修复（写锁内普通自增）后板上 `SMOKE_RESULT: PASS`、并发写计数精确（详见 `08-验证记录/v3.12-SylixOS-atomic64修复实施报告.md`）。`kill(pid,0)` 在新 harness 中因 SylixOS 无 fork 标 N/A（未验证）；共享内存 owner/崩溃恢复经 reopen 一致性用例 PASS。

### 3.2 VSOA：SDK 现成，接入方式是主要工作

真正工作不是 SDK 移植，而是让 rtdbd 在 SylixOS 构建时纳入 VSOA 源与链接目录：当前 VSOA 探测块被 `if(... AND Linux)` 排除（§2.2），需设计 SylixOS 下的 `VSOA_SDK_ROOT`/`VSOA_LIB_SUBDIR` 指向 `lib/sylixos/<arch>` 并通过 `check_vsoa_sdk.py`。这属于 CMake 与配置改造，不涉及 SDK 代码。

### 3.3 rtdbd：需分模块裁剪，优先保留 VSOA 主路径

建议按「主路径优先、legacy 可裁」推进：

1. **必保**：VSOA loopback 写入、session/鉴权纯函数、增量同步与订阅重建——这部分平台无关，风险主要在构建与 fd 合并。
2. **需改**：`SO_PEERCRED` 鉴权——UDS 侧来源凭据在 SylixOS 无等价机制时，明确「UDS 通道在 SylixOS 上不承载写」，改由 VSOA hello 握手（token + service_id）承担身份绑定（`14` 号 M1.10 已实现）。这是**契约层面**决定，须评审。
3. **可裁**：`-S` supervisor（`/proc/self/exe`）、`/run/indurtdb` UDS listener、client/监控台 UDS 通道——现场若只用 VSOA 入口，可先不移植。

### 3.4 共享内存持久性：决定 IR6 重启判据的真值

`13:202` 基于 Linux `/dev/shm` 假设「进程重启段仍在、整机重启段丢失」。SylixOS 的 `shm_open`/`mmap` 段是否落在掉电丢失的内存区，`/dev/shm` 是否存在，直接决定 `IR6` 的 `proc_restart_no_fullsync` 与 `machine_restart_pull_full` 两条判据（`20:27,73`）。这是**必须在目标板实测**的语义，无法由代码分析替代，且与 F4（整机重启）强相关。

### 3.5 跨机时钟：PTP/NTP 是同步验收前置

PLC 设备时钟不可信、物理时间戳不参与排序（`13:18,37`）；`19:167` ③本机用 `CLOCK_MONOTONIC_RAW`、④跨机须 PTP/NTP 同步并声明偏移上限。关于 RAW：仓内 OSAL 的 SylixOS 实现用的是 `CLOCK_MONOTONIC`（`sylixos/irt_osal_sylixos.c:29`），**未使用 RAW**；「SylixOS 用户态是否定义 `CLOCK_MONOTONIC_RAW`」尚未由 BSP 头文件证实（疑似缺失，待 G0 核实），本文不外推为确定事实。适配时需确认 SylixOS 单调时钟上电起点行为（`cluster/rtdbd_peers_global.c:58` 的 boot_id 依赖），否则「进程重启不触发全量」的摘要续传会误判。

### 3.6 跨架构 ABI 与运行时约束（影响「验证债」判定的关键维度）

SDK 的 SylixOS 11 架构既含 **32 位**（arm/csky/mips/riscv/sparc）又含 **大端**（powerpc/sparc）。共享内存布局与线协议是这个维度上「可行性」的真正考验，不能只当作板级验证：

- **已有机械防线**：`src/internal/irt_types.h:59-105` 用 `IRT_STATIC_ASSERT` 锁死 `sizeof(irt_header_t)==128` 与 `offsetof(...)` 各字段偏移（`packed/aligned(64)`）；线协议 `rtdbd/include/rtdbd/protocol.h:160-417`、`client/include/irtcli/client.h:100,128` 同样有编译期断言。这些断言在交叉编译时会机械暴露 32/64 位对齐差异——若失败属**编译期阻塞**，而非「验证债」。
- **仍需实测/设计确认**：① 32 位下 `size_t`/指针宽度变化是否影响任何未用定长类型（`uint32_t`/`uint64_t`）的字段；② 大端架构上线协议多字节字段是否统一网络序（需逐字段核对 `protocol.h` 与 `rtdb_client.py` 的 `struct` 格式）；③ SylixOS 单段 shm 容量上限能否容纳目标 `max_points`（10 万点 × 128B ≈ 12.8 MB）+ 索引/元数据/订阅区；④ SylixOS 小栈配置与 `__atomic_*`/嵌套调用栈深度（`CHANGELOG.md:349`）。
- **结论修正**：§3.1「核心库是验证债而非实现债」成立的前提是「静态断言在目标架构通过」。G0 交叉编译必须把静态断言通过作为硬退出判据；若 32/64 位对齐断言失败，则该判定升级为「实现债」，须回到 ABI 设计评审。
