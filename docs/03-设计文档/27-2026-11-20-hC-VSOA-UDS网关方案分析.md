# h-C VSOA↔UDS 网关方案分析（SDD 第一步）

> **状态**：v3（独立评审发现 1 P0 + 3 P1 + 4 P2 已返工 + 用户 2026-11-21 u-0~u-E 裁决落痕，见 §5.1）。纯文档、`tdd:免`；**u-0=设备侧代理**（不是外部 PC 直连设备）、u-A=只读类含 GET_PEERS、u-B Linux/u-C 放弃经网关 peers set/u-D 单只读服务身份/u-E listener≤16 且先交付方案暂不实现——本文不是开工授权。
> **触发**：用户 2026-11-20「推进 h-C」；h-C 由 22 号 G2 方案裁决「排除出 G2、另立」（22:167），目的是 SylixOS 裁 UDS 主路径后保住外部 PC 监控台。
> **边界**：网关不新增 UDS opcode、不改 ABI（13 号 §2 D9/:32、§6/:99-100 冻结 22 opcode，允许尾部 23/24 但已被 `/sync/peers` 占用）、不改发布门 FAIL 8/B 段 fields、不改对外平台口径；实现须另立变更卡 + 冻结基线 + 独立评审 + 开工授权。

## 1 问题与目标

SylixOS 裁 UDS 主路径（q-B）后，跑在外部 PC 的监控台 `tools/rtdb-monitor` 与 `client/` 库依赖本机 AF_UNIX v3 二进制协议，无法直连设备 rtdbd。h-C 目标是在外部 PC 放一个**薄 VSOA↔UDS 网关**：本机暴露 AF_UNIX socket 给零改动的 `rtdb_client.py`，网络侧用 VSOA client 连 rtdbd，保住监控台。**用户 u-0 裁决后，网关拓扑调整为"设备侧本地代理 + 外部 PC 瘦网关"两跳**（见 §3.2）。

**调研发现的两个关键事实（决定拓扑与范围）**：

1. **身份模型结构性矛盾（P0，已由 u-0 裁决）**：现有 VSOA 身份模型在 **hello 阶段**就对 PLC/sync_admin 角色强制来源 127/8 loopback（`rtdbd_authz.c:19-26`，经 `vsoa_adapter.c:171-176` 调用）。外部 PC 网关来源是外部 IP → **hello 直接 DENIED，整个会话建立不了**。旁路全堵：生产 `allow_unauthenticated=false`、`sync_peer` 只能访问 `/sync/*` 且不得收 NOTIFY。**用户裁决 u-0=设备侧代理**：在设备上跑本地代理（来源 127/8，hello 合规），外部 PC 经该代理中转，把"外部来源"转为"设备本地来源"——不改核心鉴权模型（13 号 §8.3-4 单一真源）。
2. **URL 覆盖不足（范围，u-A 裁决）**：只桥接 13 个已镜像 URL 也不够——监控台依赖 UDS-only opcode（`LIST=11`/`GET_META=8`/CRUD `12/13/14`/`GET_LOG=15`/`FIND_BY_NAME=7`/`GET_PEERS=24`），不在 13 镜像表内；只桥 13 URL 会导致点位清单、元数据、日志、CRUD、按名查询、成员表全部失效。**用户裁决 u-A=只读类含 GET_PEERS**（list/find/meta/logs/peers get），CRUD 第二阶段。

**目标（按 u-0~u-E 裁决）**：给出"能让监控台真正可用"的两跳网关方案——设备侧本地代理（hello 合规）+ 外部 PC 瘦网关（UDS↔VSOA），URL 补齐走不新增 opcode 的 URL 层扩展，明确身份映射与容量边界，区分"网关侧"与"服务端 rtdbd"改动，给出可证伪判据。本文是 SDD 第一步，实现另立变更卡。

## 2 事实基础（源码逐行核对）

### 2.1 下游消费端

- 监控台 `rtdb_client.py`：同步单连接，`socket(AF_UNIX, SOCK_STREAM)` + `connect(sock_path)`（`:216-234`），默认 `/run/indurtdb/default.sock`（:703-711）；另一条 AF_UNIX 连接做 NOTIFY 监听（`NotifyListener.start` :488-530）。帧头 `REQ_HDR/RESP_HDR="<IHHI"`（:84,90），小端 POD 逐字段对齐 C `protocol.h`。
- REST→opcode：`/api/points`→`LIST(11)`、`/api/points/{id}`→`GET(10)`、`/api/meta/{id}`→`GET_META(8)`、`/api/logs`→`GET_LOG(15)`、`/api/cmd`→`1/11/7/10/2/8/12/13/14/15/24/23`、`/api/peers`→`GET_PEERS(24)`、`WS /ws`→`CAPS(21)/订阅(4/5/18)/NOTIFY(6)/SNAPSHOT_DONE(22)`（`app.py:187-626`）。`AUDIT_DUMP(3)`/`SET_META(9)` 仅常量定义、监控台不调用。
- **UDS 是本机文件 socket，非网络协议**（运维文档 `07-部署运维/03-监控与诊断.md:60-61,171-173`）；浏览器→FastAPI 是 HTTP/WS（可跨机），FastAPI→rtdbd 是同机 AF_UNIX。网关桥接的是**本地 UDS 二进制层**。
- client/ 库：强依赖 AF_UNIX（`client.c:10-15,167-198`），CMake Linux-only（顶层 :135-147）；但环形写队列纯内存可保留（`:19-58,206-214,259-290`），只需替换 fd I/O 层。
- 零改监控台的关键：`rtdb_client.py:229-231,514-516` socket 路径参数/环境变量驱动，`app.py:41-42` 读 `RTDBD_SOCK`——**改 `RTDBD_SOCK` 指向网关 sock 即可，监控台零改一行**。

### 2.2 UDS-only 缺口（网关只桥 13 URL 的后果）

- 13 镜像表（`rtdbd_dispatch.c:20-40`）：`1/2/20/10/19/4/5/18/6/22/21/17/16`；首批不镜像 9 个（13 号 :121）：`3/7/8/9/11/12/13/14/15`；`23/24` 已被 `/sync/peers/{set,get}` 占用（13 号 :125、`rtdbd.c:1752-1764`）。
- 监控台依赖的 UDS-only 7 个：`7/8/11/12/13/14/15`。只桥 13 URL 时失效：`/api/points`/`/api/partitions`/WS 初始清单（LIST）、`/api/meta`/按名解析（GET_META/FIND_BY_NAME）、`/api/logs`、点位 CRUD（12/13/14）、终端 find/meta/logs/list/create/del/rename。GET_PEERS(24) 只能借 `/sync/peers/get`，受 admin+loopback 限制。
- **因此"薄网关只桥 13 URL"不满足 h-C 目标**，必须补齐 UDS-only URL。

### 2.3 URL 层补齐路径（不新增 opcode）

- 13 号 :121/:123 明确授权：LIST/GET_META/SET_META/CRUD/GET_LOG/FIND_BY_NAME 等"v3.13 或客户端迁移需要时**按同一 dispatch 层追加 URL 即可，不需改协议骨架**"。URL（VSOA 路由）与 opcode（UDS 帧头 uint16）在不同平面，追加 URL **不碰 UDS 22 opcode 冻结**。
- 但**网关单方面加 URL 无效**：`rtdbd_dispatch.c:20-51` 是固定 13 项表，未知 URL 在 `vsoa_adapter.c:376-378` 直接不处理。必须服务端注册 listener + 补 handler。
- 现成先例：adapter 内联处理 hello/peers（`:344-373`）在 opcode_from_url 之前按专有 URL 分支并单独注册 listener（`:538-572`）；h-B health 镜像范式（26 号 §3.2）"新增 transport 无关纯函数 + adapter 内联 + 两前端字节一致"是**形态参照**。
- **但服务端重构量被低估（P1）**：h-B health 有现成 `rtdbd_self_check_core`（`stats.c:59-69`）可直接复用；而 LIST/META/FIND/LOG/CRUD 的 UDS 实现仍是 `rtdbd.c` 的 transport 耦合函数（`op_find_by_name:1196`、`op_get_meta:1237`、`op_create_point:1331`、`op_list:1473`、`op_get_log:1501`），dispatch 层目前只有 caps/get/write/subscribe_authz/notify（`rtdbd_dispatch.h:73-136`）。"补纯函数"实为**先从 rtdbd.c 抽取重构**，服务端改动显著大于 h-B——h-C 范围须按 u-A 严控，不膨胀。
- 补齐清单（**u-A 已裁决=只读类含 GET_PEERS**）：`GET_PEERS(24)`→`/sync/peers/get`（**必须**，监控台 `/api/peers` 与终端 `peers get` 依赖，受 sync_admin+loopback 约束——u-0 设备侧代理为 loopback 来源可满足）、`/point/list`(11)、`/point/find_by_name`(7)、`/point/meta`(8)、`/logs`(15) 为第一轮只读类；`/point/create|delete|rename`(12/13/14)、`/point/set_meta`(9) 为 CRUD 类第二阶段另立。CRUD/SET_META 需把 VSOA 身份接入鉴权（`rtdbd_authz.c:38-63` 的 role→URL 白名单，plc 默认放行非 `/sync/*`）。

### 2.4 VSOA client 能力与网关形态

- `vsoa_client.h`（外部 SDK，未入库）——`call` 是**异步 RPC 回调**，url+payload 完全由调用方构造 → 任意 URL 可发；`fds`/`input_fds` 并入 select/poll；`on_datagram` 收 NOTIFY/SNAPSHOT_DONE；`subscribe` 订阅确认走回调。线程硬约束：所有回调在 `input_fds` 线程，**reconnect/close 走延迟队列，不得在回调内调用**。注：SDK 具体行号不可在本仓机械复核（`vsoa/` 未入库）；仓内 `check_vsoa_sdk.py:24-39` 符号清单确认 `vsoa_client_call/on_datagram/subscribe/fds/input_fds/close/connect` 等已导出（**不含 sync_call**）——故网关用异步 `call`，不依赖 sync_call。
- payload POD 直放：13 号 :97/:129 定调 `data` 放定长 POD 零序列化、`param` 放 JSON 元数据；网关切掉 UDS 12B 头后把 body 原样放 `vsoa_payload_t.data`，响应反向同理（`vsoa_adapter.c:339-342,504-509`）。**跨语言一致性边界**：C/C++ 侧有 `static_assert` 锁尺寸/偏移（`protocol.h:160-418`），Python 侧靠 `rtdb_client.py:84-111` 手工 struct + 逐字节测试（13 号 §7.4）——非 static_assert 保障，实现须做双前端逐字节测试。
- NOTIFY 回推：服务端 `cli_datagram` 定向推（`:221-263`，禁用 publish/quick）；网关侧 `on_datagram` 按 URL 分 `/notify`(6)/`/snapshot_done`(22)，组 UDS `RESP_HDR`+NOTIFY 帧写回 NotifyListener。**关键耦合**：每个本地 NotifyListener 连接须建独立 VSOA client 会话 + hello + 订阅，否则通知不命中/串扰。
- 平台：SDK `lib/linux/{x86,x86_64,aarch64,arm,armhf}/libvsoa-client.so` 齐备，**无 Windows 预编译库** → **u-B 裁决=Linux x86_64**。无 VSOA Python/Go 绑定 → 最稳 C/C++ 独立可执行（链 `libvsoa-client.so`）；嵌 FastAPI 需跨 Python/C 回调边界，不推荐。
- 单线程事件循环 + 延迟动作队列（`poll + client_fds/input_fds`），与 13 号 :194 一致。

### 2.5 身份与三个硬约束

- VSOA 身份：hello 带 `service_id`+token，定长表映射 `(uid,partition,service_id,role)`（13 号 :195、`vsoa_adapter.c:125-190`）；按点鉴权走 `irt_policy_allows`（deny-by-default）。UDS `SO_PEERCRED` 在网关链路消失，监控台 FastAPI token（`app.py:14-15,56-66`）不会自动传递——**u-D 裁决=单只读服务身份**：瘦网关持单一只读 VSOA token/uid、不传监控台用户 token，身份在设备侧代理建立；按点鉴权粒度为只读服务身份（覆盖"看"场景，u-A 不含写操作）。
- **硬约束 0（P0，根本性，已由 u-0=设备侧代理解决）**：`rtdbd_authz_source_allowed`（`rtdbd_authz.c:19-26`）在 **hello 阶段**即对 `PLC`/`SYNC_ADMIN` 角色强制来源 127/8 loopback（经 `vsoa_adapter.c:171-176` 调用）。外部 PC 直连来源是外部 IP → **hello 直接 DENIED、会话根本建立不了**。旁路全堵：生产 `allow_unauthenticated=false`、未握手 `cred_ok=false`（订阅/写 DENIED）、`SYNC_PEER` 仅 `/sync/*` 且不得收 NOTIFY。**用户 u-0 裁决=设备侧代理**：在设备上跑本地代理（来源 127/8、hello 合规）中转，把外部来源转为设备本地来源，不改核心鉴权模型；设备侧代理是新组件、另立 SDD。
- **硬约束 1**：`/sync/peers/set` 限 `role=sync_admin` + **loopback**（13 号 :197、`vsoa_adapter.c:269-291`）。外部 PC 来源**必然 DENIED**——**u-C 裁决=放弃经网关 peers set**（属设备本地运维，走设备侧已有通道）；瘦网关不暴露 peers set 入口。peers **get** 按 u-A 保留（设备侧代理 loopback 来源可满足 sync_admin）。
- **硬约束 2**：SylixOS 侧新增 URL handler 需编译进板上 rtdbd（走 q-C 外部 toolchain，`lib/sylixos/aarch64/` 已覆盖目标架构），不重编 SDK。

## 3 方案设计

### 3.1 总体结构（u-0 裁决后：两跳 + 三层改动）

**u-0=设备侧代理**改变拓扑：不再"外部 PC 直接 hello 设备"（会被 loopback DENIED），而是设备侧先跑一个本地代理（来源 127/8、hello 合规），外部 PC 网关连该代理中转。两跳链路：

```
rtdb_client.py (UDS) → 外部 PC 瘦网关 (UDS→VSOA) → 设备侧本地代理 (VSOA 中转) → rtdbd (loopback hello 合规)
```

| 层 | 位置 | 内容 |
|---|---|---|
| 设备侧本地代理（u-0 新增组件，另立设计） | 设备上，来源 127/8 | VSOA server 对外部 PC 暴露中转端点 + VSOA client 以 loopback 连 rtdbd（hello 合规、不被 authz 拒）；把外部来源转为设备本地来源；不改核心鉴权模型。**这是新组件，须另立 SDD/变更卡，不在本文实现范围** |
| 瘦网关（外部 PC，Linux x86_64，u-B） | 独立 C/C++ 可执行 | 本机 AF_UNIX server 给零改 `rtdb_client.py`/NotifyListener；网络侧 VSOA client 连**设备侧代理**（非直连 rtdbd）；POD 直放转换；单线程 poll + 延迟动作队列 |
| 服务端（rtdbd，含 SylixOS 板） | VSOA adapter + dispatch | 按 u-A 补齐只读 URL（共享纯函数 + 内联 handler + 两前端字节一致）；CRUD/SET_META 第二阶段；`-DVSOA` 条件编译已在 G2 打通 |

### 3.2 网关最小可行流程（两跳）

1. 启动：外部 PC 瘦网关监听 `RTDBD_SOCK` 指向的 AF_UNIX 路径；用 VSOA client 连**设备侧代理**的端点（设备侧代理再以 loopback 连 rtdbd，hello 合规）；瘦网关对 rtdb_client 表现如普通 rtdbd。**u-0 已裁决设备侧代理，不再直连设备实际 IP hello**（直连会被 `rtdbd_authz.c:19-26` loopback DENIED）。订阅 `/notify`、`/snapshot_done`。
2. 控制面：接收 `rtdb_client.py` 的 v3 帧（12B 头 + POD body）→ 按 opcode 映射到 VSOA URL（13 镜像 + §3.3 按 u-A 补齐的只读 URL）→ `vsoa_client_call` 异步发（经设备侧代理中转）→ 回调收 `vsoa_payload_t.data` → 组 UDS `RESP_HDR`+status+body 写回。
3. 推送面：`on_datagram` 收 NOTIFY/SNAPSHOT_DONE datagram → 组 UDS 帧 → 写回对应 NotifyListener 的 AF_UNIX 连接（按会话身份路由，防串扰）。
4. 身份：按 u-D 裁决**单只读服务身份**——瘦网关持一个只读 VSOA token/uid（经设备侧代理），不传监控台用户 token；每个 NotifyListener 连接对应独立 VSOA client 会话（hello + 订阅）——**容量硬约束（u-E）**：监控台 WS 上限 32（`app.py:561`）、rtdbd `RTDBD_VSOA_MAX_CLI=32`（`vsoa_adapter.h:118`），须留余量给 api_client/其他 PLC；按 u-E 裁决网关并发 listener **≤16**，第 17 个起拒绝，避免会话表耗尽被静默丢弃（`vsoa_adapter.c:113`）。
5. 断线：VSOA reconnect/close 走延迟队列（SDK 回调线程约束），不在 `input_fds` 回调内重连。
6. peers set：按 u-C 裁决**放弃经网关做 peers set**（属设备本地运维，走设备侧已有通道），瘦网关不暴露 `OP_SET_PEERS(23)` 的网关入口。

### 3.3 服务端 URL 补齐（u-A 裁决：只读类含 GET_PEERS）

按 h-B 范式补 transport 无关纯函数 + adapter 内联 handler（不改 opcode/ABI）：**u-A 第一轮只读类**：`GET_PEERS(24)`→`/sync/peers/get`（注意受 sync_admin+loopback，与设备侧代理联动——代理来源 loopback 合规）、`/point/list`(11)、`/point/find_by_name`(7)、`/point/meta`(8)、`/logs`(15)；**u-A 第二阶段**：CRUD `/point/create|delete|rename`(12/13/14)、`/point/set_meta`(9) 需 VSOA 身份接入鉴权，风险高、另立。两前端字节一致（13 号 §7.4）、UDS 侧既有 opcode 语义不变。GET_PEERS 虽受 sync_admin 约束，但 u-0 设备侧代理为 loopback 来源、若以 sync_admin token 握手可满足（u-C 仅放弃 peers **set**，get 保留）。

### 3.4 边界与集成

- **不改** UDS 22 opcode 帧格式/语义/错误码、`libindurtdb.a` ABI、发布门 FAIL 8、B 段 fields、对外平台口径。
- 与 h-A（订阅重建）正交：网关订阅/NOTIFY 依赖 rtdbd 现有定向 NOTIFY；h-A 若实现重连重建会让网关断线恢复更强，但非 h-C 前置。
- 与 h-B 正交但共用范式：h-B 的 `/health`、审计 URL 与 h-C 补齐 URL 同为 adapter 内联扩展。
- SylixOS 侧：G2 已让 rtdbd 以 VSOA 单通道板上跑通（E2E 5/5），网关是外部 PC 侧新增进程，设备侧只需新增 URL handler（条件编译已在）。

## 4 验收判据（方案退出门）

1. 每层事实有源码行号证据（监控台 7 个 UDS-only opcode、13 镜像表、URL 层追加授权 :121/:123、SDK 无 Windows 库、loopback 硬约束、身份模型），可机械复核。
2. 明确"薄网关只桥 13 URL 不够"与 URL 层补齐路径（不新增 opcode/ABI）；补齐清单分只读/CRUD 两阶段。
3. 网关形态（**两跳**：设备侧本地代理 + 外部 PC Linux x86_64 瘦网关、零改监控台、POD 直放、on_datagram 回推、独立会话防串扰、单线程事件循环、listener ≤16）可证伪；设备侧代理另立 SDD。
4. **退出前置（u-0~u-E 已裁决，见 §5.1）**：u-0=设备侧代理（拓扑成立）、u-A=只读含 GET_PEERS、u-B Linux、u-C 放弃经网关 peers set、u-D 单只读服务身份、u-E listener≤16 且先交付方案；均已反映到 §3。
5. 边界守住：不改 opcode/ABI/对外口径/发布门 FAIL 8/B 段 fields，不宣告 F2/F3a/F4 就绪，实现另立变更卡 + 开工授权。
6. 独立评审通过（fresh context + 源码回核 + 边界核对）。

## 5 风险与开放问题

| 风险 | 处置 |
|---|---|
| **u-0 根本性阻断（P0，已裁决=设备侧代理）** | hello 阶段 PLC/sync_admin 强制 loopback（`rtdbd_authz.c:19-26`），外部 PC 直连会话建立不了——裁决以**设备侧本地代理**（来源 127/8、hello 合规）中转，不改核心鉴权模型；设备侧代理是新组件、另立 SDD |

| 监控台功能降级（只桥 13 URL） | 列为事实，必须补 URL（含 GET_PEERS 24）才算"保住监控台"；补齐清单按 u-A 裁决 |

| peers set loopback 阻断 | u-C 裁决：设备侧代理 / 放弃该命令；u-0 放宽后可能一并缓解但仍须独立确认 |
| 监控台身份→VSOA token 映射 | u-D 裁决；未定时按单服务身份（按点鉴权粒度退化） |
| **多 listener 会话容量冲突（P1）** | 监控台 WS 上限 32、服务端 `RTDBD_VSOA_MAX_CLI=32` 共用——网关须限制并发 listener（如 ≤16）或 u-E 裁决容量策略；串扰须测试 |

### 5.1 用户裁决落痕（2026-11-21）

用户以「h-C 裁决：首要 u-0」一次性裁决单书面确认（均按推荐值）：

| # | 事项 | 裁决 | 执行边界 |
