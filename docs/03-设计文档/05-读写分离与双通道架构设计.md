# InduRTDB 读写分离与双通道架构设计

**版本：1.1（2026-09-23 修订：D7 由 fail-safe 改为 fail-operational）**
**日期：2026-09-23**
**基线：v3.1.0（v3.2 文档治理之后）**
**状态：决策 D4–D7 已确认；D7 修订部分需复评**

> 本文回答一个根本问题：**共享内存是否必需？** 结论是"部分必需"，并据此提出读写分离 + 双通道架构。
> 相关：功能评审 [`../06-开发规划/08-功能评审与下一步规划.md`](../06-开发规划/08-功能评审与下一步规划.md)、node-server 集成设计 [`04-node-server集成设计文档.md`](./04-node-server集成设计文档.md)。

> **v1.1 修订说明**：v1.0 的 D7 定为 **fail-safe**（`rtdbd` 不可用时拒绝写）。现场评审（issue #7）明确要求"**rtdbd 挂也还是要支持控制，而且要 rtdbd 马上起来继续运行**"，即 **fail-operational**。故 D7 改为"快速自恢复 + 客户端写队列"，详见 §4.1。注意本修订**未**退回"降级直写"，管控强度不变。
> 同批确认：① 现场**无需亚毫秒级控制回路**（§1.1 论证成立）；② `StatusCode` 用纯函数映射、不进点位可行，OPC UA 等由北向自行处理。

## 1. 问题陈述

### 1.1 共享内存的必要性：分清"单点"与"批量"

| 场景 | shm 成本 | UDS/RPC 成本 | shm 是否必需 |
|---|---|---|---|
| 控制逻辑每周期读/写几个点（1ms 周期） | ~0.07μs × N | 往返 ~5–15μs | **否**。10 次访问约 100μs，占 1ms 预算 10%，足够 |
| 每次扫描 50000 点全量（HMI / 采集 / 历史） | 35.5M pt/s ≈ **1.4ms** | 序列化 + 多次系统调用 ≈ **几十 ms** | **是**，差 1–2 个数量级 |
| 多进程同时高频读 | 每读者近乎零边际成本 | 每读者一次 IPC 往返，成本 ×N | **是** |

**结论**：shm 的真实价值是**批量/全量高频读**与**多读者零边际成本**，**不是单点低延迟**。单点场景用 IPC 完全够，ns 级优势在毫秒级控制周期里属于过度工程。

> ✅ **已确认（2026-09-23，issue #7）**：现场**不存在亚毫秒级控制回路**，上表"1ms 周期"的预算假设成立。若未来出现更严苛回路，本结论需重新评估。

### 1.2 共享内存的安全弱点（现状 v3.1.0）

| 弱点 | 说明 |
|---|---|
| 无进程级鉴权 | 同 UID 的任意进程可 attach 并写**任意点位**，含控制输出点。`access` 是内存中的静态标记，可被绕过 |
| 无审计 | 无法追溯"谁在何时写了哪个点"（`timestamp_ns` 不记录 pid） |
| 容器化冲突 | 容器默认 `/dev/shm` 独立且仅 64MB；跨容器共享需 `--ipc=host` 或挂载同一 `/dev/shm`，破坏容器隔离 |
| 复杂度代价 | 为弥补崩溃一致性已付出：`owner_pid`、所有权接管、奇数 `write_seq` 恢复、fork 检测四套机制 |
| DoS 面 | 段被删除或 `/dev/shm` 被填满 |

按 IEC 62443 分区模型，shm 等于"控制区内无边界"。

## 2. 决策摘要

| 编号 | 决策点 | 结论 |
|---|---|---|
| **D4** | 部署形态 | **多进程 + 容器混合**：驱动、控制、HMI、node-server 各自独立进程，部分在容器内（容器内只能用 RPC，host 可用 shm） |
| **D5** | 写路径管控 | **B1 强管控**：写全部经服务进程。真鉴权、真审计、无写冲突；代价是写延迟 +10μs、多一个单点 |
| **D6** | 职责边界 | **OT / IT 分界**：`rtdbd` = 控制面（shm owner、写权威、鉴权审计、通知、元数据索引）；node-server = 信息面（历史、北向、业务）。依赖单向 |
| **D7**<br>**（v1.1 修订）** | 服务不可用时的行为 | **fail-operational**：`rtdbd` 不可用时**写进入客户端队列**而非拒绝，控制继续推进；同时 `rtdbd` 必须**快速自恢复**。仍然**不提供本地直写**——写最终仍经服务端鉴权审计 |

### D6 的关键判据：控制优先于监视

- 若写权威内嵌 node-server：**node-server 挂 ⇒ 控制回路写不了数据**，现场不可接受。
- 若 `rtdbd` 独立：**node-server 挂 ⇒ 控制不受影响**，只是历史与上送中断。这才是工业现场要的失效语义。

### D7 修订的判据与边界

现场要求（issue #7）：「**rtdbd 挂也还是要支持控制，而且要 rtdbd 马上起来继续运行**」。

由此确立两条边界，二者缺一不可：

1. **控制不能停**（R1）⇒ 写不能被阻断，改为入队延迟提交。
2. **不能靠绕过管控来实现不停**（安全底线）⇒ **仍然禁止本地直写**。原 v1.0 的"安全后门论证"依然有效：若允许降级直写，干掉 `rtdbd` 即可绕过鉴权。**新方案用"快速自恢复 + 写队列"同时满足 R1 与安全底线。**

## 3. 架构

### 3.1 分区视图

```
   控制区 (OT)                              管道                信息区 (IT)
┌───────────────────────────────┐                        ┌────────────────────────┐
│ 驱动进程 ──写──┐               │                        │  node-server           │
│ 控制逻辑 ─读写─┼── 共享内存 ── │  只读数据流             │  · OPC UA 北向         │
│ HMI(host) ─读──┤  /indurtdb_x  │ ─────────────────────►│  · SQLite 历史         │
│ rtdbd ──写权威─┘               │  订阅 + 批量拉取        │  · 业务 / 报警 / 云    │
└───────────────────────────────┘                        └────────────────────────┘
        ▲                                                          │
        │            ┌──────────── 容器进程 ────────────┐          │
        └────────────┤ HMI / node-server / 其它          │◄─────────┘
              RPC    │ （无 shm，只能走 RPC：读 / 写 / 订阅）│
                     └───────────────────────────────────┘
```

### 3.2 职责划分

| 能力 | `rtdbd`（OT 面） | node-server（IT 面） |
|---|---|---|
| shm 段生命周期 | ✅ **owner**（最先启、最后退；重启后 attach 已有段） | attach |
| 点位元数据 / name→id 索引 | ✅ 建立并持有（v4.0） | 只读消费 |
| 写（采集值、控制输出、HMI 下发） | ✅ **唯一入口** + 鉴权 + 审计 | 走客户端 |
| 变更通知 | ✅ 广播 | 订阅方 |
| 读 | 直连 shm | 直连 shm（host）/ RPC（容器） |
| 历史归档、北向 OPC UA / MQTT | ❌ | ✅ |
| 业务逻辑、报警 | ❌ | ✅ |
| 集群同步 | ❌（仅暴露变更事件流，预留钩子） | ✅ |

**依赖单向**：node-server → `rtdbd`（作为客户端），`rtdbd` 不依赖 node-server。

**顺带解决**：现在 shm owner 是"首个调用 `indurtdb_initialize()` 的进程"，谁先起谁当 owner，语义随意；改由 `rtdbd` 担任后生命周期有确定答案（且重启后可重新 claim）。

## 4. 关键设计

| 项 | 设计 |
|---|---|
| 传输 | UDS（`/run/indurtdb/<instance>.sock`）为主；容器靠挂载 socket 路径共享；可选 TCP loopback |
| 协议 | 极简二进制，与 shm 点位结构对齐（几乎零序列化）。**不引入 protobuf 等第三方依赖** |
| 鉴权 | `getsockopt(SO_PEERCRED)` 取 pid/uid/gid → 查配置驱动的策略表 → 按点位区间/等级授权；越权返回错误码 |
| 审计 | 写操作记 `pid + uid + point_id + ts`，**定长环形缓冲**（遵守零堆分配约束），可导出 |
| 串行化 | 服务进程内单点写入 ⇒ **多写者 busy 冲突被消除**（非缓解） |
| 通知 | 写后向各订阅连接广播；host 进程"shm 读 + 通知触发"并用 |
| **降级** | **fail-operational**（决策 D7 v1.1）：写进入客户端队列返回 `IRT_QUEUED`，恢复后重放；**不提供本地直写** |

### 4.1 服务不可用时的行为：fail-operational（决策 D7 v1.1）

现场要求拆解为两条：**R1 控制不能停**、**R2 `rtdbd` 必须马上起来继续运行**。对应三层设计。

#### 第一层：`rtdbd` 快速自恢复（主手段，对应 R2）

- 独立 supervisor（或 systemd `Restart=always`）+ 启动预热
- **重启后 attach 已有 shm 段而非重建**——段只要未被 `shm_unlink` 就仍在，**数据不丢**；重启后重新 claim ownership、重建订阅连接
- **恢复时间目标（RTO）需量化**，建议 ≤ 100ms，并作为 v3.3 验收项（见 §8 待决）

#### 第二层：客户端写队列（兜底，对应 R1）

- 客户端库维护**定长环形队列**（遵守零堆分配约定，容量可配）
- 写调用**不阻塞**：入队后立即返回 `IRT_QUEUED`
- `rtdbd` 恢复后**按序重放**，服务端仍逐条执行鉴权与审计
- **关键点：这不绕过管控**——写最终仍经 `rtdbd`，与"降级直写"有本质区别
- 队列满策略：同点位合并（只保留最新值），超限则丢弃并告警（策略需评审确定）

#### 第三层：数据新鲜度标记（保证下游知情）

- 排队期间点位 `timestamp_ns` 不更新 ⇒ `check_timeouts()` 自然将其标记为 `TIMEOUT`
- 使用 **`COMM_FAILURE`** 质量码（v3.4 新增）显式标记"与控制面失联"
- 控制输出点在排队期间保持"上一次已提交值"，下游按安全策略处理，而不是让陈旧值静默生效

### 4.2 与 v1.0 fail-safe 方案的对比

| | v1.0 fail-safe（已废弃） | v1.1 fail-operational（现行） |
|---|---|---|
| `rtdbd` 挂时写 | 拒绝，返回错误码 | 入队，返回 `IRT_QUEUED` |
| 控制回路 | 中断 | 继续推进 |
| 是否绕过鉴权 | 否 | **否**（恢复后仍经服务端鉴权审计） |
| 复杂度 | 低 | 中：队列 + 重放 + 时序 |
| 单点故障影响 | 硬中断 | 短暂延迟 + 数据新鲜度下降 |

### 4.3 新增风险（必须诚实列出）

| 风险 | 说明 | 缓解 |
|---|---|---|
| 队列积压 | 长时间不可用导致队列填满 | 定长 + 同点位合并去重；超限告警 |
| 重放时序 | 恢复后提交的是"过去的值" | **用 v3.4 的 `source_timestamp_ns` 承载原始采集时刻**，避免时间戳失真 |
| 队列丢失 | 客户端进程自身崩溃 | 可接受——控制输出本就持续刷新，下周期会重写 |
| RTO 不达标 | 重启慢于控制周期 | RTO 量化为验收项；必要时评估热备 |

> 附带的正向收益：`source_timestamp_ns` 在此有了明确用途，进一步支撑 v3.4 该字段的必要性。

## 5. 库侧演进方式

**不要把 RPC 客户端塞进核心库。**

| 组件 | 内容 |
|---|---|
| 核心库 `libindurtdb.a` | **保持不变**：纯本地 shm + seqlock，26 个 API 不变、ABI 保持 v1、确定性不变 |
| `indurtdb-client`（新子项目） | RPC 客户端 + **写队列**；API 与核心库**同构但命名空间独立**（如 `irtcli_write_double`） |
| `rtdbd`（新子项目） | 写权威 + 鉴权 + 审计 + 通知 + 快速自恢复；内部链接核心库 |

**理由**：
1. 同一 API 在两种模式下延迟差约 100 倍（0.15μs vs ~10μs），合在一个 API 里必然被误用。
2. 核心库零膨胀，符合既有约定"以独立子项目交付，不使核心库膨胀"。
3. 写队列属于客户端行为，放在客户端库不影响核心库的确定性与零堆分配约束。

## 6. 影响、代价与风险

### 6.1 代价（诚实清单）

| 代价 | 量级 | 可接受性 |
|---|---|---|
| 写延迟上升 | 0.15μs → ~5–15μs | 1ms 周期写几次 ≈ 几十 μs，**可接受** |
| 新增守护进程 | 多一个运维对象，且是单点 | 快速自恢复 + 写队列 + 新鲜度标记三层兜底 |
| 客户端/服务端两套 API | 学习成本增加 | 由命名空间隔离 + 文档承担 |
| 写队列的内存与复杂度 | 客户端常驻定长缓冲 | 需容量规划与队列满策略 |
| 容器侧批量读仍慢 | 服务端批量读后一次回传 | 仍优于逐点，可接受 |

### 6.2 与既有差距项的关系

| 原差距 | 原方案 | 新架构下 |
|---|---|---|
| G8 跨进程变更通知缺失 | 单独做通知机制 | 并入 `rtdbd` 通知中枢，写后即广播 |
| G9 多写者 busy 不重试 | 自旋重试语义确定化 | **问题被消除**（写收敛到单点） |
| G10 无按名查找 | v4.0 shm 内索引 | 归属明确：`rtdbd` 注册期建索引，其它进程只读（issue #4 的归宿） |

### 6.3 风险登记

| 风险 | 说明 | 缓解 |
|---|---|---|
| `rtdbd` 单点故障 | 不可用期间写被延迟 | 快速自恢复（RTO 量化）+ 客户端写队列 + 新鲜度标记；**不采用直写降级** |
| 写队列积压 / 重放时序 | 见 §4.3 | 定长 + 合并去重 + `source_timestamp_ns` 承载原始时刻 |
| 协议版本演进 | 客户端/服务端版本不匹配 | 协议头带版本号，握手校验，明确兼容矩阵 |
| ~~SylixOS 支持~~ | ✅ **已确认（2026-09-23）：SylixOS 上 UDS 与 eventfd 均可用** | 按 POSIX 语义实现；仍需在目标板**实测 UDS 往返延迟**，确认落在 5–15μs 预算内 |
| 容器 socket 挂载 | 依赖部署侧配置 | 提供部署文档与示例（Docker/Podman 挂载方式） |
| 命名未定 | `rtdbd` / 客户端库名待定 | 评审时确定，需符合 `irt_` / `indurtdb_` 命名规范 |

## 7. 版本路线调整建议

| 版本 | 性质 | 内容 |
|---|---|---|
| **v3.3** | 架构级（**需专项评审**） | `rtdbd` 服务进程 + `indurtdb-client`（含**写队列**）+ 协议与鉴权 + 通知 + **快速自恢复机制** + 端到端测试 |
| **v3.4** | 语义与诊断 | **SourceTimestamp**（写队列重放的时序依据）、quality 扩展（含 `COMM_FAILURE`）、类型扩展、CRC 与版本协商、诊断与 Python 工具集、SylixOS 验证 |
| **v4.0** | ABI 变更 | shm 内 name→id 索引（由 `rtdbd` 建立）、去单例化、容量在线扩容、布局 v2 + 迁移工具 |

> **v3.3 与 v3.4 的耦合点**：fail-operational 依赖 `COMM_FAILURE` 质量码与 `source_timestamp_ns`，二者属 v3.4。若 v3.3 先落地，需先定义这两个字段的最小版本（建议 v3.3 一并引入 `COMM_FAILURE` 与 `source_timestamp_ns`，避免分两版）。
