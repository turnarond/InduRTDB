# InduRTDB Linux 产品化完善计划

**版本：1.0** ｜ **日期：2026-10-08** ｜ **基线：v3.7.0（`1247758`）**
**状态**：方向已定（Linux 优先），分档待评审

> 本文回答一个问题：**在暂缓 SylixOS 移植的前提下，Linux 版还差什么才能成为一个「好用的、可以直接交付给对接方」的产品。**
>
> 与 [`08-功能评审与下一步规划.md`](./08-功能评审与下一步规划.md) 的分工：08 是**评审结论与差距盘点**，本文是**产品化落地计划**。差距状态仍以 08 的 §9 为准。

---

## 一、方向决策

**2026-10-08 决策：Linux 优先，G4（SylixOS/ARM）暂缓。**

先把 Linux 版在**功能开发、用户使用、部署运维**三条线上完善成可交付产品，SylixOS 移植推迟到其后启动。

### 该决策的已知代价（明确留档，不回避）

| 事实 | 影响 |
|---|---|
| 同集团 `KO_MIDDLEWARE` / `base_ecs_a7` / `base_cm680` 均在跑 SylixOS | SylixOS 很可能不是「以后再说」的可选项，而是既定目标平台 |
| InduRTDB 是 node-server 的**底层数据层** | 若 node-server 要上 SylixOS，InduRTDB 跑不通会整体卡住 |
| G4 的降级理由「工具链未到位」早已不成立 | `aarch64-sylixos-elf-gcc`（GCC 10.2.1）已在本机 PATH，BSP 与真机链路均具备；真正缺的是 InduRTDB 侧的 toolchain 文件与 BSP 依赖引入方式 |

> **G4 按技术债管理**：不占用 v3.8，v3.8 维持「点位分区/命名空间」。恢复条件 = Linux 产品化完成 + BSP 引入方式确定。素材与已查明的坑见 08 的 §11 第 4 项，届时不必重新调研。

## 二、三线缺口盘点

基线事实（实测，非文档转述）：Release 构建零警告、37/37 ctest 全绿、266 个 gtest 用例、版本四处一致。**核心库本身的质量不是问题，缺口全部在「产品化」这一层。**

### 2.1 部署运维线 —— 缺口最集中，投入产出比最高

| 缺什么 | 实测证据 | 影响 |
|---|---|---|
| **无 systemd unit 文件** | 全仓库 `find *.service` 为空 | rtdbd 有 `--supervise` / `--pidfile` 自监管，但交付方拿到手需自行编写 service |
| **无 supervisor 配置** | CHANGELOG 明写「supervisor 对致命码（2/4）停止 respawn」，仓库内无对应 conf | 上述机制实际由交付方配置，行为不可控 |
| **部署运维文档** | ✅ **已补 `docs/07-部署运维/`（D2）** | — |
| **配置样例** | ✅ **已补 `config/rtdbd/`（D3）**，9 点位实测通过 | — |
| **`.gitignore` 屏蔽配置后缀** | 第 60–62 行忽略 `*.yaml`/`*.yml`/`*.json`；已加 `!config/rtdbd/*.yaml` 放行 | 自建样例仍需 `git add -f` |
| **无打包目标** | 有 install 规则（TARGETS / EXPORT / pkg-config），**无 CPack** | 交付需手工打包，版本易错配 |
| **`rtdbd`/`client`/`irt_diag` 无 install 规则** | `cmake --install` **只安装库本体** | 交付需从构建目录手动拷贝 |

### 2.2 功能线 —— 已相当完整，剩硬骨头

**已完成**：CRUD + 全类型读写 + 元数据 + `find_by_name` + 批量 range + 订阅 + RBE + 健康检查 + 审计 + 背压 + 优雅退出 + delta 持久化 + Vue 监控台。

| 剩余项 | 性质 | 归属 |
|---|---|---|
| G15 容量在线扩容 | 需改段布局，架构级 | v4.0 |
| v1 API 完全退役 | 62 个函数已标 deprecated 但**本体仍在** | v4.0 删 |
| G18 语言绑定 | 仅 Python 协议客户端，无 FFI 包 | 后续 |

### 2.3 用户使用线 —— 交付说明自己点名的约束

`docs/交付说明-v3.7.0.md` §四 列了 6 条「交付前须向对接方声明」的约束。其中三条**直接影响上手体验**：

| 约束 | 对用户的实际影响 |
|---|---|
| `peek()` 单拷贝（线程本地，下次覆盖） | 用户第一次踩坑概率极高。SDK 手册需醒目标注 + 给出正确用法示范 |
| 写冲突返回 `-2` 不重试 | 调用方**必须**自己写重试循环，否则高并发下丢写。无范式即等于踩坑 |
| 超时检测 best-effort（「真实采集周期下不触发」，issue #19） | 功能形同虚设，需明确告知适用边界 |

## 三、分档计划

### 第 1 档 ——「能交付」（预计 1–2 天）

目标：**库和 rtdbd 能直接交给对接方部署运行，不需要对接方补任何东西。**

| # | 任务 | 产出 | 验收 |
|---|---|---|---|
| D1 | systemd unit + supervisor 配置 | `deploy/` 目录 | `systemd-analyze verify` 通过；supervisor conf 可加载 |
| D2 | 部署运维文档 | ✅ `docs/07-部署运维/` 5 篇 | 已交付 |
| D3 | 配置样例 | ✅ `config/rtdbd/{policy.conf,points.yaml}` | 已交付，9 点位实测通过 |
| D4 | CPack 打包 + **为 `rtdbd`/`client`/`irt_diag` 补 install 规则** | `tar.gz` + 可选 deb | 打包物含库、头文件、pkg-config、rtdbd、工具、配置样例 |
| D5 | v3.5.0 / v3.6.0 补 tag | 历史 tag | 与 CHANGELOG 条目对齐（决策见 08 §11 第 2 项） |
| **D6** | ~~配置解析器支持 int64 / uint32~~ | ✅ **已修复**：`irt_config_parse_type()` 补两分支 + `indurtdb.c` 类型过滤上限由 `STRING` 改为 `FLOAT` + 5 个回归测试 | D3 实测发现：`type: int64` 曾被静默丢弃而 rtdbd 退出码仍为 0。已实测：11 个点位全部生效，int64/uint32 正确落段 |

### 第 2 档 ——「好用」（预计 1 周）

目标：**对接方不踩坑、不丢写。**

| # | 任务 | 产出 |
|---|---|---|
| U1 | 写冲突正确范式 | API v2 提供可选重试封装；或文档给出经过验证的重试循环范式 + 测试 |
| U2 | `peek()` 语义纠正 | SDK 手册显著标注单拷贝语义与失效条件；`examples/` 增加正确用法示范 |
