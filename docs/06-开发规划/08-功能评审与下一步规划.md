# InduRTDB 功能评审与下一步规划

**版本：1.1（v3.6 对齐）**
**日期：2026-09-23（初版） / 2026-10-06（v3.6 交付对齐 + v3.7 路线图刷新）**
**基线：v3.1.0（差距盘点基线；实际交付基线见 §9）**
**状态：决策已确认（D1=A / D2=C / D3=B）；v3.2–v3.6 已交付，v3.7 范围已与用户确认（见 §10）**

> 本文回答三个问题：① 当前到底有哪些功能（以代码为准）；② 对照优秀开源工业实时点位数据库，缺什么、差在哪；③ 下一步怎么规划、每个版本的边界在哪。
> 本文是**评审结论**，不是实现计划。每个落地任务仍需另建分支 + 实现计划（遵循 TDD 与评审约定）。

## 1. 评审方法与范围

- **代码基线**：`v3.1.0`，以 `src/`、`include/indurtdb/indurtdb.h`、`tests/` 为事实来源。
- **文档基线**：`docs/01-白皮书/` 三份白皮书、`docs/06-开发规划/05-技术演进规划.md`、`README.md`、`CHANGELOG.md`。
- **对标对象**：Eclipse iceoryx/iceoryx2（零拷贝共享内存数据面）、Apache IoTDB / TDengine / Machbase Neo（工业时序库）、openHistorian / PI System（实时历史库）、Redis（内存数据中枢）、OPC UA 信息模型 IEC 62541-8（工业语义）。
- **原则**：只对标**同层能力**（共享内存实时层），不把时序库的历史/压缩能力算作 InduRTDB 的必补项——它已在演进规划中明确划归 node-server。

## 2. 当前功能盘点（以代码为准）

v3.1.0 的本质是：**单进程单例 + 全局单 Seqlock 的共享内存点位表**。

| 分类 | 能力 | 实现要点 |
|---|---|---|
| 存储 | 共享内存布局 | `/indurtdb_<instance_id>`；`Header 64B + N×128B 点位 + M×16B 订阅心跳`；`IRT_STATIC_ASSERT` 锁定，与 v2.x 逐字节兼容 |
| | 数据类型 | bool / int32 / double / string[31+1] |
| | 工业语义 | quality（GOOD/BAD/TIMEOUT/SUBSTITUTED）+ unit + access + name[64] + timestamp_ns |
| | 元数据加载 | `load_config`：key=value（初始化）+ 自研 YAML 点位元数据解析 |
| API | 26 个 C 函数 | 单点 4 类型读写、`read_point`、`peek`（**单拷贝**到 `_Thread_local`）、`read_range`、`write_range_×3`、订阅、统计 |
| 订阅 | 进程内回调 | 256 定长槽位；共享内存侧仅存心跳表（pid + last_heartbeat_ns）+ zombie 清理 |
| 可靠性 | 崩溃自愈 | owner 崩溃接管（`kill(pid,0)` 存活检查 + `irt_shm_os_claim_ownership`）、奇数 write_seq 恢复、fork 安全（`owner_pid != getpid()` 清除 owner 标记） |
| 运维 | 超时检测 | `check_timeouts(ns)` 全量扫描，超时点标 QUALITY_TIMEOUT（写冲突时跳过，best-effort） |
| 平台 | 双 OSAL | POSIX（已验证）+ SylixOS（代码存在，未验证） |
| 集成 | 三消费路径 | find_package / pkg-config / FetchContent；子项目隔离；starter 模板；`verify_consume.sh` |
| 质量 | 测试与 CI | gtest **26 套件 / 126 用例**（ctest 注册 **16 个**：15 单元 + 1 多进程集成），全绿；soak / 故障注入 / bench 脚本；GitHub Actions Debug+Release 双配置；`-Wall -Wextra -Werror` 零警告 |

**已实测（x86, Release -O2）**：write_int32 P99 0.386μs、read_int32 P99 0.068μs、peek P99 0.062μs，均优于 P99 ≤10μs 设计目标。ARM 未实测。

## 3. 白皮书评审：定位漂移（一等缺陷）

### 3.1 三份白皮书 + 演进规划互相冲突

| 文档 | 定位 | 对外接口 | 集群 |
|---|---|---|---|
| 白皮书 1.0（对应 v2.1.0） | 取代 Modbus 的安全数据底座 | OPC UA Bridge（v3.2 路线图） | 未提 |
| 白皮书 2.0（v3.1.0） | PLC 实时数据中枢，对标 Redis | VSOA RPC + `/cluster/sync` | 📋 未实现，但在 §1/§9 当作卖点陈述 |

| **技术演进规划（最新，2026-08-10）** | **node-server 的底层共享内存实时数据层** | **复用 node-server 的 OPC UA / SQLite，不重复造轮子** | **明确不做** |

## 4. 竞品对标

### 4.1 对标矩阵

| 对标对象 | 定位 | 关键能力 | InduRTDB 差距 |
|---|---|---|---|
| **Eclipse iceoryx / iceoryx2** | 真零拷贝共享内存数据面（汽车/任务关键） | 跨进程 pub/sub、RouDi 守护进程统一管生命周期与资源、服务发现、请求-响应 | **缺跨进程通知、缺服务发现、缺生命周期守护** |
| **Apache IoTDB / TDengine / Machbase Neo** | 工业时序库，端边云协同 | 高压缩列存、SQL、订阅、OPC UA/MQTT 原生接入 | 历史/压缩已划归 node-server（✅ 决策正确）；但**缺变化上报 / deadband** 这一上送侧能力 |
| **openHistorian / PI System** | 实时历史库 | 内存快照 + ACID 归档 + 点位元数据（量程/死区/压缩）+ **按名查找** + 历史查询 | **缺按名查找、缺量程、缺死区**；归档不在边界内 |
| **Redis** | 内存数据中枢 | KV、Pub/Sub、TTL、持久化、ACL | 对等项基本齐；**缺字符串键、缺跨进程 Pub/Sub** |
| **OPC UA 信息模型（IEC 62541-8）** | 工业语义事实标准 | `DataValue = Value + StatusCode + SourceTimestamp + ServerTimestamp`；AnalogItem 含 EURange / EngineeringUnits；Deadband 与 DataChangeFilter；StatusCode limit bits（Low/High/Constant） | quality 仅 4 值、**只有 ServerTimestamp**、无量程、无死区 |

### 4.2 对标结论

InduRTDB 的**长板**（ns~μs 级共享内存访问、零依赖静态库、崩溃自愈、布局字节兼容）在当前赛道上确实是差异化优势，iceoryx 面向大 payload 数据面、TSDB 面向历史分析、Redis 面向网络 KV，**没有直接竞品同时覆盖"嵌入式 .a + 工业语义 + 共享内存"**。

InduRTDB 的**短板**集中在两处，且都不是性能问题：
1. **跨进程协同能力**：只有数据共享，没有变更通知与发现——进程间只能退化为轮询，这恰恰抵消了共享内存带来的延迟优势。
2. **工业语义深度**：quality 只有 4 个枚举、时间戳只有服务端时间、没有量程与死区，接入 OPC UA / SCADA 时语义会被降级或丢失。

| 编号 | 决策点 | 结论 | 影响 |
|---|---|---|---|
| **D1** | 产品定位 | **A. node-server 底层数据层**。对外只讲"共享内存实时数据层"；北向 OPC UA、持久化、集群一律归 node-server / Bridge，不重复造轮子。白皮书 1.0 / 2.0 移入归档，重制统一版白皮书 4.0 | 定位口径唯一；白皮书 2.0 中的 VSOA RPC、`/cluster/sync`、Redis 分片对标等表述全部下线 |

| 去单例化 | 句柄化 API v2，同进程多实例；v1 API 保留为 deprecated 薄封装 | 多实例并发用例；v1 回归不破 |
| 元数据区 | EURange / deadband / flags（每点 32B，冷数据） | 与热数据面分离，不进读写热路径 |
| 语义补齐 | quality 分层位布局 + `indurtdb_quality_to_status_code()` 纯函数 | 双向映射用例 |
| 类型扩展 | int64 / uint32 / float（**复用 value union 内已有字节**）；blob 需评审是否放得下 | `sizeof(indurtdb_point_t)==128` 断言仍通过 |
| 语义扩展 | **quality 分层位布局完整落地**（4bit 基础码 + 2bit 量程位，**不占空间**）；OPC UA StatusCode 用纯函数映射、**不进点位**；deadband / EURange 不进点位 | **仅占 padding 19B 中 8B**，余 11B；`sizeof==128` 与既有偏移不变，ABI 仍为 v1。⚠️ **`SourceTimestamp` 与 `COMM_FAILURE` 已提前到 v3.3 并于 T5 落地**（新增 `indurtdb_write_*_ts()` 与 `indurtdb_set_quality()`，ABI 仍为 v1）。方案见 [`03-设计文档/06-v3.4点位语义字段分配方案.md`](../03-设计文档/06-v3.4点位语义字段分配方案.md) |
| 可靠性 | shm 头部 CRC + 版本协商（**v1 段拒绝挂载**）；**issue #19 修复**：`check_timeouts` 在热写者自旋下被饿死（扫描让步退避 + `scan_skipped` 可观测） | attach 行为有测试；热写者场景下扫描不再整轮空转 |
| 诊断与工具 | fd/shm 泄漏检测、per-point 统计、Python 巡检/冒烟工具集 | 工具自带工程结构；可接入 CI |
| 质量 | 行覆盖 ≥80%；N 小时 soak；SylixOS 交叉编译与目标板验证（依赖工具链） | 零警告；测试全绿 |
| 术语清理（遗留） | 测试用例名 `ZeroCopyPeek`（`tests/integration/test_c_multi_process.cpp`）与历史术语仍称"零拷贝"，v3.2 仅改注释未改名（受"只改文档"边界约束） | v3.4 随代码变更一并重命名并回归 |

> **空间账（2026-09-23 细化）**：点位 `padding[19]` @109；Header 另有 **20B 空闲**（offset 44–63，供 v3.4 CRC / flags 用，此前未被识别）。
> v3.4 点位内**只新增 SourceTimestamp(8B)**，余 11B 保留；**quality 扩展靠重新定义现有 `uint8_t` 的位布局，不占空间**；**StatusCode / deadband / EURange 都不进点位**（StatusCode 是协议编码归 IT 面，用纯函数映射；deadband 是上送策略归 node-server；EURange 是元数据归 v4.0 的 `rtdbd` 元数据区）。详见 [`03-设计文档/06-v3.4点位语义字段分配方案.md`](../03-设计文档/06-v3.4点位语义字段分配方案.md)。

### v3.7 ——「语义深化 + 运维硬化」（ABI 不变，段版本仍 2）

**主题 A：核心语义深化（死区/RBE + EURange 生效）**
| 任务 | 内容 | 约束/验收 |
|---|---|---|
| T1 死区/RBE 过滤 | RBE 状态（每点 `last_reported`）放 **rtdbd 进程内存**（不进共享内存，零 ABI）；写值超死区（绝对/百分比，模式存 `meta.flags`）或跨越 EURange 边界才发 `NOTIFY`；直接 shm 写者不享受 RBE | `NOTIFY` 死区驱动；端到端用例：小幅抖动不通知、越界触发且量程位正确、首值必通知 |
| T2 EURange→量程位 | `pm_write_impl` 内置 **flag 门控快路径**：仅 flags 开启时读该点 32B 冷元数据比较，越界置 quality bit4–5；覆盖 rtdbd 与直接写者 | 热路径零回归（关闭时零开销）；直读者量程位一致 |
| T3 纯函数 + 单测 | `indurtdb_deadband_exceeded()` / `indurtdb_apply_eurange_limits()` 无状态可单测 | 绝对/百分比/跨边界/关闭 + 双向类型全覆盖 |
| T4 rtdbd 改造 | `NOTIFY` 死区驱动 + 集成测试 | 见 T1 |

**主题 B：运维硬化**
| 任务 | 内容 | 约束/验收 |
|---|---|---|
| B1 SylixOS/ARM 实测（G4） | 交叉编译零警告；目标板基础/多进程/soak/fault-injection；修 OSAL 差异 | 依赖工具链到位，否则降级 P2 不阻塞 |
| B2 运行时配置持久化 | rtdbd 在 create/delete/rename 时 append `<instance>.rtdbd.delta`；启动 `load_config(base)` → 回放 delta 重建运行时点位；base 不可变可审计 | ABI 不变；正确处理删后重建/改名顺序 |
| B3 v1 API 退役 | v1 全局函数加 `INDURTDB_DEPRECATED`；迁移 examples/demo/测试到 v2；薄封装保留 deprecated，删除推迟 v4.0 | `-Werror` 仍通过 |

**v3.7 不变式**：ABI 不变（段版本 2）；RBE 状态不进共享内存；热路径零回归（`run_bench.sh` P99 回填 README）。
