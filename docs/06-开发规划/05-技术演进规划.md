# InduRTDB 技术演进规划

**版本：1.0**
**日期：2026-08-09**
**状态：已评审**
**起点：v3.1.0（集成产品化已合并 main）**

> 本规划回答两个问题：① InduRTDB 距"可对外发布的工业级产品"还差什么；② 它如何演进以支撑"下对设备、上对 SCADA/BAS/ISCS"的完整数据链路。规划以任务级颗粒度给出，含验收标准、优先级与依赖。

---

## 1. 定位与北极星

### 1.1 定位

**InduRTDB 是工业级"共享内存实时数据层"**——一个纯 C、跨进程、确定性的内存点位存储库。它是数据链路**中间的实时热数据层**，不是整条链路。

明确的边界（做什么 / 不做什么）：

| 做 | 不做 |
|---|---|
| 跨进程共享内存实时点位存储（低延迟、确定性） | 南向设备接入（Modbus/OPC UA/S7 驱动） |
| 工业语义（quality / timestamp / unit / access） | 北向 SCADA 对接（OPC UA Server / MQTT 上送） |
| 多进程读写、订阅、崩溃自愈 | 持久化 / 历史库 |
| 作为库被集成（find_package/pkg-config/FetchContent） | 集群 / 跨节点同步 |

### 1.2 与 node-server 的关系（本规划的关键决策）

node-server（`src/service/node-server`）是框架内既有的 **"BAS Edge Data Hub — RTDB + OPC UA + IPC"**，其 `DataCenter` 已具备：
- **北向**：OPC UA Server（open62541，`opc.tcp://localhost:4840`），对外暴露数据给 SCADA/HMI；
- **持久化**：SQLite（`PointRepositoryImpl`）；
- **内置 RTDB**：进程内 C++ sharded-map（string 键、shared_mutex），与 InduRTDB 能力重叠但设计不同。

**决策：InduRTDB 作为 node-server 的底层数据层。** 因此：
- InduRTDB 提供**跨进程共享内存实时层**（node-server 内置 RTDB 是进程内的，二者互补，InduRTDB 承担多进程共享场景）；
- **北向 OPC UA、持久化不重复造轮子**——复用 node-server 已有能力，InduRTDB 通过接入 node-server 间接覆盖"上对 SCADA/BAS/ISCS"与历史落盘；
- 南向驱动（Modbus/OPC UA/S7）由框架驱动层负责，写入 InduRTDB。

### 1.3 北极星

成为**可对外发布、经实测验证**的工业级实时数据层：性能有实测背书、可靠性有长时验证、集成有规范路径、边界清晰不误导选型。

## 2. 现状与差距基线

### 2.1 v3.1.0 已具备

| 维度 | 现状 |
|---|---|
| 核心 | 纯 C11，shm + seqlock，26 函数单头文件，~996 行 |
| 可靠性 | owner 崩溃自愈、seqlock 奇数恢复、owner_pid |
| 集成 | find_package / pkg-config / FetchContent 三路径 + 子项目隔离 + starter 模板 + verify_consume.sh |
| 测试 | 15 个测试（14 单元 + 1 多进程集成），全绿 |
| 文档 | 白皮书 ×3、SRS、设计文档、SDK 手册、CHANGELOG |
| 平台 | Linux 已实现；SylixOS OSAL 代码存在但未验证 |

### 2.2 差距清单（规划起点）

| # | 差距 | 影响 | 归属 |
|---|---|---|---|
| G1 | 性能只有设计目标（P99≤10μs），无实测 | "超低延迟"卖点无背书 | 短期 |
| G2 | 无长时稳定性/故障注入证据 | 7×24 宣称无支撑 | 短期 |
| G3 | 无 CI | 无法守回归 | 短期 |
| G4 | SylixOS 未验证 | 国产 RTOS 目标市场空白 | 短期 |
| G5 | 测试规模偏小（15），缺边界/异常/并发 | 工业级可信度不足 | 短期 |
| G6 | 定位边界未讲清，易被误判为"设备→SCADA 完整方案" | 选型误导 | 短期 |
| G7 | 与 node-server 未打通（北向/持久化无法触达） | 完整链路缺失 | 中期 |

### 2.3 与 node-server 能力对照

| 能力 | InduRTDB | node-server | 处置 |
|---|---|---|---|
| 实时点位存储 | 跨进程 shm、数字 ID、seqlock、零拷贝 | 进程内 sharded map、string 键 | 互补：InduRTDB 承担多进程共享 |
| 北向 OPC UA | 无 | ✅ 已有 Server | 复用 node-server |
| 持久化/历史 | 无 | ✅ SQLite | 复用 node-server |
| 工业语义 | quality/unit/access/ts | ts/driver/device | InduRTDB 语义更全，映射传递 |
| IPC | 共享内存 | SSN IPC | 互补 |

## 3. 短期目标：补齐发布缺口

目标：把 InduRTDB 核心打磨到"可对外发布"。优先级 P0=必做，P1=应做，P2=可选。

### 3.1 实测性能基准　【P0】
- **任务**：编写基准测试程序，在目标 ARM 板（Cortex-A53/A72）实测单点读/写、peek、批量读写的 P99 延迟与吞吐；x86 作为参考对照。
- **验收标准**：产出基准程序 + 实测报告；P99 达标（<10μs）或给出实测值与优化方向；实测数据写入白皮书与 README（替换"设计目标"表述）。
- **依赖**：目标硬件到位。

### 3.2 长时稳定性与故障注入　【P0】
- **任务**：soak 测试（持续读写 N 小时，监控内存/数据一致性）；故障注入（kill owner 进程验证崩溃自愈、异常 detach、写锁内崩溃恢复）。
- **验收标准**：N 小时 soak 通过（无泄漏、无数据漂移、错误率 0）；崩溃自愈场景自动断言通过；测试脚本入库（可纳入 CI）。
- **依赖**：无（可与 3.1 并行）。

### 3.3 CI 流水线　【P0】
- **任务**：接入 CI（GitHub Actions 或等效），每次 push/PR 自动执行 build + ctest + `scripts/verify_consume.sh`；Debug/Release 双配置。
- **验收标准**：CI 配置入库并跑通；能拦截回归（以一次人为破坏验证）。
- **依赖**：无。

### 3.4 SylixOS 平台验证　【P1（若目标市场含 SylixOS 则 P0）】
- **任务**：用 SylixOS 工具链交叉编译；在 SylixOS 目标跑通基础读写与多进程测试；修复暴露的 OSAL 问题。
- **验收标准**：交叉编译零警告；基础/多进程测试在 SylixOS 通过；问题与结论记录入文档。
- **依赖**：SylixOS 工具链与目标环境。

### 3.5 测试覆盖强化　【P1】
- **任务**：补充边界条件（id 越界、string 31 字符上限、容量上限）、错误路径、并发/多进程压力测试；统计并提升覆盖率。
- **验收标准**：新增测试覆盖上述路径并全绿；覆盖率达到既定目标（建议行覆盖 ≥80%）。
- **依赖**：无。

### 3.6 定位与边界文档　【P1】
- **任务**：在 README 与白皮书顶部明确"InduRTDB 是数据中枢层，不含驱动/北向/持久化"，并说明与 node-server 的分工（本规划 1.2 节结论）。
- **验收标准**：README/白皮书更新，定位与边界表述清晰、与本规划一致。
- **依赖**：本规划评审通过。

**短期完成判据**：G1–G6 全部关闭，InduRTDB 可对外发布（有实测性能、有长时验证、有 CI、边界清晰）。

## 4. 中期目标：接入 node-server（成为其底层数据层）

目标：让 InduRTDB 通过 node-server 间接覆盖"上对 SCADA/BAS/ISCS"与持久化，打通完整数据链路。**原则：复用 node-server 已有 OPC UA 与 SQLite，不重复造轮子。**

### 4.1 InduRTDB 存储适配器　【P0】
- **任务**：在 node-server `StorageFactory` 新增 InduRTDB 存储后端（或实现适配器包装 InduRTDB 为共享内存实时层），`DataCenter` 可选 `StorageType::InduRTDB`；与现有 OPCUA/RTDB 后端并存。
- **验收标准**：node-server 以 InduRTDB 后端读写数据成功；多进程共享生效；现有 OPCUA/RTDB 后端不回归。
- **依赖**：短期发布缺口关闭（InduRTDB 稳定）。

### 4.2 数据模型映射　【P0】
- **任务**：建立 InduRTDB 数字 ID 点位 ↔ node-server string 键 `TagRecord` 的映射（配置驱动的 name↔id 表）；传递 quality/timestamp/unit/access 语义。
- **验收标准**：双向映射正确（配置驱动、可加载）；语义无丢失；映射层有单元测试。
- **依赖**：4.1。

### 4.3 北向复用：OPC UA 暴露　【P1】
- **任务**：node-server OPC UA Server 暴露 InduRTDB 点位数据，供外部 SCADA/BAS/ISCS 读取/订阅。
- **验收标准**：外部 OPC UA 客户端能读取/订阅 InduRTDB 点位且数据一致；订阅变更及时。
- **依赖**：4.1、4.2。

### 4.4 持久化复用：SQLite 落盘　【P1】
- **任务**：node-server SQLite 承担 InduRTDB 实时数据的归档与历史查询；重启可从持久化恢复。
- **验收标准**：实时数据按配置归档；历史可查询；掉电/重启后数据可恢复。
- **依赖**：4.1、4.2。

### 4.5 端到端集成测试　【P0】
- **任务**：验证完整链路 驱动(模拟)→InduRTDB→node-server→OPC UA（北向）与 →SQLite（持久化）。
- **验收标准**：端到端集成测试通过；链路延迟与数据正确性达标；纳入 CI。
- **依赖**：4.1–4.4。

**中期完成判据**：G7 关闭，InduRTDB 经 node-server 覆盖完整"设备→实时层→SCADA/持久化"链路。

## 5. 长期展望（本规划范围外）

以下能力不在本期规划，仅作方向记录，另立规划：
- **集群 / 高可用**：多节点同步、主备（rtdb_server `/cluster/sync` 路线）。
- **南向驱动生态**：Modbus/OPC UA/S7 驱动与 InduRTDB 的标准化写入接口（当前由框架驱动层承担）。
- **安全与认证**：访问控制强化、审计、乃至 IEC 61508/SIL 背景（若进入安全相关场景）。
- **OPC UA Bridge 独立组件 / CPack 打包分发**。
