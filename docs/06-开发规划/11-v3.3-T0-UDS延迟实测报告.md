# v3.3 T0 · UDS 往返延迟实测报告

**日期：2026-09-24**
**任务：** `10-v3.3任务规划.md` 中的 **T0（门槛任务）**
**结论（先说结果）：** 架构**继续可行**，但设计文档中的「UDS 往返 5–15 μs」假设**只对 P50 成立，对 P99 不成立**，须更正。

---

## 1. 为什么要测

v3.3 的读写分离架构把"写"从共享内存直写改为经 `rtdbd` 服务进程（UDS/RPC）。这个改动的全部代价，就是每次写多出一次 IPC 往返。

架构论证（[`03-设计文档/05-读写分离与双通道架构设计.md`](../03-设计文档/05-读写分离与双通道架构设计.md) §1.1）建立在两个假设上：

1. UDS 往返约 5–15 μs
2. 1 ms 控制周期下写 10 次 ≈ 100 μs，占预算 10%，可接受

假设 2 依赖假设 1。**T0 的目的就是在投入实现前，先把假设 1 实测出来。**

## 2. 方法

| 项 | 内容 |
|---|---|
| 程序 | `tests/bench/uds_latency.c`（新增） |
| 脚本 | `scripts/run_uds_bench.sh`（新增），支持 `--quick`、`WARMUP`/`ITERS`/`MSG_SIZE` |
| 结构 | `fork()` 出父子进程，父=UDS 服务端（收 N 字节回 N 字节），子=客户端测量 `send`+`recv` 往返耗时 |
| 计时 | `clock_gettime(CLOCK_MONOTONIC)`，测量窗口紧贴 send 前后 |
| 参数 | 预热 20000 次 + 测量 200000 次；分别测 16B（最小请求）与 48B（接近真实写请求） |
| 环境 | Linux 7.0.0-31-generic x86_64，Intel Xeon Gold 6330 @ 2.00 GHz，112 核；`-O2` |

## 3. 结果

### 3.1 请求/响应 16 B

| 指标 | 实测 |
|---|---|
| min | 5.220 μs |
| mean | 11.201 μs |
| **P50** | **11.585 μs** |
| **P99** | **18.182 μs** |
| P99.9 | 26.761 μs |
| max | 516.695 μs（离群） |
| 吞吐 | 79.83 K round-trip/s |

### 3.2 请求/响应 48 B（接近真实写请求）

| 指标 | 实测 |
|---|---|
| min | 6.721 μs |
| mean | 13.339 μs |
| **P50** | **12.777 μs** |
| **P99** | **23.956 μs** |
| P99.9 | 29.931 μs |
| max | 878.015 μs（离群） |
| 吞吐 | 67.51 K round-trip/s |

两轮测量数值稳定（P50 11.6 / 12.8 μs，P99 18.2 / 24.0 μs）。

## 4. 结论与影响评估

### 4.1 假设校验

| 假设 | 校验结果 |
|---|---|
| P50 落在 5–15 μs | ✅ **成立**（11.6 / 12.8 μs） |
| P99 落在 5–15 μs | ❌ **不成立**（18.2 / 24.0 μs，超出上限 21%–60%） |

设计文档中"往返 ~5–15 μs"的表述**必须更正**为实测值，不能继续沿用。

### 4.2 架构是否还成立 → **成立**

按现场确认的"1 ms 控制周期、控制一般不频繁"重算预算：

| 口径 | 每次写 | 每周期 10 次写 | 占 1 ms 预算 |
|---|---|---|---|
| 均值 | ~13 μs | ~130 μs | **13%** |
| P99 悲观叠加 | ~24 μs | ~240 μs | **24%** |

即使按 P99 悲观估算也在预算四分之一以内，**架构前提没有被推翻**。

### 4.3 但有一个更优的写法值得纳入设计

实测的是**同步等待确认**的往返。而在 fail-operational 的设计里，客户端本来就有**本地写队列**——若写调用只做"入队即返回"，则：

- **应用可见的写延迟 = 本地入队开销（ns 级），完全不受 UDS RTT 影响**
- 只有"同步等确认"模式才付 12–24 μs 的代价

建议 v3.3 提供两种写入模式（待评审）：

| 模式 | 语义 | 延迟 | 适用 |
|---|---|---|---|
| 异步（建议默认） | 入队即返回 `IRT_QUEUED` | ns 级 | 控制回路高频写 |
| 同步 | 等服务端确认已落 shm | P50 ~13 μs / P99 ~24 μs | 需确认的关键写、HMI 下发 |

> 注意：异步模式下"是否已提交"需通过质量位与队列状态判断，不能假定立即生效——这与 T3 的 `COMM_FAILURE` / 新鲜度标记设计正好咬合。
