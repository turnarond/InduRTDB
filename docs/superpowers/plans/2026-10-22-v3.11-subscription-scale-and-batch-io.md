# v3.11 单连接 10k 订阅与批量 I/O 实现计划

> 设计依据：`docs/superpowers/specs/2026-10-22-v3.11-subscription-scale-and-batch-io-design.md`（已批准，2026-10-22）
> 日期：2026-10-22
> 状态：**待实施**
> 目标：单连接 10,000 订阅、连接池 32 初始 / 128 最大、批量读写、流式快照与能力协商。

## 1. 目标与非目标

### 目标

1. 单连接订阅上限从 1024 提升到 **10,000**；每连接初始 1024，按需增长。
2. 连接池从固定 128 个内嵌连接改为 **32 条预创建 + 最多 128 条按需分配**。
3. 新增 `BATCH_READ` / `BATCH_WRITE`，单请求最多 1024 点，逐项返回状态。
4. `SET_SUBS` 支持 10k，快照改为**分批流式**，新增 `SNAPSHOT_DONE` 完成屏障。
5. 新增 `OP_CAPS` 能力协商；旧客户端保持 ≤1024 订阅可用且不收到新帧。
6. 容量参数支持 CLI + YAML，优先级为默认值 < YAML < CLI，非法值 fail-fast。
7. 批量吞吐相对单点流水线 ≥ 2×；完成 2k/20k/200k/500k/1M 规模表征。

### 非目标

- 不改共享内存布局（段版本 3、点位 128 B、元数据 32 B）。
- 不新增公开 C API（保持 117 = 62 + 55）。
- 不做多线程 `rtdbd`；仍是单线程 `poll`。
- 不保证批量写跨点位原子性。
- 不把 1M × 10Hz 作为功能通过条件；饱和即记录上限。
- 不为每个通知或每个写请求分配内存。

## 2. 关键决策（本计划直接采用）

| # | 决策 | 理由 |
|---|---|---|
| D1 | `OP_HEALTH` 线格式保持 **72 B 不变**；新计数器只进 `rtdbd_stats_t` 与 SIGUSR1 dump | 避免破坏 `scripts/check_rtdbd_health.py` 与旧监控客户端 |
| D2 | `notify_drop_snapshot` 只统计“队列压力导致的快照丢弃”；断连清理只计 `notify_drop` | 保持验收不变式 `notify_drop_snapshot == 0` 有意义 |
| D3 | 性能矩阵新增 `scripts/run_scale_matrix.py`，复用 `run_station_load.py` 的辅助函数与 JSON 格式 | 20k 单站脚本与 2k–1M 矩阵是两种工作流，避免把现有脚本改复杂 |
| D4 | `max_points` 仍为 CLI-only，不进入 `rtdbd:` YAML 段 | 不改变点位段/共享内存语义 |
| D5 | 启动预分配失败 → `RTDBD_EXIT_SHM (3)`；运行期有界分配失败 → `RTDBD_ST_NO_MEM (5)` | 与现有段初始化/运行期错误分类一致 |
| D6 | 快照填队列批大小从 64 起，按 `snap_outq_count` 与队列空位动态调整 | 避免每轮 poll 只填一帧导致 10k 快照过慢 |
| D7 | `OP_SNAPSHOT_DONE` 只作为出站帧；入站 opcode 22 不注册处理器，按未知 opcode 拒绝 | 协议方向明确，避免客户端误用 |
| D8 | 批量请求/响应使用静态 BSS 暂存区，单线程串行复用 | 满足“禁止每写分配”，避免 72 KB 栈帧 |
| D9 | 批量写缓存一次 `peer_cred`，逐项从点位元数据取 `partition` 做 policy/白名单校验 | 满足跨分区逐点鉴权，避免每项 syscall |
| D10 | `SET_SUBS` 原子替换采用“预校验 + 暂存新表 + 成功后交换” | 失败时旧订阅集完全不变 |

## 3. 不可违反的约束

- `-Wall -Wextra -Werror`，零告警（GCC/Clang）。
- 不新增公开 C API；`python3 scripts/check_api_count.py` 必须仍是 **117 (62+55)**。
- **不新增 C/C++ 测试二进制**；所有断言并入既有 `test_c_*` / `test_rtdbd_*`。
- `rtdbd` 仍是单线程 `poll`；禁止每通知/每写请求分配。
- 不改 `indurtdb_point_t` / `indurtdb_meta_t` 尺寸与字段顺序。
- `git add` 只用显式路径，禁止 `git add -A`；不 push/tag/merge。
- 不删除既有测试来“通过”；旧协议行为必须保持可用。
- Release 与 Debug 构建都必须通过 `ctest`。

### Phase 2：`rtdbd_subtab_t` 动态扩容

**文件**

- `rtdbd/src/subtab.h`
- `rtdbd/src/subtab.c`
- `rtdbd/src/rtdbd.c`（初始化/释放调用点）
- `tests/integration/test_rtdbd_core.cpp`

**先写失败测试**（`test_rtdbd_core.cpp` 已编译 `subtab.c`）

- `SubtabGrowsAtHalfLoad`：容量 2048 插入到 1025，触发扩容，全部 `has()` 为真。
- `SubtabReserveRollback`：`reserve(UINT32_MAX)` 返回 `false`，旧表内容不变。
- `SubtabGrowthRehashPreserves`：扩容前后插入/删除/查询一致。
- `SubtabRemoveAfterGrowth`：扩容后 backward-shift 删除仍正确。

**实现**

```c
typedef struct {
    rtdbd_subtab_slot_t* slots;
    uint32_t             cap;    /* 2 的幂 */
    uint32_t             count;
} rtdbd_subtab_t;

void rtdbd_subtab_init(rtdbd_subtab_t* t, uint32_t initial_cap);
void rtdbd_subtab_free(rtdbd_subtab_t* t);
bool rtdbd_subtab_reserve(rtdbd_subtab_t* t, uint32_t min_cap);
```

- 容量下限 `RTDBD_SUBTAB_MIN_CAP=2048`，上限 `RTDBD_SUBTAB_MAX_CAP=32768`。
- 初始容量 = `next_pow2(2 * initial_subs_per_conn)`，默认 2048。
- 增长条件：`count + 1 > cap / 2`；容量序列 2048 → 4096 → 8192 → 16384 → 32768。
- 分配新表、重哈希、成功后交换；失败返回 `false`，旧表不变。
- `has/remove/decide` 不再使用静态 `RTDBD_SUBTAB_MASK`。
- 更新 `test_rtdbd_core.cpp` 中依赖 `RTDBD_SUBTAB_CAP` 的碰撞测试。

**验收**

- `test_rtdbd_core` 通过；`has/remove` 不分配内存。

### Phase 3：连接池 32 → 128

**文件**

- `rtdbd/src/rtdbd.c`
- `rtdbd/src/rtdbd_conf.h`（仅新增默认值宏）

**先写失败测试**（`test_rtdbd_notify.cpp`）

- `ConnectionsUpTo128`：同时建立 128 条连接，全部可读写；第 129 条被关闭。
- `ConnPoolReuse`：200 次连接/关闭后 fd 数有界。
- `PreallocatedConnections`：启动即存在 32 条预创建槽位；关闭后可复用。

**实现**

- `g_conns` 改为 `rtdbd_conn_t* g_conns[RTDBD_MAX_CLIENTS]`。
- `rtdbd_conn_t` 增加：
  - `uint32_t* subs; uint32_t subs_cap;`
  - `rtdbd_subtab_t sub;`
  - `bool caps_negotiated; bool snap_active;`
  - `uint32_t snap_next, snap_emitted, snap_outq_count;`
- 新增 `RTDBD_INITIAL_CLIENTS 32`、`RTDBD_INITIAL_SUBS_PER_CONN 1024`。
- 启动：为前 `initial_clients` 个槽位 `calloc` 连接结构，并按 `initial_subs` 分配 `subs` + `subtab`；失败退出 `RTDBD_EXIT_SHM`。
- `accept()`：优先复用 `fd < 0` 的预创建槽；否则在 `max_clients` 内 `calloc`；再否则关闭新 fd 并 `conn_alloc_fail++`。
- 关闭：动态分配的连接 `free` 全部内存并置空槽位；预创建连接 reset 复用。
- 所有 `conns[i].` 改为 `conns[i]->` 并加 NULL 检查；`rtdbd_ctx_t.conns` 改为 `rtdbd_conn_t**`。
- `notify_broadcast`、`conn_table_check`、`op_health` 适配指针数组。
- 共享内存 `max_subscribers` 仍为 `RTDBD_MAX_CLIENTS`，不随 `max_clients` 改变。

**验收**

- 128 连接可用；32 条预创建生效；连接 churn 无 fd/内存增长。

### Phase 4：通用出站帧与部分发送门控

**文件**

- `rtdbd/src/rtdbd.c`
- `tests/integration/test_rtdbd_backpressure.cpp`

**先写失败测试**

- `PartialSendDefersRequests`：慢读端制造部分发送，再发请求；响应在该帧完成后才出现，字节流无交错。
- `LiveDropCounted`：队列满时实时帧被丢弃，`notify_drop` 与 `notify_drop_live` 增长，`notify_drop_snapshot==0`。
- `NeverEvictPartiallySentHead`：`outq_sent != 0` 时队首不被淘汰。
- `ControlFrameNeverDropped`：`SNAPSHOT_DONE` 入队不受实时丢弃策略影响。

**实现**

```c
typedef struct {
    uint16_t opcode;
    uint16_t payload_len;
    union {
        rtdbd_notify_t        notify;
        rtdbd_snapshot_done_t done;
    } u;
} rtdbd_outq_frame_t;

RTDBD_STATIC_ASSERT(sizeof(rtdbd_outq_frame_t) == 40, "outq frame must be 40B");
```

- `outq` 改为 `rtdbd_outq_frame_t outq[RTDBD_OUTQ_CAP]`。
- 新增 `outq_push_notify()`、`outq_push_snapshot()`、`outq_push_done()`；后两者为控制/快照帧，永不丢弃。
- 实时帧满队列规则：
  - `outq_sent == 0` 且队首为实时帧：淘汰队首；
  - `outq_sent == 0` 且队首为快照/控制帧：丢弃本次实时帧；
  - `outq_sent != 0`：丢弃本次实时帧；
  - 三种情况都计 `notify_drop` 与 `notify_drop_live`。
- `outq_flush` 每帧动态组头：总长 = `sizeof(rtdbd_req_hdr_t) + payload_len`（44 B 或 20 B），按 `outq_sent` 续发。
- 快照帧在 `reserved[1]` 置 `RTDBD_NOTIFY_F_SNAPSHOT`。
- 主循环事件：`POLLOUT`（有队列）+ `POLLIN`（仅 `outq_sent == 0`）。
- 删除 `op_set_subs` 的 `if (outq_sent != 0) return 1;`；请求由主循环延迟处理。
- `conn_discard_outq` 断连只累加 `notify_drop`；`conn_clear_outq_soft` 不计任何丢弃。

**验收**

- `test_rtdbd_backpressure` 与 `test_rtdbd_notify` 通过；无帧交错。

### Phase 6：`SET_SUBS` 10k + 流式快照 + `SNAPSHOT_DONE`

**文件**

- `rtdbd/src/rtdbd.c`
- `tests/integration/test_rtdbd_notify.cpp`
- `tests/integration/test_rtdbd_backpressure.cpp`
- `tests/fixtures/`（10k 点 YAML 生成辅助，不新增可执行文件）

**先写失败测试**

- `SetSubs10kSnapshotDone`：10k 点、`OP_CAPS` 后 `SET_SUBS` 10k → 10k 个升序 snapshot 帧，随后 `SNAPSHOT_DONE{count=10000, flags=1}`。
- `LegacyClientNoCapsNoDone`：不发 `OP_CAPS` → 快照正常，无 `SNAPSHOT_DONE`，无解析错误。
- `SetSubs10kEmptySnapshot`：合法但全部不可读/删除的点 → `SNAPSHOT_DONE.count == 0`（已协商时仍发送）。
- `SetSubsWhileSnapshotQueued`：快照帧已排队但无部分发送时再次 `SET_SUBS` → 软清旧队列，旧快照取消，新快照完成，无交错。
- `SnapshotSurvivesSlowConsumer`：慢读端 → `notify_drop_snapshot == 0`，实时帧丢弃计入 `notify_drop_live`。
- `SetSubsRejectsDuplicate`、`SetSubsOverMaxReturnsBadRequest`：旧订阅不变。

**实现**

- `g_set_subs_ids[10000]`（40 KB BSS），请求最大 `4 + 4*10000 = 40,004 B`。
- 排序：`qsort` + 相邻重复检测；保持升序。
- 原子替换：
  1. 逐 id `point_subscribable` 校验；
  2. 分配目标容量的 `subs` 数组与暂存 `subtab`；
  3. 全部插入成功后再交换；
  4. 任一步失败 → 释放暂存，返回 `NO_MEM`/`BAD_REQUEST`，旧订阅集不变。
- `conn_install_subs()` 与 `conn_start_snapshot()` 拆分；`conn_replace_subs` 不再立即逐帧入队。
- 快照字段：`snap_active`、`snap_next`、`snap_emitted`、`snap_outq_count`。
- `conn_snapshot_pump()` 每轮主循环调用：
  - 条件：`snap_active && snap_next < nsubs && snap_outq_count < 767` 且队列有空位；
  - 每轮填 64 帧（按空位调整），构造 NOTIFY 并置 `RTDBD_NOTIFY_F_SNAPSHOT`；
  - 入队时同步更新 RBE `valid/last_reported`；
  - 点删除/不可读时跳过，`snap_emitted` 不增加。
- 最后一张快照帧入队后，立即 `outq_push_done()`（仅 `caps_negotiated`），`count=snap_emitted`，`snap_active=false`。
- `SET_SUBS` 成功后先 `conn_clear_outq_soft()`，再启动新快照；旧快照不再发 `SNAPSHOT_DONE`。
- `notify_broadcast` 使用实时入队；快照使用快照入队。

**验收**

- 10k 快照全部收到；`SNAPSHOT_DONE.count` 正确；`notify_drop_snapshot == 0`。
- 旧客户端无 `SNAPSHOT_DONE` 且不报错。
- 10k 集成测试运行时间控制在 ~30 s 内；128×10k 只做性能档，不进默认 ctest。

### Phase 7：`BATCH_READ` / `BATCH_WRITE`

**文件**

- `rtdbd/src/rtdbd.c`
- `tests/integration/test_rtdbd_proto_v3.cpp`

**先写失败测试**

- `BatchRead1024`、`BatchReadPartialStatus`（有效/未注册/删除混合）、`BatchReadPreservesOrder`、`BatchReadDuplicateIds`、`BatchReadCountZeroBadRequest`、`BatchReadOverMaxBadRequest`、`BatchReadPayloadMismatch`。
- `BatchWrite1024`、`BatchWritePartialFailure`、`BatchWriteCrossPartition`、`BatchWriteDuplicateIds`、`BatchWriteAuditAndStats`、`BatchWritePayloadMismatch`。

**实现**

- 从 `op_write` 抽出 `write_one(cx, const rtdbd_write_req_t*, uint32_t partition, uint16_t* status)`，保持单点 `OP_WRITE` 行为不变。
- `op_batch_read`：
  - 校验 `payload_len == 4 + 4*count`、`1 <= count <= cx->max_batch`；
  - 静态响应缓冲 `4 + 1024*72 = 73,732 B`；
  - 逐项 `do_get`，响应顺序与请求一致；失败项 `value` 全 0。
- `op_batch_write`：
  - 校验 `payload_len == 4 + 24*count`、`1 <= count <= cx->max_batch`；
  - 静态请求缓冲 `4 + 1024*24 = 24,580 B`，响应缓冲 `4 + 1024*8 = 8,196 B`；
  - `peer_cred()` 每请求一次；
  - 每项读点位元数据取 `partition`，做 `irt_policy_allows` 与 `rtdbd_conf_partition_allowed`；
  - 调 `write_one`；成功项 `irt_audit_record` + `n_writes++`；
  - 每成功项触发既有 `notify_broadcast`，不合并；
  - `n_batch_write_reqs++` 每请求一次。
- 整包校验失败 → `BAD_REQUEST`，不执行任何写入；单项失败不影响其他项，整包响应 `status=OK`。
- 注册到 `kOps[]`：opcode 19/20。

**验收**

- `test_rtdbd_proto_v3` 通过；批量读/写 1024 点；部分失败不回滚成功项；跨分区逐点鉴权正确。

## 8. 风险与回滚

| 风险 | 缓解 |
|---|---|
| `conns[]` → `conns*[]` 改动面大 | 单独 Phase 3，机械替换 + NULL 检查，全量 ctest |
| 10k 测试慢/不稳定 | 用 10k 点 YAML fixture，避免 10k 次 CREATE_POINT；128×10k 只进性能档 |
| 快照饿死实时帧 | 767/256/1 预算；`notify_drop_snapshot==0` 断言 |
| 旧健康脚本被破坏 | `OP_HEALTH` 72 B 不变（D1） |
| `--max-subs` 默认值变化 | 显式 `--max-subs 1024` 可回退；升级文档标注 |
| 分配失败破坏订阅 | 暂存表 + 成功后交换；失败 `NO_MEM`，旧状态不变 |
| 批量 72 KB 响应阻塞慢客户端 | 本机 UDS；测试覆盖慢读；客户端必须持续读取 |
| 1M×10Hz 不可达 | 明确为饱和测试，只记录上限 |

回滚策略：

- 任一 Phase 失败，`git checkout -- <files>` 回到上一提交，不跨 Phase 混改。
- 若 10k 动态分配方案不可行，回退到“每连接固定 10k 预分配”会突破内存目标，不采用；改为降低默认上限并记录。
- 若 `SNAPSHOT_DONE` 兼容性出现回归，保留 `OP_CAPS` 门控，禁止对未协商连接发送任何新帧。
