# v3.11 设计：单连接 1 万订阅与批量读写

**日期**：2026-10-22
**状态**：已批准（2026-10-22）；实现计划见 `docs/superpowers/plans/2026-10-22-v3.11-subscription-scale-and-batch-io.md`（已产出）
**基线**：v3.10.0（协议 v3、段版本 3、公开 API 117）
**版本号**：v3.11（暂定；若并入其他版本，仅改标题）

---

## 1. 意图与为什么

v3.10 解决的是“单站 2 万点、50 客户端、每客户端 500 个可视点位”。它的每连接订阅上限是 1024，整个 rtdbd 的连接上限是 128，因此总订阅关系上限是：

```text
128 × 1024 = 131,072
```

这只覆盖 100 万点的 13.1%。当点位规模到 20 万、50 万、100 万时，报警、历史、前端即使只订阅一部分，也会先撞订阅容量，而不是先撞共享内存点位容量。

同时，现有协议只有单点 `GET` / `WRITE`，没有批量读写请求。大规模查询只能由客户端串行发多条请求，syscall 和往返次数成为主要开销。

**一句话**：v3.11 把“单连接订阅容量”从 1024 提升到 10,000，并新增批量读写协议；不追求单连接承载 100 万订阅。

### 1.1 用户已确认的约束

- 单连接订阅目标：**10,000**，即扩大 10 倍。
- 实际推送量由数据变化驱动，正常工况不会持续全量变化。
- 查询可能一次涉及较多点位，**查询延迟不做硬性要求**，允许分批。
- 初始快照允许分批、流式回送。
- 连接池：初始预留 **32** 条，最大 **128** 条。
- 每连接订阅：初始预留 **1024**，最大 **10000**。
- 以上容量参数必须可通过配置调整。
- 新增批量读写接口；批量接口的吞吐应显著高于逐条接口。

## 2. 目标 / 非目标 / 反目标

### 2.1 目标

- 单连接可成功建立 10,000 个订阅；`SET_SUBS` 支持 10,000 个 id。
- 10,000 点初始快照可分批回送，不再因为出站队列 1024 槽而丢弃快照。
- 默认连接池 32 条，按需扩展到 128 条；默认每连接预留 1024 订阅，按需扩展到 10,000。
- 容量参数支持 CLI 与配置文件，且启动时 fail-fast 校验。
- 新增 `BATCH_READ` / `BATCH_WRITE`，单请求最多 1024 个点位；批量吞吐显著高于逐条流水线。
- 新增能力查询，客户端可在运行期获知每连接订阅上限、批量上限、连接上限。
- 10 万 / 20 万 / 50 万 / 100 万点位的性能测试可执行、可记录、可复现。
- 既有 ≤1024 订阅的客户端保持兼容。

### 2.2 非目标

- 单连接 100 万订阅。
- 批量写跨点位原子性（本设计采用逐点部分成功）。
- 大批量查询的低延迟 SLA；只要求正确、可分批、可观测。
- 订阅持久化、断线续订、跨进程直接写通知。
- 修复 v3.10 已知的 rtdbd CPU 60.3% 性能债；本设计只测量并防止明显回退。
- 改变共享内存点位布局、段版本或公开 API 数量。

### 2.3 反目标（即使功能可用也算失败）

- 通过无上限堆增长支持 10k/128 连接，导致内存不可预测。
- 快照分批时静默丢帧，或客户端无法判断快照何时结束。
- 批量写失败一半却不告诉客户端哪些点成功。
- 为支持 10k 订阅而让普通 `SUBSCRIBE` / `WRITE` 路径分配内存。
- 为了 1M 测试通过而把超时、丢帧、错误全部隐藏。

## 3. 容量模型

### 3.1 硬上限与默认值

| 参数 | 编译期硬上限 | 默认值 | 说明 |
|---|---:|---:|---|
| `max_clients` | `RTDBD_MAX_CLIENTS = 128` | 128 | 同时连接数 |
| `initial_clients` | `max_clients` | 32 | 启动时预创建的连接 |
| `max_subs_per_conn` | `RTDBD_SUB_MAX_PER_CONN = 10000` | 10000 | 单连接订阅上限 |
| `initial_subs_per_conn` | `max_subs_per_conn` | 1024 | 每连接初始订阅容量 |
| `max_batch` | `RTDBD_BATCH_MAX = 1024` | 1024 | 单次批量读写点位数 |
| `outq_cap` | 1024 | 1024 | 出站 NOTIFY 帧队列，不随订阅数扩大 |

`--max-subs` 的含义保持“每连接订阅上限”，但默认值和范围改为 `1..10000`。旧的 `--max-subs 4` 仍然有效。

### 3.2 内存模型

每连接内存按“初始 1024 + 按需增长”计算：

| 状态 | 订阅 id 数组 | 订阅/RBE 哈希表 | 出站队列 | 约合计 |
|---|---:|---:|---:|---:|
| 初始 1024 | 4 KB | 2048 × 16 B = 32 KB | 1024 × 40 B = 40 KB | **76 KB** |
| 满 10000 | 40 KB | 32768 × 16 B = 512 KB | 40 KB | **592 KB** |

- 32 条初始连接：约 **2.4 MB**。
- 128 条连接全部满 10k：约 **75.8 MB**（不含分配器元数据和临时快照内存）。
- 出站队列槽从 32 B 的 `rtdbd_notify_t` 改为 40 B 的通用帧（见 §4.10），以容纳 `SNAPSHOT_DONE`。
- 这是硬上限；不是启动即分配。只有实际超过 1024 的连接才增长。
- 连接关闭时释放该连接的订阅数组、哈希表和连接结构，内存回落到当前活跃连接规模。
- 允许运行期有界分配；**禁止**每个通知、每个写请求分配内存。

### 3.3 连接池

- `g_conns` 从 `rtdbd_conn_t[128]` 改为 `rtdbd_conn_t* g_conns[128]`。
- 启动时创建 `initial_clients` 条连接，每条按 `initial_subs_per_conn` 分配订阅数组和哈希表。
- 第 `initial_clients+1` 条连接开始，在 `accept()` 时 `calloc` 连接结构；失败则关闭新 fd 并记录 `conn_alloc_fail`。
- 连接关闭时 `free` 该连接的所有动态内存，槽位置空。
- `pollfd` 数组仍按 `max_clients + 1` 在栈上分配；`max_clients ≤ 128`，约 1 KB，可接受。
- 共享内存段 `max_subscribers` 仍固定为 `RTDBD_MAX_CLIENTS`，不随运行期 `max_clients` 改变，避免旧段兼容问题。

### 3.4 订阅存储增长

`rtdbd_subtab_t` 从“内嵌 `slots[2048]`”改为“指针 + 容量”：

```c
typedef struct {
    rtdbd_subtab_slot_t* slots;
    uint32_t             cap;    /* 2 的幂 */
    uint32_t             count;
} rtdbd_subtab_t;
```

- 初始容量 = `next_pow2(2 * initial_subs_per_conn)`，默认 2048。
- 增长条件：`count + 1 > cap / 2`，即负载因子超过 50%。
- 容量序列：2048 → 4096 → 8192 → 16384 → 32768；上限 32768。
- 增长时分配新表、重哈希、成功后替换；失败返回 `false`，旧表保持不变。
- `subs[]` id 数组按同样容量增长，默认 1024，最大 10000。
- `SET_SUBS` 先按目标 count 预留，再构建新表；构建成功后一次性替换旧订阅集，失败则旧订阅集不变。
- 单点 `SUBSCRIBE` 在达到当前容量时按需增长；增长失败返回 `RTDBD_ST_NO_MEM`，不改变已有订阅。

### 3.5 配置

#### CLI

新增/调整：

```text
--max-clients N        同时连接上限（默认 128，范围 1..128）
--initial-clients N    启动预创建连接数（默认 32，范围 1..max-clients）
--max-subs N           每连接订阅上限（默认 10000，范围 1..10000）
--initial-subs N       每连接初始订阅容量（默认 1024，范围 1..max-subs）
--max-batch N          单次批量读写上限（默认 1024，范围 1..1024）
```

#### 配置文件

复用 `--config` 指向的 YAML，在 `points:` 之前新增顶层 `rtdbd:` 段：

```yaml
rtdbd:
  max_clients: 128
  initial_clients: 32
  max_subs_per_conn: 10000
  initial_subs_per_conn: 1024
  max_batch: 1024

points:
  # 既有点位配置不变
```

优先级：**内置默认值 < 配置文件 < CLI**。

校验规则：

- `1 <= initial_clients <= max_clients <= 128`
- `1 <= initial_subs_per_conn <= max_subs_per_conn <= 10000`
- `1 <= max_batch <= 1024`
- 任一非法值 → 启动失败，退出码 `RTDBD_EXIT_CONFIG`，错误信息给出键名和允许范围。
- 不做静默截断，不自动修正。

## 4. 协议设计

### 4.1 版本策略

- 协议主版本保持 **3**。
- 不改变既有 opcode 的负载布局。
- 新增 opcode 是加法；旧客户端继续工作。
- 新客户端通过 `OP_CAPS` 探测服务端能力；探测失败（连接被旧服务端关闭）后重连，按旧服务端路径处理。
- `OP_SNAPSHOT_DONE` **只在客户端发送过 `OP_CAPS` 的连接上发送**；未协商的旧客户端不会收到这个新推送帧，保持“只解析 NOTIFY”的兼容性。
- `OP_CAPS` 成功后，服务端在该连接上记录 `caps_negotiated = true`；连接关闭即复位。

### 4.2 新增 opcode

| opcode | 名称 | 方向 | 说明 |
|---:|---|---|---|
| 19 | `RTDBD_OP_BATCH_READ` | C→S | 批量读取点位当前值 |
| 20 | `RTDBD_OP_BATCH_WRITE` | C→S | 批量写入点位 |
| 21 | `RTDBD_OP_CAPS` | C→S | 查询服务端容量与批量能力；成功后启用本连接的新推送能力 |
| 22 | `RTDBD_OP_SNAPSHOT_DONE` | S→C | 通知客户端 `SET_SUBS` 快照流结束；仅对已协商连接发送 |

快照帧标识：

```c
/* rtdbd_notify_t.reserved[1] 的 bit0；reserved[1] 其余位与 reserved[2] 仍为 0 */
#define RTDBD_NOTIFY_F_SNAPSHOT 0x01u
```

### 4.3 状态码

新增：

```c
#define RTDBD_ST_NO_MEM 5u   /* 有界分配失败，旧状态保持不变 */
```

既有状态码不变。**不新增 `BUSY`**：部分发送期间的请求由主循环延迟处理（§4.9），`SET_SUBS` 不再需要客户端重试。

### 4.4 `OP_CAPS`

请求负载：空。

响应负载（32 B）：

```c
typedef struct {
    uint32_t proto_version;
    uint32_t max_clients;
    uint32_t initial_clients;
    uint32_t max_subs_per_conn;
    uint32_t initial_subs_per_conn;
    uint32_t max_batch;
    uint32_t flags;       /* bit0=BATCH_READ, bit1=BATCH_WRITE, bit2=SNAPSHOT_DONE */
    uint32_t reserved;    /* 必须为 0 */
} rtdbd_caps_t;
```

`RTDBD_STATIC_ASSERT(sizeof(rtdbd_caps_t) == 32)`。

语义：

- 请求无负载；响应 `status=OK` 时携带 `rtdbd_caps_t`。
- 成功即把本连接标记为 `caps_negotiated=true`，之后才发送 `OP_SNAPSHOT_DONE`。
- 旧服务端不认识该 opcode，会返回 `BAD_REQUEST` 并关闭连接；新客户端必须把“探测时断连”视为旧服务端，重连后回退到 v3.10 路径（`max_subs=1024`、无批量、无 `SNAPSHOT_DONE`）。
- 该 opcode 可在连接生命周期内重复发送；重复发送只更新客户端拿到的能力值，不改变连接状态。

### 4.5 `OP_BATCH_READ`

请求负载：

```c
typedef struct {
    uint32_t count;             /* 1..max_batch */
    uint32_t point_ids[count];  /* 按请求顺序 */
} rtdbd_batch_read_req_t;       /* 变长；头部 4 B */
```

响应负载：

```c
typedef struct {
    uint32_t point_id;
    uint16_t status;
    uint16_t reserved;          /* 必须为 0 */
    rtdbd_get_resp_t value;     /* 64 B；status != OK 时全 0 */
} rtdbd_batch_read_item_t;      /* 72 B */

typedef struct {
    uint32_t count;
    rtdbd_batch_read_item_t items[count];
} rtdbd_batch_read_resp_t;
```

语义：

- 响应项顺序与请求顺序一致。
- 每个点位独立返回状态；无效 id、未注册、读取失败只影响该项，不影响整批。
- `status == OK` 时 `value` 有效；否则 `value` 全 0。
- 重复 id 允许，按请求顺序重复返回。
- 读权限与现有 `GET` 一致，不额外引入 ACL。
- `count == 0` 或 `count > max_batch` → `BAD_REQUEST`，不返回项。
- 响应最大 `4 + 1024 × 72 = 73,732 B`。

### 4.6 `OP_BATCH_WRITE`

请求负载：

```c
typedef struct {
    uint32_t count;                 /* 1..max_batch */
    rtdbd_write_req_t items[count]; /* 24 B/项，复用单点写结构 */
} rtdbd_batch_write_req_t;
```

响应负载：

```c
typedef struct {
    uint32_t point_id;
    uint16_t status;
    uint16_t reserved;   /* 必须为 0 */
} rtdbd_batch_write_item_t;  /* 8 B */

typedef struct {
    uint32_t count;
    rtdbd_batch_write_item_t items[count];
} rtdbd_batch_write_resp_t;
```

语义：

- **逐点部分成功**：按请求顺序逐项校验、鉴权、写入、触发通知。
- 单项失败只记录该项状态，继续处理后续项；不因一个点失败回滚整批。
- 响应项顺序与请求顺序一致，`point_id` 回显请求 id。
- 重复 id 允许，按请求顺序依次写，后写覆盖前写；每项均有独立状态。
- 类型不支持、鉴权拒绝、点位不存在、写入错误分别返回既有状态码。
- **分区与鉴权**：每个 item 用其 `point_id` 所属点位的 `partition` 做 policy/分区白名单校验；**不受连接 `OP_SELECT` 默认分区限制**。一批可以跨分区，只要每个点都通过策略。`rtdbd_write_req_t` 不带 partition 字段，服务端从点位元数据读取。
- **审计与统计**：每个成功项写一条审计记录（与单点 `WRITE` 相同），`n_writes` 按成功项 +1；另加 `n_batch_write_reqs` 按请求 +1。审计环溢出沿用现有策略，不因批量而少审计。
- 整包 `count == 0`、`count > max_batch`、`payload_len` 不匹配 → `BAD_REQUEST`，不执行任何写入。
- 批量写不提供跨点位原子性；需要事务语义的上层必须自行实现。
- 批量写通知：每个成功项按现有单点写路径产生 NOTIFY；批量写不合并通知。

### 4.7 `OP_SNAPSHOT_DONE`

响应/推送负载（8 B）：

```c
typedef struct {
    uint32_t count;   /* 本次实际发出的 snapshot 帧数；跳过/删除的点不计入 */
    uint32_t flags;   /* bit0=COMPLETE；其余保留为 0 */
} rtdbd_snapshot_done_t;
```

- **仅对 `caps_negotiated=true` 的连接发送**；未发送 `OP_CAPS` 的旧客户端不会收到该帧。
- 仅在一批 `SET_SUBS` 的所有 snapshot 帧都已入队并发送完成后发送。
- `OP_SNAPSHOT_DONE` 与 NOTIFY 走同一个出站队列，排在最后一个 snapshot 帧之后，因此不会越过 snapshot 帧；实时帧可以出现在它之前或之后。
- `count` 是实际发出的 snapshot 帧数；如果某个已订阅点在快照过程中删除/不可读，该点跳过且不计入 `count`。
- 客户端应以 `OP_SNAPSHOT_DONE` 作为**唯一完成屏障**；`count` 用于观测/校验，不要求客户端先等满 `count` 帧。
- `count == 0` 时，`SET_SUBS` 成功后立即入队并发送该帧（仅已协商连接）。

### 4.8 `SET_SUBS` 变更

- 单次最多 10,000 个 id；请求负载最大 `4 + 4 × 10000 = 40,004 B`。
- 校验规则保持：id 必须可订阅、去重、整组原子替换、失败旧订阅不变。
- 重复检查从 O(n²) 改为排序后线性扫描；`qsort` 排序，保持快照 id 升序。
- 成功响应仍为空负载。
- 成功后不再一次性入队 10,000 帧，而是启动**分批快照流**：
  - 清空旧出站队列（软清理，不计 `notify_drop`）。
  - 替换订阅集，设置 `snap_active=true`、`snap_next=0`、`snap_emitted=0`。
  - 主循环在出站队列有空位时，按升序把快照帧填入队列。
  - 为实时变化保留 256 个队列槽，另为 `SNAPSHOT_DONE` 保留 1 个控制槽；快照最多占用 `outq_cap - 256 - 1 = 767` 槽。
  - 快照帧使用现有 NOTIFY 格式，并在 `reserved[1]` 置 `RTDBD_NOTIFY_F_SNAPSHOT`；入队时同步设置该点位的 RBE `valid/last_reported`，避免同一值重复推送。
  - 每入队一帧 `snap_emitted++`；`SNAPSHOT_DONE.count` 使用该值。
  - 当 `snap_next == nsubs` 且最后一个快照帧已入队，把 `OP_SNAPSHOT_DONE` 排到该帧之后；已协商连接才会收到。
- **快照与实时通知允许交错**：实时变化的 NOTIFY 可以排在快照帧之间；新客户端用 `RTDBD_NOTIFY_F_SNAPSHOT` 区分快照帧，旧客户端忽略该保留位。`OP_SNAPSHOT_DONE` 是快照完成屏障，不要求快照帧连续。
- **快照帧不丢弃**：`outq` 满时只丢弃实时帧。
  - 快照入队只在 `snap_outq_count < 767` 且队列有空位时进行；队列满时暂停快照，不覆盖已有快照帧。
  - 实时帧入队时若队列满：
    - `outq_sent == 0` 且队首是实时帧：淘汰队首，为本次实时帧腾位。
    - `outq_sent == 0` 但队首是快照/控制帧：不移动队首，丢弃**本次实时帧**。
    - `outq_sent != 0`：队首已部分上线，不能淘汰（否则新旧帧拼接会破坏帧边界）；丢弃**本次实时帧**。
    - 三种情况都计入 `notify_drop` 与 `notify_drop_live`；`n_notifies` 仍按“本次尝试入队”计数。
  - 新增统计：`notify_drop_live`、`notify_drop_snapshot`；后者必须始终为 0，用于验收“快照不被丢弃”。
- 快照期间收到新的 `SET_SUBS`：
  - 当前存在部分发送帧（`outq_sent != 0`）时，主循环按 §4.9 延迟读取/处理该请求；不返回 `BUSY`，不丢请求。
  - 当前帧发送完成后再处理：停止旧快照、清空队列、按新订阅集重新开始；旧快照不再发送 `SNAPSHOT_DONE`。
- 快照期间点位被删除：跳过该点，不阻塞快照；`snap_emitted` 不增加，客户端通过后续 `GET`/`LIST` 发现缺失。

### 4.9 请求处理与部分发送

现有实现中，若 NOTIFY 帧只发送了一部分，再直接发送请求响应会破坏帧边界。v3.11 明确一条全局不变式：

> 当 `outq_sent != 0` 时，不处理新的请求；先完成当前帧发送，再处理 POLLIN。

- 主循环对 `outq_sent != 0` 的连接只监听 `POLLOUT`，暂不处理 `POLLIN`。
- 该规则适用于所有 opcode，不只 `SET_SUBS`。
- 请求不会被丢弃，也不会返回 `BUSY`；它会在当前帧发送完成后按正常路径处理。
- `SET_SUBS` 在快照期间的处理因此是“先完成当前帧，再替换订阅集”，不需要客户端重试。

### 4.10 出站队列帧

现有 `outq` 只能存 32 B 的 `rtdbd_notify_t`，`outq_flush` 也把帧长硬编码为 44 B。v3.11 需要同时排队 NOTIFY 与 `SNAPSHOT_DONE`，因此改为通用帧：

```c
typedef struct {
    uint16_t opcode;       /* RTDBD_OP_NOTIFY 或 RTDBD_OP_SNAPSHOT_DONE */
    uint16_t payload_len;  /* 32 或 8 */
    union {
        rtdbd_notify_t        notify;
        rtdbd_snapshot_done_t done;
    } u;
} rtdbd_outq_frame_t;

RTDBD_STATIC_ASSERT(sizeof(rtdbd_outq_frame_t) == 40, "outq frame must be 40B");
```

- `rtdbd_conn_t.outq` 改为 `rtdbd_outq_frame_t outq[RTDBD_OUTQ_CAP]`。
- `outq_sent` 表示当前帧已发送字节数；帧总长为 `sizeof(rtdbd_req_hdr_t) + payload_len`，不再固定 44 B。
- `outq_flush` 每帧用 `rtdbd_req_hdr_t` 组头：`opcode=frame.opcode`、`payload_len=frame.payload_len`，再拷贝 `frame.u` 的前 `payload_len` 字节。
- `outq_push_notify()` 设置 `opcode=NOTIFY`、`payload_len=32`；快照帧在 `notify.reserved[1]` 置 `RTDBD_NOTIFY_F_SNAPSHOT`。
- `outq_push_done()` 设置 `opcode=SNAPSHOT_DONE`、`payload_len=8`；这是控制帧。
- **控制帧与快照帧永不丢弃**；实时帧按 §4.8 的规则丢弃并计数。
- 快照上限 767 + 实时保留 256 + 控制保留 1 = 1024，保证最后一个快照帧之后一定能入队 `SNAPSHOT_DONE`。
- 若 `outq_push_done()` 在不变式被破坏时仍无空位，视为内部错误：关闭该连接并记录 `notify_send_fail`，不允许丢弃控制帧。

## 5. 批量接口为什么更快、边界在哪

批量接口的主要收益：

- 一次请求头 + 一次响应头，减少 syscall。
- 一次鉴权/连接上下文建立，减少重复解析。
- 客户端可流水线化，减少往返等待。
- 批量读可在一次响应中返回 1024 个点，显著降低每点协议开销。

但不会把每点成本按批量数除下去：

- 每个点仍要做存在性、类型、鉴权、共享内存读写。
- 批量写每个成功点仍会触发通知扇出。
- 批量读响应最大约 72 KB，仍受 socket 发送和客户端读取速度约束。
- 当前 20k 写/s 已到 60.3% CPU；批量写提升的是吞吐上限，不是把 CPU 成本归零。

因此验收目标是“批量吞吐显著高于逐条流水线”，不是“批量 1024 点耗时等于单点”。

## 6. 性能测试规格

### 6.1 测试目标

分两类：

1. **容量正确性**：10k 订阅、128 连接、批量接口、快照分批是否按规格工作。
2. **规模化表征**：2k / 20k / 200k / 500k / 1000k 点位下，读写、批量读写、通知、CPU、内存的实际曲线。

### 6.2 点位规模

| 规模 | 说明 |
|---:|---|
| 2,000 | 小站/回归基线 |
| 20,000 | v3.10 既有单站基线 |
| 200,000 | 中规模 |
| 500,000 | 大规模 |
| 1,000,000 | 共享内存点位上限 |

1M 点位的共享内存约 128 MB；测试机需预留足够内存。

### 6.3 写负载

- 固定 10 个采集驱动，按点位范围分摊全部点位。
- 每个点位按 `1 Hz`、`5 Hz`、`10 Hz` 三档更新。
- 单档写吞吐 = `point_count × hz`：
  - 20k × 1 Hz = 20k 写/s
  - 200k × 1 Hz = 200k 写/s
  - 1M × 1 Hz = 1M 写/s
  - 1M × 10 Hz = 10M 写/s（预期饱和，用于找上限）
- 每档独立运行；不允许把不同 Hz 混在一次统计里。
- 20k 档持续 600 s；200k/500k/1M 档持续 60 s 或到明确饱和，记录实际完成量。

### 6.4 读负载

读客户端按 `1 Hz` 或 `0.5 Hz` 轮询：

| 读类型 | 每次读取比例 | 说明 |
|---|---:|---|
| 报警 | 总量的 10% | 可分批，每批 ≤1024 |
| 历史 | 总量的 20% | 可分批，延迟不敏感 |
| 前端 | 总量的 1%–5% | 前端掌握全量清单，但每次只取子集 |

- 读请求优先使用 `BATCH_READ`；每批 1024 点。
- 同时保留一组逐条 `GET` 对照，用于计算批量加速比。
- 前端连接每连接订阅不超过 10k；不要求单连接订阅全量。

### 6.5 通知负载

两种 profile：

1. **部署 profile**：按报警 10%、历史 20%、前端 1%–5% 建订阅；总订阅量约 `0.35 × point_count`。
2. **全量扇出压力 profile**：100 条连接 × 10k 订阅覆盖 1M 点；用于测最坏通知扇出，不代表现场常态。

通知测试要求：

- 每条连接只订阅子集，不要求单连接收全量。
- 记录 `notify_drop`、`notify_send_fail`、每连接队列高水位。
- 快照测试单独统计快照帧数、完成时间、是否收到 `SNAPSHOT_DONE`。

### 6.6 指标

必测：

- 写吞吐（点/s、请求/s）、写 ACK P50/P99/P999。
- 批量写吞吐、每批点数、每点成本。
- 单点读吞吐、批量读吞吐、每点读成本、批量加速比。
- 通知端到端延迟 P50/P99（写入时刻到客户端收到）。
- rtdbd CPU（用户态 + 系统态，单核百分比）。
- rtdbd RSS、峰值 RSS、共享内存大小。
- 连接数、订阅数、每连接订阅高水位。
- `notify_drop`（总）、`notify_drop_live`、`notify_drop_snapshot`、`notify_send_fail`、`conn_alloc_fail`、`subs_alloc_fail`、`n_batch_write_reqs`。
- 客户端错误数、超时数、断连数。

### 6.7 验收口径

**功能/容量（必须通过）**

- 单连接 `SET_SUBS` 10,000 个 id 成功。
- 10,000 点快照的 snapshot 帧全部收到；已协商客户端收到 `SNAPSHOT_DONE`，且 `count` 等于实际 snapshot 帧数。
- `notify_drop_snapshot == 0`；快照阶段若实时帧被丢弃，必须计入 `notify_drop_live`，不能算作快照丢失。
- 128 条连接可建立；默认 32 条预创建生效。
- `initial_subs=1024` 时，第 1025 个订阅触发扩容并成功。
- 批量读写 1024 点成功；逐项状态正确；部分失败不回滚成功项；批量写跨分区按逐点策略校验。
- 旧客户端 ≤1024 订阅仍可用；未发送 `OP_CAPS` 的旧客户端不要求收到 `SNAPSHOT_DONE`。

**性能（分层判定）**

- 20k 基线：相比 v3.10 不得出现 >10% 的吞吐回退；`notify_drop=0`（部署 profile）。
- 批量接口：相同总点数、同一连接、相同客户端并发度下，`BATCH_READ` / `BATCH_WRITE` 吞吐目标 ≥ **单点流水线**的 **2×**。基线定义为“同一连接最多 32 个未完成单点请求、每请求一个点”，批量为 1024 点/请求；同时记录串行单点作为参考。未达到时记录瓶颈，不伪造通过。
- 200k/500k/1M：以“可完成、可观测、无崩溃/泄漏”为通过条件；记录实际可持续写速率和饱和点，不设固定 CPU/延迟 SLA。
- 1M × 10Hz：允许饱和；必须记录在哪个吞吐点开始出现丢帧/超时/错误。

### 6.8 测试环境与复现

- x86_64 Linux，Release 构建；记录 CPU 型号、核数、内存、内核版本。
- UDS 本机通信，不使用网络。
- 每档测试前：停 rtdbd → 删除 `/dev/shm/indurtdb_<instance>` → 按规模启动 → 预热 10 s → 清零统计 → 正式采样。
- 每档至少 3 次，取中位数；保留原始日志和 JSON/CSV。
- CPU 用 `/proc/<pid>/stat` 或 `getrusage` 统计；必要时用 `perf stat` 辅助定位。
- 生成器与 rtdbd 分核运行，避免生成器 CPU 污染被测进程；记录是否使用 `taskset`。
- 脚本输出固定字段，便于跨版本比较。

## 7. 兼容性

| 维度 | 影响 |
|---|---|
| 共享内存布局 | 不变（段版本 3、点位 128 B、元数据 32 B） |
| 公开 API | 不变（117） |
| 协议 | 加法：4 个新 opcode + 1 个新状态码 + NOTIFY 保留位；主版本仍为 3 |
| 旧客户端 + 新 rtdbd | 可用；仍可 ≤1024 订阅、单点 GET/WRITE；未发 `OP_CAPS` 时不会收到 `SNAPSHOT_DONE` |
| 新客户端 + 旧 rtdbd | `OP_CAPS` 被旧服务端拒绝并断连 → 重连后回退 ≤1024、禁用批量；不要依赖 `NOT_IMPLEMENTED` |
| 旧段 + 新 rtdbd | 兼容；`max_subscribers` 仍固定 128 |
| `--max-subs` 默认值 | 1024 → 10000；旧脚本显式传值时不受影响 |

## 8. 风险与回退

| 风险 | 缓解 |
|---|---|
| 10k 订阅导致每连接内存增大 | 初始 1024，按需增长；连接关闭释放；配置硬上限；统计 RSS |
| 动态分配失败 | 返回 `NO_MEM`，旧订阅不变；记录 `subs_alloc_fail` |
| 快照 10k 帧压垮出站队列 | 分批流式发送；快照最多占 767 槽，另留 1 槽给 `SNAPSHOT_DONE`；快照帧不丢弃，队列满时优先丢实时帧 |
| 快照期间页面切换 | 部分发送时主循环延迟处理新请求；当前帧完成后停止旧快照并按新订阅集重启 |
| 批量写放大通知扇出 | 每点仍按现有通知路径；性能测试单独统计批量写通知成本 |
| 批量响应 72 KB 阻塞慢客户端 | 与现有 `LIST` 同类；本机 UDS，客户端必须持续读取；测试覆盖慢读场景 |
| 1M × 10Hz 不可达 | 明确为饱和测试，记录上限，不作为功能失败 |
| 默认 `--max-subs` 变化影响旧部署 | 发布说明标注；显式配置可恢复 1024 |

## 9. 测试与门禁

1. **单元**
   - `rtdbd_subtab` 扩容、重哈希、50% 负载、分配失败回滚。
   - 连接池 32→128、连接关闭释放、重复 accept 槽位复用。
   - 配置解析：默认值、YAML、CLI 覆盖、范围错误、`initial > max`。
   - `SET_SUBS` 10k：去重、排序、原子替换、快照游标、快照帧优先级、`SNAPSHOT_DONE.count`。
   - 批量读写编解码、逐项状态、重复 id、部分失败、上限校验。
   - 批量写逐点分区鉴权、跨分区批次、逐项审计/计数。
   - `OP_CAPS` 字段与 flags；`SNAPSHOT_DONE` 仅在 `caps_negotiated` 后发送。
   - 快照帧不丢弃；队列满时丢实时帧并正确计入 `notify_drop_live`。
2. **集成**
   - 128 连接 × 10k 订阅；快照帧完整 + `SNAPSHOT_DONE`（已协商连接）。
   - 未发送 `OP_CAPS` 的旧客户端：快照正常、无 `SNAPSHOT_DONE`、不因保留位出错。
   - 快照期间切换订阅：当前帧完成后处理新 `SET_SUBS`，旧快照取消，新快照完成；无帧交错。
   - 旧客户端 ≤1024 订阅回归。
   - 批量读 1024、批量写 1024、部分失败；批量写跨分区逐点策略。
   - 慢消费者：实时帧可丢弃并计数，`notify_drop_snapshot` 保持 0。
   - `outq_sent != 0` 时请求被延迟，不出现帧交错。
3. **性能**
   - 按 §6 矩阵执行；输出 JSON/CSV + 原始日志。
   - 20k 基线对比 v3.10。
   - 批量加速比统计。
4. **门禁**
   - `ctest` 全绿（Release + Debug）。
   - `-Wall -Wextra -Werror` 零告警。
   - API 计数 117 不变。
   - `verify_consume.sh` 通过。
   - 不新增 C/C++ 测试二进制；测试加入既有二进制。

## 10. 已裁定 / 留给实现者

### 已裁定

- 单连接 10k；连接 32 初始 / 128 最大；订阅 1024 初始 / 10k 最大。
- 容量参数 CLI + YAML，CLI 覆盖 YAML。
- 初始快照分批流式；快照帧带 `RTDBD_NOTIFY_F_SNAPSHOT`；实时帧可与快照帧交错；`SNAPSHOT_DONE` 是唯一完成屏障。
- `SNAPSHOT_DONE` 仅在客户端发送过 `OP_CAPS` 后发送；旧客户端不收到该帧。
- 快照帧不丢弃；队列满时丢实时帧，`notify_drop_snapshot` 必须为 0。
- 批量写逐点部分成功，不保证跨点原子性。
- 批量写逐点按点位所属分区鉴权；一批可跨分区；每成功项写一条审计并计入 `n_writes`。
- 批量上限 1024；批量读响应逐项状态。
- 批量加速比基线：同一连接 32 个未完成单点请求，批量 1024 点/请求。
- 协议主版本保持 3；新增 opcode 加法；新增 `NO_MEM` 与 NOTIFY 保留位。
- 允许运行期有界分配；禁止每通知/每写分配。
- `SNAPSHOT_DONE` 在 `count==0` 时也发送（已协商连接）。

### 留给实现者

- `rtdbd_subtab` 扩容时临时表的分配策略（单次 `malloc` vs 预分配 arena），但必须满足上限和失败回滚。
- 快照填队列的批大小（建议 64，按队列空位动态调整）。
- 性能脚本是扩展现有 `scripts/run_station_load.py` 还是新增 `scripts/run_scale_matrix.py`。
- 统计字段的具体命名与 dump 格式。
