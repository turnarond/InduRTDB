# v3.10 设计：单站规模化接入（2 万点 / 50 客户端 / 可视窗口订阅）

**日期**：2026-10-20
**状态**：待批准（builder check 的 11 个问题已归档，见 §10）
**基线**：v3.9.1（协议 v3、段版本 3、公开 API 117）

---

## 1. 意图与为什么

InduRTDB 目前没有外部需求输入，本设计从**单站 ISCS/BAS 的真实负载**反推下一版边界，而不是继续按功能清单排期。

目标场景：一个车站的 BAS/ISCS 实时层，**2 万点位、1s 采集周期、50 个读取方（HMI/控制器/诊断）**，HMI **只订阅当前画面可见的点位**（通常 ≤500 个）。

现状的共享内存核心在这个量级完全够用；真正会撞墙的是**接入形态**：

| 现状 | 单站后果 |
|---|---|
| 每连接订阅上限 `RTDBD_SUB_MAX = 32` | 一个画面 500 点无法订阅 |
| 实例订阅者上限默认 32 | 第 33 个客户端连不上 |
| 每连接出站队列 64 槽 | 一次画面刷新 500 点必丢通知 |
| 无“替换订阅集”操作 | 翻页只能不断新增订阅，很快触顶 |
| 超时策略是全局单值 | 1s 快点与 60s 慢点无法共存 |
| NOTIFY 不带 quality | 画面上的 Timeout/Bad 无法实时变色 |
| 监控台连接即拉全量并订阅全部点位 | 2 万点直接打爆链路 |

**一句话**：v3.10 只解决“单站 2 万点能不能稳定接进来”，不解决 10 万点以上中心级聚合。

## 2. 目标 / 非目标 / 反目标

### 目标
- 2 万点、1s 周期、50 客户端、每客户端 500 个可视点位稳定运行。
- 订阅集可**原子替换**（翻页不累积）。
- 可视窗口内通知**不静默丢失**；一旦丢弃必须可观测并能重同步。
- 每点位可配置超时（兼容现有全局超时）。
- NOTIFY 携带 quality。
- 监控台 2 万点可正常分页浏览与实时刷新。
- 不改共享内存布局、不改公开 API 数量（117 不变）。

### 非目标
- 10 万–50 万点的线路中心聚合（v4.x 另立设计）。
- 受控通道批量写（P1，单站 20k/s 仅占现有 UDS 能力约 25%）。
- 值持久化 / 掉电恢复（定位仍为内存实时层）。
- 双机冗余 / 主备切换（归 node-server 或上层）。
- 按用户/角色的点位级 ACL（现有 UID + 分区策略足够单站）。

### 反目标（即使能跑也算失败）
- 通过“无限加大队列”掩盖扇出问题，导致内存随客户端数线性失控。
- 为了 500 点画面把 `notify_drop` 变成常态，却不在 UI 暴露。
- 引入堆分配破坏“运行期零堆”的既有约束。

## 3. 负载模型与验收指标

**设计容量**：20,000 点（代码路径支持到 50,000，不做额外优化）；50 客户端；每客户端订阅 ≤500 点；1s 周期，10% 点位 200ms。

| 指标 | 目标 | 依据 |
|---|---|---|
| 直连写 P99 | ≤10 µs | 现值 0.255 µs |
| 直连读 P99 | ≤10 µs | 现值 0.044 µs |
| rtdbd 单点写往返 P99 | ≤50 µs | v3.3 实测 18–24 µs |
| 可视窗口通知端到端 | ≤50 ms | 1s 周期下的可感知阈值 |
| 负载下 `notify_drop` | **0** | 可视窗口语义 |
| rtdbd CPU（20k 写/s + 50×500 订阅） | ≤10%（单核） | 留现场余量 |
| rtdbd RSS | ≤50 MB | 连接表按 50 计 |
| 段内存（20k 点） | ≤4 MB | 176 B/点 + 对齐 |
| 连接 + 订阅 500 点 | ≤100 ms | 画面切换体验 |
| 超时扫描 20k | ≤2 ms | 实测 0.6 ms |

**实测基线（本机 x86_64 Release，2026-10-20）**：10k/100k 点初始化 1.3/10.3 ms；全量写 4.5/28 ms；全量读 0.29/2.69 ms；超时全标记 0.59/3.30 ms；内存 1.8/18 MB。

**v3.10 实测偏差（2026-10-22）**：600 s 单站负载（20k 点 × 1 Hz × 50 客户端 ×
500 订阅）写吞吐 19,996/s、`notify_drop=0`、无断链、RSS 10,184 KB；但 rtdbd CPU
为 362.08 s / 600.12 s ≈ **60.3% 单核**，**未达到 ≤10% 的设计目标**。该偏差记录为
已知性能债，不影响本轮功能验收；后续优化广播/发送路径的 syscall、锁竞争与每连接
flush 策略。部署侧在优化前应按约 0.7 个核心预留。完整证据见
`docs/08-验证记录/v3.10-T10-单站规模化验证.md`。

## 4. 部署前提（必须写进文档）

**只有经 `rtdbd` 的写才会产生 NOTIFY。** 核心库的订阅回调是进程内的，其他进程直接写共享内存不会通知 `rtdbd`。因此单站部署约定：

- 驱动/控制逻辑的写统一走 `rtdbd`（直连写只用于不要求通知的本机控制回路，且该点位对 HMI 只能靠轮询/重同步）。
- 20k 点 × 1s = 20k 写/s，占受控通道单点能力（约 80k/s）的 25%，可接受。

## 5. 设计

### D1 订阅集：新增 `OP_SET_SUBS`（原子替换）

- 新增 opcode `RTDBD_OP_SET_SUBS = 18`（17 已被 `OP_SELECT` 占用）。
- 请求负载：`u32 count` + `count × u32 point_id`；`count ≤ RTDBD_SUB_MAX_PER_CONN`；重复 id 去重。
- 校验（整组通过才生效）：id 在 `[0, max_points)` 且 `pts[id].name[0] != '\0'`（已注册）；点位**自身** `partition` 必须通过 `irt_policy_allows(uid, partition, id)`。**不**与连接的 `SELECT` 分区绑定（监控台默认跨分区浏览）；任一 id 失败则整组拒绝（越界/未注册 `RTDBD_ST_NOT_FOUND`，策略拒绝 `RTDBD_ST_DENIED`，长度/格式非法 `RTDBD_ST_BAD_REQUEST`），订阅表不变。
- 语义：一次性替换订阅表；**空集合 = 全部退订**。
- 替换后：先清空该连接的出站队列（**不计** `notify_drop`，避免翻页被误判为丢帧；不新增健康字段），再按 id 升序为每个点位入队一帧当前值。页 ≤500、队列 1024，快照可完整容纳。
- 保留现有 `OP_SUBSCRIBE` 逐点订阅（受同一上限约束），并**采用同一套校验**；行为较 v3.9.1 收紧。
- 旧客户端连新服务端可用；新客户端连旧服务端：旧服务端对未知 opcode 返回 `BAD_REQUEST` 并关闭连接，客户端重连后回退逐点 `SUBSCRIBE`，页大小降为 32（旧 `RTDBD_SUB_MAX`）。
- 每连接订阅上限 `RTDBD_SUB_MAX_PER_CONN = 1024`（可视窗口 500 + 余量）。
- 实例客户端上限 `RTDBD_MAX_CLIENTS = 128`（50 现场 + 监控台 + 诊断余量）。

### D2 出站队列：64 → 1024 槽

- `rtdbd_notify_t` 32 B，1024 槽 = 32 KB/连接；128 连接约 4 MB BSS，符合零堆约束。
- 保留“满则丢最旧”，但 500 点画面刷新 < 1024，正常负载不丢。
- `SET_SUBS` 在单线程事件循环内完成“清队列 → 入快照”，不会与并发的写通知交错；清空量不计入 `notify_drop`（也不新增健康字段），避免翻页被误判为丢帧。
- `notify_drop` 已计入健康快照；监控台检测到增长时提示“实时流已降级，正在重同步”，并重新发送 `SET_SUBS` 取快照。

### D3 订阅成员与 RBE 状态：线性表 → 开放寻址哈希

- 现状有**两处**线性成本：`conn_has_sub()` 对每次写做订阅表线性扫描，`rbe_decide()` 再做 RBE 表线性扫描。1024 订阅 × 20k 写/s × 50 连接约 5 亿次比较/s，D3 只换 RBE 表仍不达标。
- 改为**一张**容量 `roundup_pow2(2 × 订阅上限)` 的开放寻址表（2048 × 16 B = 32 KB/连接），键为 `point_id`，条目含 `valid` 与 `last_reported`；**成员判断与 RBE 门控共用该表**，均为 O(1)。
- 哈希用 FNV-1a（与 `irt_index` 一致），线性探测；删除只发生在整表清空，无需墓碑。
- `SET_SUBS` 替换时清空整表：翻页后所有点位重新“首值必发”，画面立即有值。
- 仅影响经 `rtdbd` 的写；直接写者仍无 RBE/通知（见 §4）。

### D4 每点位超时：复用元数据保留位（不改 ABI）

- `indurtdb_meta_t.reserved[8]` 中启用 `u32 timeout_ms`；`flags` 使用 **bit3** `IRT_META_FLAG_TIMEOUT`（bit2 已被 `INDURTDB_META_FLAG_DEADBAND_PCT` 占用），同步更新 `IRT_META_FLAG_KNOWN` 与协议注释。
- 配置入口：点位 YAML 增加可选 `timeout_ms`，由 `irt_config.c` 解析并写入元数据（与 `eur_min/eur_max/deadband/flags` 同路径）；不新增 `SET_META` 字段，监控台只读展示。
- `check_timeouts(global_ns)` 语义：点位启用 per-point 且 `timeout_ms > 0` 时用其值，否则用 `global_ns`；`global_ns == 0` 时**仍扫描**，只处理已启用 per-point 的点位（0 = 关闭全局默认，不是关闭扫描）。
- 全局默认入口：`rtdbd --timeout-ms <u32>`（毫秒，默认 `0`，`0` = 不给未配置点位的点设全局超时）。启动时换算为 `cfg.timeout_ns = ms * 1000000ULL`，作为 1 Hz 扫描的 `global_ns` 实参。
- **扫描归属 `rtdbd`**：新增独立 1 Hz 周期任务，调用 `check_timeouts(cfg.timeout_ns)`；只对 **Good→Timeout** 的点位发 NOTIFY，避免 20k 点每周期全量抖动。`check_timeouts` 本就跳过已 TIMEOUT 的点，因此同一超时不会重复通知。20k 扫描实测 0.6 ms，CPU 可忽略。
- 恢复方向（Timeout→Good）由正常写入完成：`pm_write_impl` 强制 GOOD，rtdbd 的写路径随即推送带 Good 质量的 NOTIFY，无需扫描参与。
- 跃迁检测由 `rtdbd` 维护一份固定 `RTDBD_TIMEOUT_MAX_POINTS = 50000` 的质量快照（50 KB BSS，覆盖设计上限 5 万点）完成：扫描前读旧值，扫描后比对。若启动时 `max_points > 50000`，禁用超时扫描并打印一次告警——不静默截断（D4/D7）。
- 不新增公开 API（`check_timeouts` 签名不变），API 计数保持 117。

### D5 NOTIFY 携带 quality

- `rtdbd_notify_t` 现有 `reserved[3]`，用 `reserved[0]` 存 `quality`，报文长度不变（32 B）。
- 新 Python 客户端把 `NOTIFY` 解析改为 `<IBB2xQQQ`；旧客户端忽略该字节。
- **新旧服务端区分**：客户端连接后先发一次 `SET_SUBS` 探测。成功 = 新服务端，启用质量字节；失败/断链 = 旧服务端，重连后回退并**忽略**质量字节（旧服务端 `memset` 的 0 会被误读为 Good）。
- 协议版本仍为 3（加法，保留字节）；不在 `PING` 增加能力位。
- 监控台直接使用推送质量；回退模式下保留 REST 值。

### D6 监控台：服务端分页 + 可视窗口订阅

- `GET /api/points?offset&limit&partition`：返回当前页与总数；元数据来自启动时缓存的注册表（CRUD 后刷新），值不再逐点 GET。
- **每个浏览器 WebSocket 独占一条 UDS 通知连接**：`SET_SUBS` 是连接级语义，共享一个 `NotifyListener` 会让两个页面互相覆盖订阅集。服务端限制并发 WS 会话数（默认 32），超限拒绝并提示。
- WebSocket 新增 `{op:"set_subs", ids:[...]}` → `OP_SET_SUBS`；翻页/过滤/分区切换都发整页 id。
- 首屏由 `SET_SUBS` 的快照帧填充值；连接建立时不再推 2 万点全量。
- 列表分页改为服务端分页；当前页 ≤200（默认 50），订阅当前页。
- 保留 `{op:"subscribe"}` 作为旧服务端回退路径：探测失败 → 重连 → 逐点订阅，页大小强制 32，并显示“旧版 rtdbd：仅支持 32 点/页”提示。

### D7 配置与默认值

- `rtdbd --max-subs` 含义改为**每连接订阅上限**，默认 1024，范围 1–1024。
- `rtdbd --timeout-ms` 新增：全局默认超时（毫秒），默认 `0`；`0` 只关闭全局默认，不关闭扫描（D4）。
- 共享内存 `max_subscribers` **不再由 `--max-subs` 决定**，固定为 `RTDBD_MAX_CLIENTS`（128），即 `cfg.max_subscribers = RTDBD_MAX_CLIENTS`。
- `RTDBD_MAX_CLIENTS = 128`（编译期）；50 现场 + 监控台/诊断余量。
- 共享内存 `max_subscribers` 在段创建时固定。
  - **升级注意**：已有段（32）在 attach 时因 `max_subscribers < 128` 失败。升级步骤：停 `rtdbd` → 删除 `/dev/shm/indurtdb_<instance>` → 启动（点位由配置重载，当前值丢失）。写入 `docs/07-部署运维/04-故障排查与升级.md`。
  - 现有测试中的 `--max-subs 4` 仍有效（只限制每连接订阅数），但会创建 128 订阅者的新段。
  - 测试夹具必须在 fork `rtdbd` 前 `shm_unlink("/indurtdb_<instance>")`，否则上一次运行留下的 4/32 订阅者旧段会让 attach 失败（见 §7 任务 0）。

## 6. 兼容性

| 维度 | 影响 |
|---|---|
| 共享内存布局 | 不变（段版本 3、点位 128 B、元数据 32 B） |
| 公开 API | 不变（117）；`check_timeouts` 语义扩展为“每点优先” |
| 协议 | 加法：新 opcode + 保留字节（quality）；版本号仍为 3 |
| ABI | 不变 |
| 旧监控台 + 新 rtdbd | 可用（逐点 SUBSCRIBE；不显示推送质量） |
| 新监控台 + 旧 rtdbd | 降级可用：SET_SUBS 探测失败 → 重连 → 逐点订阅、32 点/页、无质量推送 |
| 旧段 + 新 rtdbd | **需重建段**（订阅者上限提升） |

## 7. 测试与验收

1. **单元**：SET_SUBS 校验/替换/清空/去重；成员哈希与 RBE 哈希命中、冲突、整表清空；per-point 超时优先于全局、`global_ns == 0` 仍扫描；NOTIFY 质量编解码。
2. **集成**：50 连接 × 500 订阅；翻页 20 次订阅表不增长；快照完整且 `notify_drop == 0`；两个 WS 会话各自 `SET_SUBS` 互不影响；旧 opcode 回退（探测失败 → 重连 → 32 点/页）。
3. **超时**：`rtdbd` 1 Hz 扫描把 Good→Timeout 推送一次；恢复写入由写路径推送 Good；同一超时周期不重复推送。
4. **负载**（新增 `scripts/run_station_load.sh`）：20k 点、1s、20k 写/s 经 rtdbd、50 客户端 × 500 订阅、持续 10 分钟；断言 `notify_drop == 0`、P99 与 CPU/RSS 达标。
5. **E2E**：监控台 2 万点分页、翻页订阅替换、质量实时变色、超时点显示。
6. **门禁**：`ctest` 全绿、零警告、API 计数 117、`verify_consume.sh`。

## 8. 风险与回退

| 风险 | 缓解 |
|---|---|
| 每连接内存增大（≈68 KB） | 128 连接上限封顶，约 8.7 MB BSS；实测 RSS 纳入验收 |
| 500 点快照帧 + 并发写仍可能超 1024 | 暴露 `notify_drop`，监控台提示并重发 SET_SUBS 重同步 |
| 大量点位同周期超时（跃迁风暴） | 每连接只订阅可视窗口（≤500）且队列 1024；仍溢出则计入 drop 并触发重同步 |
| 每浏览器一条 UDS 连接 | 并发 WS 会话上限 32，超限拒绝并提示 |
| RBE/成员哈希实现错误导致漏报 | 保留线性实现作对照测试；首值必发用例 |
| 旧段无法 attach | 升级文档明确重建步骤；启动错误信息给出提示 |
| 直接写者误以为会推送 | §4 写入白皮书、SDK 与部署文档 |

| # | 评审问题 | 裁定 |
|---|---|---|
| 1 | 谁跑超时扫描、跃迁如何到订阅者 | `rtdbd` 1 Hz 扫描；只推 Good→Timeout；恢复由写路径推送；20 KB 快照比对（D4） |
