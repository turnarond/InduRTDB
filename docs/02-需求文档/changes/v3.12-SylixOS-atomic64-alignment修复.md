## 问题与影响

SylixOS 3.6.5 / ARM64（Cortex-A55）单台实测：`indurtdb_h_write_double` 触发内核异常（进程 exit 28），addr2line 把崩溃点定位到 `__aarch64_ldadd8_relax`。G1 报告记 `irt_point_manager.c:107`（`irt_pm_write_double` 内联展开的调用点），真正的 fetch_add 语句是被内联的 `:82` `__atomic_fetch_add(&hdr->stats.writes, 1)`。时间/OSAL（CASE 1）PASS，写路径（CASE 2）不可用。

**根因（汇编实证 + 布局分析）**：
1. GCC 10.2.1 在 `-mcpu=generic`（ARMv8.0 基线、无 LSE）下把 64 位 `fetch_add` 降级为 out-of-line helper `__aarch64_ldadd8_relax`（实测 `bl __aarch64_ldadd8_relax`）。注意同工具链下 8 字节 CAS 走的是**另一个** helper `__aarch64_cas8_acq_rel`（实测 `bl __aarch64_cas8_acq_rel`），不能笼统说"helper/LL-SC 机制异常"——LL-SC 机制在对齐地址上于 SylixOS 可用（见第 2 点）。
2. 更深层且经验证的主因：`stats.writes` 偏移 28、`stats.timeouts` 偏移 36（`irt_types.h:43-44`），在 `packed` header 中**仅 4 字节对齐**；AArch64 的 8 字节原子访问（helper 内 LL-SC 或 LSE `ldadd`）要求 8 字节自然对齐。**由调用顺序间接推断**：`pm_write_impl_q` 中 `:43` 的写锁获取走偏移 16（8 字节对齐）的 `write_seq` CAS，先于 `:82` 执行；G1 backtrace 未含该 CAS 的崩溃地址，故对齐的 8 字节 CAS 未崩、非对齐的 `writes` fetch_add 崩溃——**对齐差异是关键混杂变量**（此为源码顺序 + backtrace 的间接推断，非独立断言输出，板上复验时一并确认）。残余风险：不排除 `__aarch64_ldadd8_relax` 特有实现问题，但方案 A 同时规避"非对齐"与"out-of-line helper"两个变量，对该残余风险同样免疫。
3. 读端 `__atomic_load_n` 用 `__ATOMIC_RELAXED`（`irt_point_manager.c:202`、`indurtdb.c:797`），实测生成**普通 `ldr x0,[x0]`**（非 `ldar`），AArch64 普通 Load 支持非对齐，G1 现场大量执行未崩，排除读端风险。**实施禁令**：不得将这些 stats 读端改为 ACQUIRE/SEQ_CST（会生成 `ldar`，对偏移 28/36 的非对齐地址触发 alignment fault）；如要更强一致性只能随布局重排（改 ABI，本卡禁止）。

影响：所有 `indurtdb_h_write_*` 在 SylixOS 上不可用（写后统计累加必崩）；Linux 侧不受影响（x86-64 对非对齐原子容忍）。不修则 SylixOS 适配停在 G1，G2 无从起步。

## 设计决策

**方案 A（推荐）：把两处 64 位 `fetch_add` 改为"seqlock 写锁内普通自增"。**

- 改动：`irt_point_manager.c:82`（writes）与 `:278`（timeouts）的 `__atomic_fetch_add(&field, 1, RELAXED)` → 将累加移入各自的 `irt_seqlock_write_end()` 之前、写锁保护区内，用普通 `field += 1`。
  - writes：当前 `:80 fence` → `:81 write_end` → `:82 fetch_add`。改为 `:80 fence` → `stats.writes += 1` → `:81 write_end`。
  - timeouts：当前 `:276 fence` → `:277 write_end` → `:278 fetch_add`。改为 `+= 1` → `write_end`。
- 正确性依据：
  1. **写者已串行**：两处均在 `irt_seqlock_write_begin`（`:43`、`:256`）取得的写锁内，同一时刻仅一个写者，普通 `+=` 无写-写竞争。
  2. **读者安全**：读端 `irt_pm_write_count`（`:200-202`）与 `:797` 用 `__atomic_load_n`；即使读到撕裂值，统计字段是纯诊断用途（验收判据不依赖精确值），可接受瞬时不精确；如需更强保证，读端可用 seqlock 读重试（评估后定，非必须）。
  3. **CRC 安全**：`stats` 被 `irt_header_crc32_of` 刻意排除（`irt_shm.c:41-43`），锁内修改不触发 attach CRC 校验失败。
  4. **对齐安全**：普通 `+=` 编译为 `ldr/str`，AArch64 普通访存支持非对齐，规避 8 字节原子对齐要求。
- 零 ABI/布局/公开 API/协议变更；Linux 侧行为等价（仅统计发布时序从"锁后"移到"锁内"，诊断字段不受影响）。

**备选方案与不取理由**：
- B. CAS 循环替换 fetch_add：8 字节 CAS 同样要求对齐，非对齐字段（偏移 28/36）风险未消除；G1 中对齐的 write_seq CAS 成功不能外推到非对齐字段。不取。
- C. 编译选项 `-mno-outline-atomics` 或 `-march=armv8.1-a`（LSE，实测该选项已生成内联 `ldadd`/`casal`）：汇编实证可消除 out-of-line helper，但① 内联 `ldadd`/LL-SC 对非对齐地址仍明确 alignment fault，未解根因；② 影响全库原子语义、风险面大；③ 需改工具链配置，超出 bugfix 最小面。不取为主方案，可作为方案 A 的补充验证项。
- D. 把 `stats.writes/timeouts` 改 32 位或调整偏移到 8 对齐：改 Header 布局 → 段版本变更 + ABI 破坏（`CODEBUDDY.md:157`），禁止。
- E. SylixOS 原生 `Lw_Atomic64_Add`：底层 `ldxr/stlxr` 已确认可用（`arm64_atomic.h:151-176`），但仍要求 8 字节对齐且 `atomic64_t` 有 `aligned(8)` 属性，与非对齐字段不兼容；引入平台条件编译破坏核心库可移植性。不取。

**验证策略（双轨）**：
1. Linux 侧：`check_all.sh` full ALL GREEN（53/53 + 9 守卫）、ON 60/60 零回归；`write_count` 相关单测保持通过。
2. SylixOS 侧：用既有 toolchain 交叉编译，ftp 上传 `/tmp` 同名 harness（G1 已验证工具链/平台 ARM64_GENERIC），telnet 重跑 CASE 1-4，要求 4/4 PASS 且 `exit 0`；清理临时段/文件。
3. 故障注入：构造多进程并发写（fork 2+ 进程各写 N 次），验证 `write_count` 无崩溃且计数单调递增、等于各进程写入次数之和（写锁串行下应精确，无丢失）。
