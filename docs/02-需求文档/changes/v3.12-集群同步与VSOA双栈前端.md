## 问题与影响

InduRTDB 当前只能单机跨进程共享内存读写，`rtdbd` 对外仅有 UDS 二进制协议，出不了本机。现场 6 台 PLC 设备各跑一个服务，服务只连本机 `127.0.0.1` 且可能写库；设备挂掉后服务整体迁移到另一台设备继续读写；每个节点都要持有全量点表并把本地写同步给其余节点。不做的后果：迁移后读到的是空/旧数据，多节点数据互不收敛，无法满足「像 Redis 一样的独立可执行服务」目标。

影响面：新增 VSOA 对外通道、**运行时集群成员配置接口**、`rtdbd` 传输解耦层与 `rtdbd_session_t`、可加的公开 C API、`sync:` 配置段与 CLI 观测面、IR1–IR7 共 7 类集成用例；**不改动共享内存布局、既有 22 个 UDS opcode 一字不改（尾部可加 `OP_SET_PEERS(23)` / `OP_GET_PEERS(24)`）、`libindurtdb.a` 依赖面零改动**。

## 设计决策

权威裁决见 `docs/03-设计文档/13-2026-11-06-集群同步边界与假设裁决.md`：**D1–D10 为返工前基线，7 题重裁后的正式方案是 §9**（§10 为 POC 清单，**2026-11-07 用户裁决拆 A/B 两段，见 §10.2**）。本节要点按 §9 同步：

- 推翻 D1，集群同步纳入本库边界；全对等 active-active，所有节点可写、无主从、无从库拒写。
- 按服务分区写，冲突只在迁移窗口：用 `service_id + epoch` 纪元隔离 + 建连追平屏障，不用 LWW / CRDT / 物理时钟。
- 每 origin 一条 `(node_id, boot_id, offset)` 增量流；全量快照无停顿流式 + 固定 backlog；默认异步 + 可选 `WAIT`。
- 传输采用 VSOA；对外格局为**双栈过渡**（UDS 保留、VSOA 镜像首批 10 组能力 / 13 个 opcode，客户端逐步迁移），UDS 不预设下线时间。
- 首批只做 PLC 服务数据面；运维管控、监控台仍走 UDS。
- 抽出 `rtdbd_dispatch()` 与传输解耦，先建 `rtdbd_session_t` 传输无关会话 + 延迟动作队列，UDS / VSOA 各挂一层适配，共享同一套业务语义与写权威路径。
- **7 题重裁新增（§9）**：① VSOA 前端为 v3.12 现场主写入口，`service_id/epoch/WAIT` 走建连握手，UDS 退为 legacy 且不参与纪元隔离；② `/sync/delta` 走 RPC 批次 + reply 即 ack、快照走分页 RPC、禁用 quick channel；③ 单线程统一 `poll` 事件循环 + 每轮预算 + 符号级 checker；④ `role=plc/sync_peer/sync_admin` 隔离，业务写复用 `irt_policy_allows` deny-by-default；⑤ `NOTIFY`/`SNAPSHOT_DONE` 逐连接 `cli_datagram` 定向，禁用 publish；⑥ `SET_PEERS` 整组替换运行时下发对端 IP（成员事先不可知）；⑦ 稳态按 origin offset 流式应用、终态由全量快照定稿，多数派门控 + boot_id 摘要校验 + 冷启动权威源。
- 备选与否决理由：主备单写者（与现场全节点可写冲突，已撤回）；纯自研 UDS/TCP（用户明确要求 VSOA，已撤回）；静态库链 VSOA（污染 `find_package`/`pkg-config`/`FetchContent`，否决）；sidecar 独立进程（多一跳与一套生命周期，未选）。
