# 05 · v1 → v2 API 迁移指引

**版本**：1.0 ｜ **日期**：2026-10-08 ｜ **基线**：v3.8

面向仍在使用 **v1 全局单例 API** 的集成方。

---

## 0. 一句话结论

> **存量 v1 代码零改动即可运行。** v1 的 62 个函数全部保留，行为未变。
> 但 v3.8 起**错误码语义变了**（见 §4）——这是升级后唯一需要留意的地方。

---

## 1. 两个版本号：段版本 ≠ API 版本

这是最容易混淆的一点，先说清楚：

| 维度 | 当前值 | 含义 | 升级影响 |
|---|---|---|---|
| **API 版本** | v1（全局函数）/ v2（`indurtdb_h_*` 句柄） | 调用方式 | v1 全保留，**零改动可继续用** |
| **共享内存段版本** | **3** | `/dev/shm/indurtdb_*` 的二进制格式 | v3.9 起为 3（v3.4–v3.8 为 2）；**段版本不匹配一律拒绝挂载** |
| 库版本 | 3.9.0 | 产品版本 | — |

**段版本是硬边界**：跨段版本升级（v3.3 → v3.4+、v3.4–v3.8 → v3.9+）必须停机迁移或重建，
**不支持新旧进程混跑**。段迁移用 `tools/irt_migrate`（见 §6）。

---

## 2. v1 API 现在是什么状态

| 事实 | 说明 |
|---|---|
| **全部保留** | 62 个 v1 函数一个都没删 |
| **全部标 deprecated** | 头文件中 55 处 `INDURTDB_DEPRECATED` 标记，编译会出告警 |
| **实现是薄封装** | 每个 v1 函数等于「用默认句柄 `g_default` 调一次 `indurtdb_h_*`」 |
| **移除计划** | **v4.0** 移除；过渡期充足，当前无需紧急迁移 |

因此**不做任何改动也能继续跑**，只是编译告警会变多。

---

## 3. 需要迁移吗？判断标准

| 你的情况 | 建议 |
|---|---|
| 单实例、单进程读写 | **不必迁**。v1 够用，等 v4.0 再说 |
| 一个进程要管多个 `instance_id` | **必须迁** —— v1 是单例，同时只能持有一个实例（见 §5） |
| 需要按名查找 / 元数据 / 批量范围读写 | **迁** —— 这些能力只在 v2 有句柄形态（`find_by_name` / `get_meta` / `write_range_*`） |
| 已经用 `rtdbd` 走读写分离 | **迁** —— 客户端库 `irtcli` 面向 v2 设计 |
| 只是想消掉编译告警 | 加 `-DINDURTDB_NO_DEPRECATE_WARN` 可静音，但那是**掩盖**不是迁移 |

---

## 4. ⚠️ 错误码语义变化（v3.8 起）——这是唯一需要改代码的地方

v3.8 修正了写路径的错误码契约。**存量 v1 代码不改也会编译通过、运行正常**，
但如果你的代码**依赖了旧的返回值**，就会受影响。

### 4.1 具体变化

| 场景 | 旧行为 | 新行为 | 影响 |
|---|---|---|---|
| Seqlock 写冲突 | 立即返回 `-2`，**不重试** | 库内重试 3 次；耗尽返回 **`INDURTDB_ERR_BUSY(-5)`** | 丢写率由 ~50% 降至 <2%；返回值号变了 |
| 只读点位拒写 | 返回 `-3` | 返回 **`INDURTDB_ERR_READ_ONLY(-6)`** | 语义码不同 |
| `write_*` 内部映射 | -2 与 `-2` 混用 | 已统一到对外语义码 | — |

> 此前内部 `-2`（写冲突）恰好等于对外的 `ERR_NOT_FOUND`，`-3`（只读拒写）
> 恰好等于 `ERR_FULL`。调用方无法按文档区分「忙 / 只读 / 越界」。已修正。

### 4.2 最容易踩的坑

**如果你之前这样写重试循环：**

```c
int rc = indurtdb_write_double(id, v);
while (rc < 0) {              /* ❌ 把所有错误都重试 */
    rc = indurtdb_write_double(id, v);
}
```

那么升级后它**开始重试「只读点位拒写」**（`-6`）——白烧 CPU 与延迟预算。

**正确写法**（只对 BUSY 重试）：

```c
int64_t deadline = now_ns() + 100 * 1000 * 1000;   /* 100ms 预算 */
for (;;) {
    int rc = indurtdb_write_double(id, v);
    if (rc == 0) break;
    if (rc != INDURTDB_ERR_BUSY) break;            /* 其他是真实错误，退出 */
    if (now_ns() >= deadline) break;               /* 预算耗尽，放弃 */
    sched_yield();
}
```

注意**按截止时间**重试而非固定次数：全局单 seqlock 下无界竞争中，
固定 N 次重试必有残余尾部；按时间重试才能同时保证「零丢写」与「延迟有上界」。

### 4.3 错误码对照表

| 宏 | 值 | 含义 | 可重试 |
|---|---|---|---|
| `INDURTDB_OK` | 0 | 成功 | — |
| `INDURTDB_ERR_ARG` | -1 | 参数非法（空指针、空名、越界 id） | ✗ |
| `INDURTDB_ERR_NOT_FOUND` | -2 | 按名未找到点位 | ✗ |
| `INDURTDB_ERR_FULL` | -3 | 索引/表已满，无法注册 | ✗ |
| `INDURTDB_ERR_NOT_INIT` | -4 | 未初始化 | ✗ |
| `INDURTDB_ERR_BUSY` | -5 | 并发写冲突，重试耗尽 | ✓ |
| `INDURTDB_ERR_READ_ONLY` | -6 | 只读点位禁止写入（SRS §4.3） | ✗ |

> `INDURTDB_ERR_READ_ONLY(-6)` 为 v3.8 新增，纯追加，向后兼容。

## 5. v1 的硬限制（这才是该迁的理由）

### 5.1 单进程单例

同一进程内 `indurtdb_initialize()` 只能持有一个实例，切换必须先 `shutdown()`。
**v2 用句柄彻底解决**：

```c
indurtdb_t *a = NULL, *b = NULL;
indurtdb_cfg_t cfg;
cfg.max_points = 10000;
cfg.max_subscribers = 32;

indurtdb_h_open(&a, "instance_a", &cfg);
indurtdb_h_open(&b, "instance_b", &cfg);   /* 同一进程，两个实例并存 */

indurtdb_h_write_double(a, 1001, 23.5);
indurtdb_h_write_double(b, 1001, 99.9);   /* 互不影响 */

indurtdb_h_close(a);
indurtdb_h_close(b);
```

### 5.2 `peek()` 单拷贝（两个版本都适用）

数据经 Seqlock 拷到**线程本地缓冲**后返回其指针，**同线程下次 `peek()` 即覆盖**。
需长期持有请用 `indurtdb_read_point()` 拷到自管理缓冲。**这在 v2 中同样成立，不是迁移能解决的问题。**

## 6. 段迁移（跨段版本升级必做）

与 API 迁移是两件不同的事：`irt_migrate` 搬的是**共享内存段数据**，不是调用代码。

```bash
# v1 段 src_id → 当前版段 dst_id（源段保留；dst 已存在需 --force）
python3 -m irt_migrate migrate --src <src_id> --dst <dst_id> \
    [--source-ts-mode zero|keep] [--force]

python3 -m irt_migrate check --src <src_id>     # 先检查再迁
```

| 项 | 处理 |
|---|---|
| 点位值 / 类型 / 质量 / 入库时刻 | 逐字节搬运（v1/v2/v3 点位同为 128B，偏移不变） |
| 点位名 | 搬运，并在目标段内**重建 name→id 索引** |
| 点位 `partition`（v3.9 新增） | v1 源段无此字段 → 全部落**默认分区 0** |
| 采集时刻 `source_timestamp_ns` | 默认置 0（`--source-ts-mode keep` 可保留） |
| 元数据区（v2 新增） | 清零 |
| 订阅者心跳区 | 清零（离线迁移，由新 `rtdbd` 重建） |

详见 `tools/irt_migrate/README.md`。

## 7. 无 v2 对应物的 v1 函数（14 个）

多数是**纯函数/无状态**，不需要句柄，v2 形态就是它本身：

| 函数 | 说明 |
|---|---|
| `indurtdb_value_to_double` | 6 种数值类型归一化（纯函数） |
| `indurtdb_eurange_limit` | 计算量程位 LOW/HIGH/NONE（纯函数） |
| `indurtdb_deadband_exceeded` | 绝对/百分比死区判定（纯函数） |
| `indurtdb_quality_to_status_code` | OPC UA StatusCode 映射（纯函数） |
| `indurtdb_status_code_to_quality` | 反向映射（纯函数） |
| `indurtdb_quality_is_usable` | quality 可用性判定（纯函数） |
| `indurtdb_meta_pct_without_range` | 百分比死区缺量程基准的提示（纯函数） |
| `indurtdb_validate_point_meta` | 点位元数据校验（纯函数） |
| `indurtdb_validate_config` | 配置批量校验（纯函数） |
| `indurtdb_cfg_error_reason` | 错误码转文本（纯函数） |
| `indurtdb_get_last_error` | 线程局部错误串，见下方 ⚠️ |
| `indurtdb_initialize` / `indurtdb_shutdown` | v2 对应 `indurtdb_h_open` / `indurtdb_h_close` |
| `indurtdb_detach` | ⚠️ **v2 暂无对应函数**，见下 |

### ⚠️ 两个已知缺口

**① `detach` 无 v2 对应物。** `indurtdb_detach()` 用于「放弃接管但保留段」
（fail-fast 退出场景：数据不因本次退出而销毁，下次启动仍能 attach）。
v3.7 新增它是为修 rtdbd 的 fail-fast 路径（此前用 `shutdown()` 会因 owner 语义
删除整段，把「配置写错」升级为「数据销毁」）。**v2 句柄暂无等价能力**，
多句柄场景需自行处理。属待补项。

**② `get_last_error` 是线程局部全局，不是 per-handle。**

```c
static _Thread_local char g_last_error[256];
```

它按线程隔离，但**同一线程内的多个句柄共享**。多句柄并发场景下，
拿到 `ERR_BUSY` 后读 `get_last_error()` 可能读到**另一个句柄**的错误描述。

**建议**：多句柄场景**以返回码为准**判断错误类型，`get_last_error()` 仅作
日志辅助，不要用它做控制流。**待补项**：per-handle 错误缓冲。

## 8. 迁移检查清单

- [ ] 确认是否真的需要迁（§3 判断标准）—— 多数单实例场景可以不动
- [ ] 若代码有 `while (rc < 0)` 式重试循环，按 §4.2 改为只重试 `BUSY`
- [ ] 若跨 v3.3 → v3.4+：停机、用 `irt_migrate` 迁段（§6）
- [ ] 若需多实例：改用 `indurtdb_h_open` + `indurtdb_h_*`（§5.1）
- [ ] `peek()` 的结果不要跨调用持有，长期持有用 `read_point()`（§5.2）
- [ ] 跑 `bash scripts/verify_deploy.sh --prefix <prefix>` 确认安装与运行正常
