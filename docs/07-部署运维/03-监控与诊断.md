# 03 · 监控与诊断

## 1. 健康检查

### 段自检 API（库侧）

返回类型是 **`int`**，返回下列宏之一（`include/indurtdb/indurtdb.h:359-361`）：

```c
int st = indurtdb_h_self_check(h);      /* v2 句柄，推荐 */
int st = indurtdb_self_check();         /* v1 薄封装，已标 DEPRECATED */
```

纯读校验共享内存段头的 `magic` / `version`：

| 宏 | 值 | 含义 |
|---|---|---|
| `INDURTDB_HEALTH_OK` | 0 | 段头完好 |
| `INDURTDB_HEALTH_DEGRADED` | 1 | **核心 self_check 当前不产出**，预留给调用方分层 |
| `INDURTDB_HEALTH_UNHEALTHY` | 2 | `magic` 或 `version` 不符 |

> v1 的 `indurtdb_self_check()` 已标注 `INDURTDB_DEPRECATED`（v3.7 B5），新代码用 v2 句柄版本。

### rtdbd 健康快照（协议侧）

opcode `RTDBD_OP_HEALTH`（= 16）：**只读、免鉴权**（与 `GET_LOG` 同级，负载仅计数与连接数，不含点位值）。

> ⚠️ **协议主版本仍为 2**，仅新增 opcode，不 bump 版本。既有 v3.6 monitor 行为完全不变。

健康判定使用 **60s 滑动窗口**：`DEGRADED` 可自愈，避免一次瞬时误请求让进程余生永久告警。

## 2. 运行统计

rtdbd 内置定长计数器单例（`rtdbd/src/stats.{h,c}`，零堆分配）：

| 计数器 | 含义 |
|---|---|
| `n_writes` | 成功写入数 |
| `n_notifies` | 通知投递数 |
| `decode_fail` | 报文解码失败 |
| `write_rejected` | 写被拒（越界 / 只读 / 鉴权不过） |
| `write_error` | 写入错误 |
| `notify_drop` | 通知丢弃（队列满丢最旧、连接关闭、flush 失败） |
| `notify_send_fail` | 发送失败 |
| `uptime_ns` | 运行时长 |
| `health` | 健康状态 |

### SIGUSR1 dump

```bash
kill -USR1 $(cat /run/rtdbd/hvac_ahu01.pid)
cat /tmp/rtdbd.stats          # 或 --stats-file 指定的路径
```

> **信号安全**：处理器只置 `volatile sig_atomic_t` 标志，实际 dump 在主循环执行。

### 告警基线建议

| 指标 | 建议阈值 | 动作 |
|---|---|---|
| `health == DEGRADED` | 持续 > 60s 滑动窗口 | 告警（瞬时抖动不触发） |
| `notify_drop` 速率 | > 0 持续 1 分钟 | 订阅端消费不过来，排查慢消费者 |
| `decode_fail` | > 0 | 客户端协议版本不匹配 |
| `write_rejected` 突增 | 环比 > 5x | 鉴权策略过窄或客户端 bug |

## 3. 背压行为

每连接出站队列为 `outq[64]` 定长环形缓冲，嵌入 `rtdbd_conn_t`，**零堆分配**。

| 情况 | 行为 |
|---|---|
| 队列有空间 | 写入成功即入队；主循环仅在 `outq_count > 0` 时监听 `POLLOUT` |
| 队列满 | **丢最旧（保序）**并计 `notify_drop` |
| `POLLOUT` 就绪 | `outq_flush` 用 `MSG_DONTWAIT` + `outq_sent` 做部分发送 |
| 连接关闭 / flush 失败 | 待发队列计入 `notify_drop` |

> `POLLOUT` 就绪只保证套接字缓冲有**部分**空间。若沿用阻塞 `send_all`，嵌入式小缓冲下单线程服务端会被卡死——这是刻意规避的 head-of-line 阻塞。

**`notify_drop` 持续增长 = 订阅端消费能力不足**，是容量规划的直接信号。

## 4. 诊断工具

### irt_diag

纯 Python（stdlib only）+ C harness，覆盖段巡检、端到端冒烟、fd 泄漏检测。详见 `tools/irt_diag/README.md`。

```bash
# 巡检段健康（version / 点数 / CRC / owner pid）
python3 -m irt_diag.cli inspect --id <instance_id>

# 冒烟：起服务 → 写 → 读 → 订阅 → 停（需先构建 harness）
python3 -m irt_diag.cli smoke --harness <path>/irt_diag_harness --id <instance_id>

# fd 泄漏检测：反复启停 N 轮比较 fd 计数
python3 -m irt_diag.cli leak --harness <path>/irt_diag_harness --id <instance_id> --cycles 20
```

退出码：`inspect` 0=健康 / 1=不健康 / 2=段不存在；`leak` 0=无泄漏 / 3=检测到 fd 增长 / 2=无法判定。

> `inspect` 的 CRC 覆盖区间与 `irt_header_crc32_of` 逐字节一致（`[0:16] + [48:72]`）；`scan_skipped` 位于保留区 `[76:80]`，不计入 CRC，运行时自增不影响巡检。

### 长稳与故障注入

```bash
bash scripts/run_soak.sh                 # 默认 10s；SOAK_DURATION=30 可延长
bash scripts/run_e2e.sh
bash scripts/run_bench.sh --quick        # P50/P99/吞吐
```

`run_soak.sh` 验证多进程持续读写数据完整性、owner 崩溃接管、奇数 `write_seq` 恢复，并清理 `/dev/shm` 残留。

## 5. Web 监控台

`tools/rtdb-monitor/`，后端 FastAPI，经 UDS 连 rtdbd。

```bash
cd tools/rtdb-monitor
pip install -r requirements.txt

export RTDBD_SOCK=/run/rtdbd/default.sock
export RTDB_MONITOR_TOKEN=secret          # 可选：设置后需 token 鉴权

python3 -m uvicorn app:app --host 127.0.0.1 --port 8080
# 浏览器打开 http://127.0.0.1:8080
```

支持：枚举全部点位、实时值推送、按名/id 查看、设置点位值。

> `RTDB_MONITOR_TOKEN` 走的是**监控台自身**的 token 鉴权，与 rtdbd 的 uid 策略（`--policy`）是两套机制。生产环境务必设置 token 并只监听回环地址。
