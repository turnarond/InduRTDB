# 04 · 故障排查与升级

## 1. 常见故障速查

| 现象 | 可能原因 | 处置 |
|---|---|---|
| rtdbd 启动正常但**所有写被拒** | 未传 `--policy`，或策略为空 / 规则与对端 uid、id 区间不匹配 | 核对 `--policy` 路径；确认规则已生效（见 §1.1） |
| 退出码 **1** | 参数非法 / socket 创建失败 | 检查 stderr 与参数取值 |
| 退出码 **2** | 配置校验失败（含 `--policy` 文件非法） | 核对 `eur_min < eur_max`、`deadband >= 0`、百分比死区 ∈ [0,100]、`flags` 无未知位；policy 非法时 stderr 给出 `invalid policy ...: line <n>: <原因>` |
| 退出码 **3** | 共享内存段损坏或初始化失败 | 段头 magic/version 不符；确认是否误用旧版本工具访问新段 |
| 退出码 **4** | 启动自检失败 | 同 3 |
| 进程反复重启 | 退出码 2/4 被 supervisor 无限重启 | 配置 `RestartPreventExitStatus=2 4`，让坏配置暴露而非掩盖 |
| `write_*` 返回 **BUSY(-5)** | Seqlock 写冲突，库内重试已耗尽 | **正常行为，非错误**。按截止时间重试，见 §1.2 |
| `write_*` 返回 **READ_ONLY(-6)** | 只读点位拒写（SRS §4.3） | 配置里该点位 `access: 1`，检查是否配错 |
| `peek()` 读到的值莫名被改 | `peek` 是**单拷贝**，同线程下次调用即覆盖 | 改用 `read_point()` |
| 订阅端收不到 `NOTIFY` | 写入方**绕过了 rtdbd 直写共享内存** | 写必须经 rtdbd；直写不产生通知（写权威唯一） |
| `notify_drop` 持续增长 | 订阅端消费慢于生产 | 扩队列或优化订阅端；该指标是容量规划的直接信号 |
| SIGUSR1 后无 dump | `--stats-file` 路径不可写 / 路径变更 | 核对路径与权限 |
| 升级后 attach 失败 | **段版本不兼容** | 见 §3 |

### 1.1 确认鉴权策略真的生效

policy 文件格式非法时 rtdbd **启动即失败**（退出码 2，stderr 含
`invalid policy <path>: line <n>: <原因>`），不再静默跳过。因此「进程活着」不等于
策略正确——需确认规则内容本身是否覆盖了对端 uid 与 id 区间。快速自查：

```bash
# 规则应为 uid:partition|*:min:max 四段十进制；统计非注释非空行数
grep -vE '^\s*(#|$)' /etc/rtdbd/policy.conf | wc -l
```

若该值为 0，等同"拒绝所有写"。

### 1.2 写冲突的正确重试范式

库内已对 seqlock 冲突做有限重试（把 2 线程丢写率从 **~50% 降到 <2%**）。剩余的少量
`INDURTDB_ERR_BUSY(-5)` 是**合法返回**，调用方需自行重试。

**固定「重试 N 次」不是正确范式。** 全局单 seqlock 下，N 次有界重试在无界竞争中仍会被耗尽
（实测 4 次在 4 线程争抢下仍漏 1/1000）。正确做法是**按截止时间重试**：

```c
/* 只对 BUSY 重试；ARG / READ_ONLY / NOT_INIT 等是真实错误，重试无意义 */
int64_t deadline = now_ns() + 100 * 1000 * 1000;      /* 100ms 预算 */
for (;;) {
    int rc = indurtdb_h_write_double(h, id, value);
    if (rc == INDURTDB_OK) break;
    if (rc != INDURTDB_ERR_BUSY) break;               /* 真实错误，退出 */
    if (now_ns() >= deadline) break;                  /* 预算耗尽，放弃 */
    sched_yield();
}
```

重试次数自适应竞争强度，而**总延迟有上界** —— 这才是实时系统要的。

> 该范式在 `tests/unit/test_c_concurrency.cpp` 的
> `CConcurrency.ConcurrentWriteHighContentionNoDroppedWrites` 中经实测验证：
> 4 线程争抢同一点位、1000 次写**零丢失**。集成方可直接照抄。
>
> **实测中踩过的坑**：若只按 `rc < 0` 粗略重试，会把 `ERR_READ_ONLY`（只读点位）
> 也重试一遍，白白浪费预算。必须比对 `INDURTDB_ERR_BUSY` 精确判断。
>
> 注：真实部署中写经 rtdbd 串行化，不会出现测试里这种同点争抢，冲突率极低。

## 2. 残留与自愈

| 项 | 行为 |
|---|---|
| owner 崩溃 | attach 方通过 `kill(pid, 0)` 存活检查发现 owner 已死，调用 `irt_shm_os_claim_ownership()` 接管 |
| Seqlock 奇数恢复 | attach 时若发现遗留奇数 `write_seq`（写锁内崩溃），自动推进到偶数恢复一致性 |
| fork 安全 | `owner_pid != getpid()` 判定子进程，先清 `os.owner` 再 shutdown，避免子进程 `shm_unlink` 误删父进程段 |

### 手动清理残留段

测试/崩溃后可能留下 `/dev/shm/indurtdb_*`：

```bash
ls -la /dev/shm/indurtdb_*
rm -f /dev/shm/indurtdb_*        # 确认无进程占用后再删
```

> **owner 判定使用 `O_EXCL` 原子创建**，不依赖 `st_size == 0`，因此残留段不会造成"误判 owner"；但段内容可能是陈旧的，排查异常时仍应清理。

## 3. 版本升级与 ABI 边界

### ⚠️ v3.4 是硬边界

**v3.4 将共享内存段版本从 1 升到 2，v1 段拒绝挂载。**

| 项 | v3.3 及更早 | v3.4 及以后 |
|---|---|---|
| `irt_header_t` 大小 | 64 B | **128 B** |
| 段结构 | Header + 点位 + 心跳（线性） | **四区段**，偏移由 Header 的 `off_*` 给出 |
| Header 新增 | — | `crc32`、`flags`、`off_points/off_index/off_meta/off_subs`、`index_count`、`scan_skipped` |
| 兼容方向 | — | **v1 段拒绝挂载** |

**结论：v3.3 与 v3.4+ 无法共用同一个共享内存段。跨此边界升级必须停机。** 配套迁移工具为 `irt_migrate`。

### ⚠️ v3.9 是第二个硬边界

**v3.9 将共享内存段版本从 2 升到 3（`IRT_SHM_VERSION` 2 → 3），v2 段拒绝挂载，v3 段也被 v3.8 及更早拒绝。**

点位布局仅一处语义变更：偏移 **120..123** 处由 `reserved[0:4)` 更名为 `uint32 partition`，`sizeof(indurtdb_point_t)` 仍为 **128 字节不变**。随之 name→id 索引键由 `name` 变为 `(partition, name)`。除此之外，128B 段头与点位其余字段在 v2 / v3 间**逐字节相同**。

| 项 | v3.4–v3.8 | v3.9 |
|---|---|---|
| 共享内存段版本 | 2 | 3 |
| 点位偏移 120..123 | `reserved[0:4)` | `uint32 partition` |
| `sizeof(indurtdb_point_t)` | 128 | 128（不变） |
| name→id 索引键 | `name` | `(partition, name)` |
| 兼容方向 | — | **互不挂载** |

配套迁移工具为 `tools/irt_migrate`（支持 v1→v3 与 v2→v3），用法与不变式见 [`tools/irt_migrate/README.md`](../../tools/irt_migrate/README.md)。

> v2→v3 迁移语义：点位值 / 类型 / 质量 / `timestamp_ns` / `name` / `access` / `unit` 逐字节搬运；`source_timestamp_ns` 默认置 0（`--source-ts-mode keep` 可保留）；`partition` 强制为 0；name→id 索引按分区键重建；v2 元数据区（32 B/点）原样保留；订阅者心跳区清零；段头版本改写为 3 并重封 CRC32。

### v3.10：非段版本边界，但旧段仍需删除

**v3.10 不升 `IRT_SHM_VERSION`（仍为 3），`indurtdb_point_t` 仍为 128 B，协议主版本仍为 2**；
新增 opcode `SET_SUBS=18`、NOTIFY 质量字节与 `--timeout-ms`。

但 rtdbd 初始化时把段内 `max_subscribers` 固定为 **128**（`RTDBD_MAX_CLIENTS`），而 v3.9.x
及更早版本按旧 `--max-subs` 写入（默认 32，常见值 32/64）。`irt_shm_attach` 会拒绝“现有槽位小于请求槽位”的旧段，
因此**不能直接复用旧段**。`--max-subs` 在 v3.10 的含义也已变为“每连接订阅点位上限”。

升级步骤：

```bash
# 1. 停 rtdbd（正常 SIGTERM 会 shm_unlink 旧段）
systemctl stop rtdbd

# 2. 确认旧段不存在；若 kill -9/崩溃残留，手动删除
ls -l /dev/shm/indurtdb_<instance>
rm -f /dev/shm/indurtdb_<instance>

# 3. 用新参数启动（示例：2 万点、每连接最多 1024 订阅）
rtdbd --instance <instance> --socket /run/rtdbd/<instance>.sock \
      --policy /etc/rtdbd/policy.conf --config /etc/rtdbd/points.yaml \
      --max-points 20000 --max-subs 1024 --timeout-ms 0

# 4. 验证
python3 scripts/check_rtdbd_health.py -s /run/rtdbd/<instance>.sock
bash scripts/run_e2e.sh
```

> 停机后点位当前值丢失，启动时由 `--config` 重新加载；运行时创建/修改的点位需
> `--delta-file` 才能跨重启保留。升级前若需保留值，按上文“运行中先备份”做段快照，
> 但**不要恢复旧段到 v3.10**——只用于回滚或迁移取数。

**兼容矩阵**

| 客户端 / 服务端 | v3.9.x rtdbd | v3.10 rtdbd |
|---|---|---|
| v3.9.x 监控台 | 原行为 | 逐点 `SUBSCRIBE` 仍可用；无分页/批量快照 |
| v3.10 监控台 | 探测失败 → legacy 32 点/页；`UNSUBSCRIBE`+`SUBSCRIBE` 替换 | 完整 `SET_SUBS`、当前页订阅、质量推送、服务端分页 |
| v3.9.x SDK / irtcli | 原行为 | 原 opcode 全部兼容；忽略 NOTIFY 质量字节 |
| v3.10 SDK | `probe_set_subs()` 返回 false；退回逐点订阅 | 完整 `set_subs` / quality 解析 |

### ⚠️ 停机即删段：迁移前必须先备份

**`rtdbd` 正常退出（SIGTERM）会触发优雅关闭，调用 `indurtdb_h_close()`；后者作为段 owner 执行 `shm_unlink()`，即共享内存段在正常停机时被从 `/dev/shm` 删除。** 仅部分错误路径（如配置非法）刻意不调用 `indurtdb_h_close`，以保留段。

**因此「停机 → 迁移」不能按字面执行** —— 停机后段已不存在，无段可迁。正确顺序：

1. **rtdbd 仍在运行时**先做段文件快照：`cp /dev/shm/indurtdb_<id> <backup>`
2. 停机
3. 把快照恢复到 `/dev/shm/indurtdb_<id>`
4. 迁移（见 `tools/irt_migrate`）
5. 校验
6. 启动 v3.9 `rtdbd`

> `kill -9`（非优雅退出）**不**执行 `shm_unlink`，段得以保留，但可能遗留 seqlock 写锁（奇数 `write_seq`）。**仅作应急**，正常流程请用「运行中先备份」。

### 升级检查清单

1. 读 `CHANGELOG.md` 确认目标版本的 **ABI / 段版本** 变更
2. 若跨段版本边界：**先在 rtdbd 仍运行时备份段文件**（见上方「停机即删段」警告）→ 停机 → 恢复/迁移 → 升级 → 验证
   - v3.10 是例外：段版本仍为 3，但段内订阅槽位 32→128，不能复用旧段；按上方「v3.10：非段版本边界，但旧段仍需删除」执行
3. **版本号四处同步**：`VERSION`、CMake `project(VERSION)`、`indurtdb.h` 宏、`README`/`CHANGELOG`
4. 执行发布前检查清单：[`06-开发规划/09-文档一致性检查清单.md`](../06-开发规划/09-文档一致性检查清单.md)
5. 升级后跑一次自检：

```bash
python3 -m irt_diag.cli inspect --id <instance_id>
bash scripts/run_e2e.sh
```

> 迁移 + 回退演练证据见 [`08-验证记录/v3.9-T8-迁移与回退演练.md`](../08-验证记录/v3.9-T8-迁移与回退演练.md)。

### 点位容量变更

`--max-points` 决定段布局。**与既有段不一致时行为异常**。需要调整容量应：停进程 → 清理旧段 → 用新 `--max-points` 启动。

> 容量在线扩容（分段增长）尚未实现，属 v4.0 范围。

## 4. 性能基线

设计目标 **P99 ≤ 10 μs**。x86_64 Release `-O2` 实测（v3.7.0）：

| 操作 | P50 | P99 |
|---|---|---|
| `write_int32` | 0.247 μs | 0.255 μs |
| `write_double` | 0.110 μs | 0.113 μs |
| `read_int32` | 0.042 μs | 0.044 μs |
| `peek` | 0.036 μs | 0.038 μs |
| `read_range`（100 点） | 0.234 μs | 0.271 μs |
| `write_range`（100 点） | 1.398 μs | 1.433 μs |

跨进程 UDS 延迟（写请求）：16B 报文 P50 ≈ 11.6 μs / P99 ≈ 18.2 μs；48B 报文 P50 ≈ 12.8 μs / P99 ≈ 24.0 μs。

**改动读/写热路径后必须复测并回填 README**：

```bash
bash scripts/run_bench.sh
bash scripts/run_uds_bench.sh
```

> **热路径零 meta 读**是硬不变式：默认 `write_*` 强制 `quality = GOOD` 且不读点位元数据。语义字段（EURange / 死区）只允许经 rtdbd 的质量感知写入口进入，违反会让 P99 回归。
