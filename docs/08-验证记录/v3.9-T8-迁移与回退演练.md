# v3.9 T8 · 真实 v2→v3 迁移与回退演练

> 任务：v3.9 T8「迁移工具 v2→v3 + 校验 + **回退演练**」。
> 记录一次**在真机 rtdbd 上跑通**的完整升级/回退流程，作为验收证据；不是单元测试的替代。

## 1. 环境与方法

| 项 | 值 |
|---|---|
| 源版本 | `v3.8.0`（tag，commit `5c784b8`，`IRT_SHM_VERSION == 2`） |
| 目标版本 | 当前工作分支 `feature/v3.9-T8-migrate-v2-to-v3`（`IRT_SHM_VERSION == 3`） |
| 工具 | `tools/irt_migrate`（纯 Python，`python3 -m irt_migrate`） |
| 平台 | Linux，`/dev/shm` |
| 段参数 | `--max-points 4096 --max-subs 8`，配置 `config/rtdbd/points.yaml`（11 个具名点位） |

v3.8 在独立 worktree `/tmp/opencode/v38` 构建（`cmake -G Ninja -DCMAKE_BUILD_TYPE=Release`，rc=0），
避免污染主构建树。演练脚本：`/tmp/opencode/t8_drill.sh`，完整日志 `/tmp/opencode/t8_drill.log`。

**方法**：让 **v3.8 的 rtdbd 真正创建并持有 v2 段**（而非 Python 合成夹具），
再用 v3.9 侧工具迁移，最后用 **v3.9 的 rtdbd + irtcli 实读**迁移产物。

## 3. 迁移（v2 → v3）

```
$ python3 -m irt_migrate migrate --src t8drillsrc --dst t8drilldst --force
{ "op": "migrate", ... "source_version": 2, "max_points": 4096,
  "max_subscribers": 8, "index_capacity": 8192, "source_ts_mode": "zero" }
{ "op": "validate", "source_version": 2, "max_points": 4096, "checked": 4096,
  "point_mismatches": [], "index_mismatches": [], "crc_ok": true,
  "index_count": 11, "index_capacity": 8192,
  "partition_all_zero": true, "meta_preserved": true }
migrate exit=0

$ python3 -m irt_migrate info t8drilldst
{ "version": 3, "kind": "v3", ... "index_count": 11, "crc32": "0xc2690aca" }
```

- **全量 4096 点逐字节比对**（`checked: 4096`）：点位不一致 0、索引不一致 0。
- `crc_ok: true`：迁移后 Header CRC 重算一致。
- `partition_all_zero: true`：4096 点 `partition` 全为 0（默认分区）。
- `meta_preserved: true`：v2 元数据区 131072B 逐字节保留。

## 5. 回退演练

### 5.1 v3.8 拒绝挂载 v3 段

```
$ ./build/rtdbd/rtdbd --socket ... --instance t8drilldst ...   # v3.8 二进制
rtdbd: indurtdb_initialize failed: shm init failed
v3.8 挂载 v3 段 exit=3 （期望非 0）
```

v3.8 以退出码 **3**（共享内存初始化失败）拒绝 v3 段——版本协商拒绝生效，
**新版段对旧库不可读**，符合设计 §6「回退：重新部署 v3.8 + 清理段」。

### 5.2 回退后恢复（由保留的 v2 段重迁移）

```
$ rm -f /dev/shm/indurtdb_t8drilldst
$ python3 -m irt_migrate migrate --src t8drillsrc --dst t8drilldst --force
重新迁移 exit=0 ； info t8drilldst → version=3 kind=v3 index_count=11
$ ./build/client/irtcli --sock ... list   → 11 个点位全部恢复
```

**回退方案可行**：只要旧段（或旧段的运行时备份）仍在，即可重新得到可用的 v3 段；
`irt_migrate` 对目标路径是 `O_CREAT|O_RDWR` + `ftruncate` + `mmap` 原地覆写，
**不 `shm_unlink`**，路径/inode 保持不变。

## 6. 重要发现：rtdbd 优雅退出会删除共享内存段

演练中发现一个**影响升级流程**的行为：

```
$ kill <v3.8 rtdbd pid>           # SIGTERM，优雅退出
$ ls /dev/shm/indurtdb_t8drillsrc
ls: 无法访问 '...': 没有那个文件或目录      # 段已被删除
```

- 原因：`rtdbd` 正常退出路径调用 `indurtdb_h_close(g_h)`（`rtdbd/src/rtdbd.c` 收尾处），
  该函数作为 **owner** 执行 `shm_unlink`（`src/osal/posix/irt_osal_posix.c`：
  `irt_shm_os_unmap` 在 `s->owner` 时 `shm_unlink`）。仅**配置校验失败**等错误路径
  刻意不调用 `indurtdb_h_close` 以保留段。
- **影响**：设计 §6 的「停机 → 迁移」若按字面「先停机再迁移」执行，owner 段会随停机消失，
  迁移将无源可迁（数据只能靠 `--config` 重建）。
- **对策（本演练采用的可行流程）**：
  1. rtdbd **仍在运行时**先备份段文件：`cp /dev/shm/indurtdb_<id> <backup>`；
  2. 停机；
  3. 将备份恢复到 `/dev/shm/indurtdb_<id>`（或用 `--dst <new_id>` 事先产出新段）；
  4. 迁移 / 校验；
  5. 启动 v3.9 rtdbd。
  备选：`kill -9`（非优雅退出，不触发 `shm_unlink`）——但会遗留 seqlock 写锁状态，
  仅作应急，不作为标准流程。
- 该行为**非 T8 引入**，v3.8 与 v3.9 一致。是否改为「退出时 `detach` 保留段」属行为变更，
  超出 T8 范围，已在文末列为待裁定项。
