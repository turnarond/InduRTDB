## 4. 600 秒全量负载

```bash
bash scripts/run_station_load.sh --duration 600
```

```text
station-load: points=20000 clients=50 subs/client=500 write-rate=20000/s workers=8 duration=600.0s

结果
==========================================================
写 ACK: 12,000,008 次 / 600.12s = 19,996/s  errors=0  P99=545.4 μs
读帧: min=300,500 median=300,500 max=300,508  client_errors=0
health: n_writes+12,000,008  n_notifies+15,025,016  notify_drop+0
rtdbd pid 564279: RSS 10,184 KB  CPU 362.08s

PASS: notify_drop=0；客户端无断链；帧数达到下限
```

- 写吞吐：`12,000,008 / 600.12 s = 19,996/s`，达到 20k 点 1 Hz 目标。
- 写 ACK P99：`545.4 μs`。这是 50 客户端、20k 写/s 并发下的客户端观测值，含 UDS、
  调度与批量发送开销，**不等同于**设计稿的单点写往返 P99 ≤50 μs 门禁；本轮未用该值
  判定单点延迟指标。
- 每客户端帧数：`300,500 / 300,500 / 300,508`（min/median/max），
  与 `500 点 × 600 s` 一致；50 个客户端全部保持连接。
- `notify_drop=0`，`client_errors=0`，`errors=0`。
- rtdbd RSS `10,184 KB`，低于设计目标 50 MB。

## 6. 本轮修复

### 6.1 50 客户端并发建连丢握手

`rtdbd` 原 `listen(listen_fd, 8)` 的 accept backlog 小于并发读客户端数。50 个客户端
同时建连时握手可能丢失，负载端表现为连接失败或零帧。已改为与连接表容量一致的
`RTDBD_MAX_CLIENTS`（128），见 `rtdbd/src/rtdbd.c`。

### 6.2 负载生成器被 GIL 限制

原负载脚本在单 Python 进程内启动 8 个写线程和 50 个读线程。GIL 使线程无法并行
产生目标写负载，standalone 实测仅约 1.5k 写/s，容易把**负载生成器上限**误判为
**rtdbd 上限**。已改为 8 个写进程 + 50 个读进程，每个进程独立 UDS 连接；同一脚本
即可稳定压出约 20k 写/s。

## 7. 已知偏差与后续

| 指标 | 设计目标 | 实测 | 结论 |
|---|---|---|---|
| 负载下 `notify_drop` | 0 | 0 | 达标 |
| 客户端断链 | 0 | 0 | 达标 |
| rtdbd RSS | ≤50 MB | 10,184 KB | 达标 |
| rtdbd CPU（20k 写/s + 50×500 订阅） | ≤10% 单核 | 362.08 s / 600.12 s ≈ **60.3% 单核** | **未达标，记录为已知性能债** |

CPU 偏差不影响本轮功能验收：吞吐、帧完整性、`notify_drop`、连接稳定性均通过。
后续优化应聚焦广播/发送路径的 syscall 与锁竞争、每连接 flush 策略及事件循环开销；
在优化完成前，部署侧应按约 0.7 个核心为 rtdbd 预留 CPU 余量。

设计文档已同步标注该实测偏差：`docs/superpowers/specs/2026-10-20-v3.10-single-station-scale-design.md`。
