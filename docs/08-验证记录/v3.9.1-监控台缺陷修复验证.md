# v3.9.1 监控台缺陷修复验证

**日期**：2026-10-20
**范围**：`tools/rtdb-monitor` + `rtdbd`（三个缺陷：实时推送静默失效 / 日志未初始化内存 / 点位时间戳时钟源）
**结论**：三处修复均已在真实 `rtdbd` + 真实 FastAPI 服务上复现并验证通过；无协议、段格式与公开 API 变更。

## 复现与修复前后对照

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | WS 连接正常，约 2s 后不再收到任何 `update` | `NotifyListener` socket `settimeout(2.0)`，`_loop` 将空闲超时当作致命 `OSError` 吞掉，监听线程永久退出 | 仅在**帧边界**把空闲超时视为继续等待；前端收到 `list` 后显式 `subscribe` |
| 2 | `/api/logs` 与日志视图出现二进制乱码 | `irt_logbuf_emit` 局部 `msg[116]` 未初始化，`memcpy` 整块入环形缓冲 | `memset(msg, 0, sizeof(msg))` |
| 3 | 点位详情时间显示 `40432/4/16` | `timestamp_ns` 取 `CLOCK_MONOTONIC_RAW`，前端按 Unix epoch 毫秒渲染 | 新增 `irt_time_realtime_ns()`，入库时刻改用 `CLOCK_REALTIME`；`check_timeouts` 同钟 |

## 证据

### 1. 静默 > 2s 后仍收到实时推送

命令（真实 `rtdbd` + `app.py`，UDS + WebSocket）：

```
$ python3 - <<'PY'
# 连接 ws://127.0.0.1:18080/ws → subscribe [0] → sleep 3.5s → POST /api/points/0/set
PY
first: list 2
sub: {'op': 'subscribed', 'ids': [0]}
idling 3.5s ...
push after idle: {'op': 'update', 'pointId': 'temperature', 'id': 0, 'value': '42.5', 'quality': '0', 'ts': 1792483316680733603, 'sourceTs': 0, 'type': 2}
```

修复前同场景：静默 3.0s 后写入，`listener thread alive = False`，`notify = []`。

回归用例已并入 `tools/rtdb-monitor/tests/test_e2e.py`（静默 3.0s 后写值，断言仍收到 `update`）。

### 2. 日志无未初始化残留

```
$ curl -s http://127.0.0.1:18080/api/logs | python3 -c "..."
entries 3
garbled 0
sample ['rtdbd listening on /tmp/webui_rtdbd.sock (instance=web_ui_test)',
        'create point id=0 name=temperature partition=0 (uid=997)']
```

C 侧断言已并入 `tests/integration/test_rtdbd_proto_v2.cpp`（`GetLog`）：`msg` 的 NUL 之后必须全为 `\0`。

### 3. 入库时刻为墙钟

```
ts_ns: 1792483164521601615  wall_ns: 1792483164522638612  delta_s: 0.00103783
```

单测 `tests/unit/test_c_osal.cpp::COsalTime.RealtimeNsIsWallClock`：与 `time(nullptr)` 的差值必须小于 1 天（单调时钟会远超该窗口）。

## 已知取舍

- `timestamp_ns` 与 `check_timeouts` 现在同用 `CLOCK_REALTIME`：墙钟被人工回拨时，超时检测可能产生一次误判（`check_timeouts` 本就是 best-effort）；心跳/订阅超时仍用单调时钟，不受影响。
- 监控台在 `rtdbd` 重启后不会自动重连（需重启 `app.py`），本次未纳入修复范围。
