### 5.1 关键失败/饱和点

- **20k × 5Hz**：`写 ACK 60,000,004 / 600.10s ≈ 99,983/s`，`notify_drop` 三次
  `189,308 / 190,167 / 192,210`；错误 `FAIL: notify_drop=189308（必须为 0）`。
- **20k × 10Hz**：第 1 次 `写 ACK 89,286,902 / 600.13s ≈ 148,779/s`，
  `notify_drop=543,776`；错误 `FAIL: notify_drop=543776（必须为 0）`。
  目标 200k/s 未达到，服务端 CPU 约 99% 单核。
- **200k × 1Hz**：第 1 次 `写 ACK 8,582,058 / 60.13s ≈ 142,720/s`，
  `notify_drop=108,010`；三次 drop 为 `67,128 / 75,620 / 108,010`。
- **200k × 5Hz**：第 1 次 `写 ACK 7,026,306 / 60.15s ≈ 116,818/s`，
  `notify_drop=1,016`；另两次为 0，故 `2/3`。
- **500k × 1Hz**：第 1 次 `写 ACK 7,293,548 / 60.13s ≈ 121,298/s`，
  `notify_drop=0`，但 `读帧 min=146,807 < 291,660`；三次 `n_writes` 约 6.7M–7.4M，
  而非目标 30M。
- **1,000,000 × 1Hz**：`n_writes` 约 6.5M–6.7M，`notify_drop=0`，
  `读帧 min=71,000 / 68,000 / 74,119 < 300,000`；无崩溃、无客户端错误。

### 5.2 结论

1. **2k 全档、20k 1Hz 达标**：目标写率基本达到，`notify_drop=0`，无断链。
2. **20k 5/10Hz 未达 `notify_drop=0` 红线**：写端/通知路径在约 100k–150k 写/s
   时进入饱和；5Hz 约 19 万次丢弃，10Hz 约 54 万次。无崩溃，但属于可观测的背压丢帧。
3. **200k 1Hz 未达 `notify_drop=0`**：目标 200k/s 只跑到约 138k/s，仍出现 6.7–10.8 万
   次丢弃；200k 5/10Hz 的脚本通过只表示“帧数下限 + 无丢弃”，不表示达到目标写率。
4. **500k/1M 的失败是端到端写吞吐饱和导致的帧数下限失败，不是通知丢失**：
   `notify_drop=0`、`notify_send_fail=0`、`client_errors=0`，读帧与实际写入量成正比
   （例如 500k 档实际约 7.3M 写 × 9,722/500,000 ≈ 14.2 万帧，与实测 14.7 万帧一致）。
5. **观测到的端到端写吞吐上限约 100k–150k 写/s**：200k/500k/1M 与 20k 10Hz 均在
   rtdbd CPU 约 95%–100% 单核时饱和；但 10 个 Python 写进程也可能成为瓶颈，本轮未能
   把两者完全隔离。RSS 随点位数增长（41.6 / 98.9 / 193 MB），未观察到崩溃。
6. **批量读加速稳定**：所有档位中位数 6.0×–11.2×，满足设计稿 ≥2× 目标。

## 6. 判定与限制

| 验收项 | 结果 |
|---|---|
| 2k × 1/5/10Hz | **PASS**：9/9，`notify_drop=0` |
| 20k × 1Hz | **PASS**：3/3，19,995 写/s，`notify_drop=0` |
| 20k × 5/10Hz | **FAIL**：`notify_drop>0`；需按背压/容量上限处理 |
| 200k × 1Hz | **FAIL**：`notify_drop>0`；且目标写率未达 |
| 200k × 5/10Hz | **稳定性通过，目标写率未达**；5Hz 有 1 次 1,016 丢弃 |
| 500k/1M | **稳定性通过，目标写率未达**；`notify_drop=0`，无崩溃/断链 |
| 批量接口 | **PASS**：中位数 6.0×–11.2× |

限制：

- 矩阵 JSON 只记录总 `notify_drop`，未单独记录 `notify_drop_live` /
  `notify_drop_snapshot`；`notify_drop_snapshot==0` 由 C++ 测试覆盖，不在本矩阵逐档统计。
- 完整矩阵的 20k 档为 1 个读进程（7,000 订阅）；同 profile（50 客户端 × 500 订阅）
  的 v3.10 对照见 §4.1：吞吐无回退、`notify_drop=0`、CPU +4.0%。
- 未采集写/读负载进程的 CPU，因此“100k–150k 写/s 饱和”是端到端观测值，不能完全
  归因于 rtdbd 或 Python 负载生成器中的任一侧。
- 500k/1M 的“读帧低于下限”由脚本 `min_expected = subs × duration × 0.5` 触发；
  当写端未达到目标写率时，该下限不适用，应看实际写吞吐与 `notify_drop`。
