## 3. 两个制度性前置（2026-11-26 已裁决 → 见《正式发版制度裁决决议》）

> **状态更新**：本节两项前置已由用户裁决——① P7/P8 采用"豁免字段白名单 + 机器判据 + 独立评审"；② P10/P11 采用"rtdbd 内部应用接口 + epoch 栅门、不动 lib API/117"。详见 `docs/plans/2026-11-26-正式发版制度裁决决议.md`。下文为原始待裁决描述，保留作审计。

1. **P7/P8 置 measured 口径**：P7 3/4（缺 `deny_non_loopback`）、P8 5/6（缺 `join_triggers_full`），两字段被判永久 unavailable（server 仅绑 loopback / 无真实 WAL）。机械校验器不验字段名完整性——若裁决"接受字段不全置 measured"，可零代码消掉 FAIL 2；若坚持"字段齐才 measured"，则需改产品绑定/WAL（不划算）。
2. **P10/P11 全量应用路径 vs 既有边界**：此前裁决 S3"逻辑选源不落 shm"、不改 ABI、UDS opcode 冻结；真实跨节点同步要求"全量快照应用到本机点集"，正面冲突。必须先裁决新增何种最小应用接口（不改 UDS opcode/ABI 前提下）。

## 4. 最小正式发版路径与顺序

1. **裁决两项前置**（0.5 人日）。
2. **并行**：P6 + P9（共享计数出口）+ P3（依赖 S2b 页对齐）——约 10–17 人日。
3. **关键路径**：P10（S2b connector → 全量应用 → epoch 落盘 → F3b 注入）→ P11 复用——约 17–28 人日。
4. **收尾**：6 板统一现场 F2/F3a/F4 采集 → B 段 JSON 七项 measured → `check_release_conditions.py` ok=true → `release_gate.py --conditions <台账> <artifact>` EXIT=0 → 正式 tag `v3.12.0` + 用户确认。

## 5. 风险与策略

- **制度风险 > 技术风险**：永久 unavailable 字段 + 字段不全口径 + 自签证据使门归零可能被无限推迟。
- **技术最大风险**：P10 产品语义与"S3 不落 shm"边界冲突；且需 6 板现场窗口配合。
- **策略**：边界版已发，不要再出第二个边界版；直接做大工程是唯一让门归零的路径。
- **不放行纪律**：任一阶段失败即停，不手填假绿；正式 tag 须用户确认。

## 6. 一句话结论

P6/P9/P3 可在约 10–17 人日并行补齐；真正的决定项是 **P10→P11 connector/全量应用大工程**（17–28 人日）与 **P7/P8 measured 裁决**——二者不到位，发布门永不为零。
