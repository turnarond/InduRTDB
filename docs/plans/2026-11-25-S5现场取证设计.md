# S5 现场取证设计（brainstorming 结论）

> 状态：设计确认（2026-11-25，用户逐节确认），待 SDD 变更卡实施。本文是设计，不是开工授权、不是放行。
> 触发：生产发布 FAIL8 闭环 S1–S4 全绿后进入 S5（现场取证）。用户裁决：P10 全场 + P11 的 `machine_restart_pull_full` 在当前产品实现下取不到现场真值（S3 不落 shm、S2 无跨机 connector），**保持 pending、如实标注、不放行**，绝不把 logic-only 改名 measured。
> 责任边界（全程不变）：我建工具 + 核验数据一致性；用户现场执行并对真实性负责；用户指定独立工程师复核签名；我不代签、不碰设备、不填假 measured、不放行、不 tag/合 main。

## 第 1 节：范围与诚实边界

S5 定位：建板载取证程序 + 现场指令文档 + JSON schema/映射 + 回填流程，**明知 P10/P11 部分字段取不到，不强行闭环发布门**。

B 段 7 项可取证性矩阵（S1–S4 后，调研结论）：

| 项 | 可取证性 | 处置 |
|---|---|---|
| P3 | 部分 | `/stats/notify` 给延迟（注明"尝试发出、非确认送达"）；`t3_wall_ms/t3_rss_*/t3_frames/t3_bytes` 无 VSOA 出口 → 标 unavailable |
| P6 | 部分偏不能 | `sub_rebuild_ok` 可局部证；`deferred_ops`/`callback_reconnect_attempts`/`caps_reset_ok` 无计数出口 → 标 unavailable |
| P7 | 部分（限定语义） | `deny_bad_token`/`deny_peer_write`/`admin_set_peers_ok` 可；`deny_non_loopback` 限定为 sync_admin 管控 URL + sync_peer 来源，不泛化 PLC 非 loopback 写 → 口径在 schema 写明 |
| P8 | 部分 | 5 项 peers 可由 `/sync/peers/set|get` 真取；`join_triggers_full` 无真实 WAL/落 shm → 标 unavailable |
| P9 | 部分偏不能 | `peer_notify_leak` 行为级可；`rbe_gate_hits/misses` 无 VSOA URL、`snapshot_done_caps_only` 生产未接线恒 0 → 标 unavailable |
| **P10** | **不能** | 全场 pending：`nodes_converged`/`terminal_hash`/`dict_max_snapshot_match` 无 6 节点落 shm 终态一致链路（S3 不落 shm、S2 无跨机 connector） |
| **P11** | **部分** | `proc_restart_no_fullsync`/`digest_match` 可辅助观测；`machine_restart_pull_full` 依赖跨机 connector + 全量应用 → 整项 pending |

诚实边界：
- 工具输出 JSON 逐字段标来源 `on-site`（现场真取）/ `logic-only`（禁填 measured）/ `unavailable`（禁填）。
- 校验脚本做**映射拦截 + 签名链追溯**：`unavailable`/`logic-only` 字段不得进入台账 measured；脚本不声称工具层硬防手改（手改由执行者真实性声明 + 独立工程师签名链约束，核验报告交叉比对回显日志 ↔ JSON）。
- 台账只从 `on-site` 字段回填；P10/P11 项 fields 保持 `{}`、status `pending`，note 写"现场不可得"原因。
- **发布门不因 S5 变绿**：`check_release_conditions.py` ok=false、`release_gate.py --conditions` 非 0，FAIL 8 维持。

## 第 2 节：工具形态与现场流程

**A. 板载取证程序** `tests/sylixos/s5_forensics.c`（AArch64 交叉编译，复用 G2 VSOA client 模式）：
- 三模式（命令行参数）：`f2`（6 节点状态采集）、`f3a`（1/6/30s 分区观测）、`f4`（重启前后两态）。
- 不依赖 fork / shell 重定向 / 系统库改动；C stdio 自写 JSON 文件；telnet 回显关键行、ftp 回传 JSON。
- 采集来源：现有 VSOA URL（`/health`、`/stats/notify`（仅 PLC hello 可读）、`/sync/peers/get`（sync_admin loopback）、`/point/list`、`/logs`）+ 本地点值读回。
- 逐字段带 `_source` 标记；不可得字段写 `null` + reason，不构造值。
- F2 JSON：`{node_id, epoch, writes, notify_latency_ns, peers, digest, snapshot_epochs, ...}`；F3a：`{partition_duration_s, rbe_gate_hits/misses, stale_epoch_rejected, ...}`；F4：`{epoch_before, epoch_after, subs_restored, peers_restored, digest_match_proc, ...}`。
- 不做跨机同步断言（P10）、不做整机拉全量断言（P11 machine_restart_pull_full）——这两项 JSON 写 `"unavailable"` + reason。

**B. 现场指令文档** `docs/08-验证记录/v3.12-S5-现场取证指令-F2-F3a-F4.md`：
- 六板部署表（IP 仅列：`192.168.30.220/223/224/225/226/227`，凭证不入文档）；ftp 上传 rtdbd + 5 个 VSOA .so + policy/token + 取证程序到 `/root/indurtdb_s5`。
- telnet 双会话（会话1 起 rtdbd、会话2 跑取证）；`LD_LIBRARY_PATH` 会话内赋值（无 export/重定向）；评估版 license 1h 退出提示。
- 每步命令 + 期望输出 + JSON 回传命名（带板 IP + 时间戳）+ 清理段/进程/目录 + 真实性声明模板（执行者签名栏、独立工程师复核栏）。
- F3a 注入手段（拔网线/交换机 ACL）留占位："由执行者现场决定并记录"；stale epoch 帧注入同样现场记录。

**C. 主机侧校验** `scripts/check_s5_capture.py`（带 `--self-test`）：读回传 JSON，校验字段齐全、`unavailable`/`logic-only` 不得映射 measured、on-site 阈值/来源合法；输出核验报告（我核数据一致性）。

## 第 3 节：字段映射、回填流程与验证

**A. JSON → B 段映射表** `docs/08-验证记录/v3.12-S5-capture-schema.md`：逐字段列 `JSON 路径 → B段字段 → 来源标记 → 合法值/阈值 → 处置`。硬规则：
- `on-site` 且值合法 → 可回填 fields；
- `logic-only`/`unavailable` → 永不回填，对应字段缺失、整项 `status=pending`；
- 缺字段或 `null` 无 reason → 校验 FAIL。
- P10 三字段、P11 `machine_restart_pull_full` 在映射表直接标 `unavailable: "产品语义不足（S3不落shm/S2无跨机connector），现场不可得"`。

**B. 台账回填流程**：
1. 用户现场执行三套取证、ftp 回传 JSON + 运行日志到约定目录。
2. 我跑 `check_s5_capture.py` 核验（字段/来源/阈值/签名链），出核验报告。
3. 只把 `on-site` 字段按映射填入台账 fields；evidence 指向真实 JSON + 日志；`verified_by` 由用户指定独立工程师复核签名。
4. P10/P11 fields 保持 `{}`、status `pending`，note 写"现场不可得"原因。
5. 发布门 FAIL 8 不变；`check_release_conditions.py` ok=false、`release_gate.py --conditions` 非 0——S5 不做发布放行。

**C. 验证策略**：
- `check_s5_capture.py --self-test`：三坏样本 RED（unavailable 映射 measured / logic-only 填 measured / null 无 reason）→ FAIL；good → PASS。
- 板载程序交叉编译：`aarch64-sylixos-elf-gcc` 零警告 + ELF 架构核对（复用 G2 工具链）；Linux stub 下 JSON 自写逻辑可跑通；真机仅用户在板上执行。
- 指令文档评审：命令可复核、无凭证泄露、无"已就绪/可放行"误导。

**D. 责任边界**：同文首——我建工具/核验一致性，用户现场执行/真实性负责，独立工程师签名，我不代签/不碰设备/不填 measured/不放行/不 tag。

## 明确不做

不接管 node-server 业务面；不落 shm/不做跨机 connector（S2b/S3 后续）；不填 P10/P11 measured；不放行发布门；不改 VERSION/打 tag/合 main；不在文档写凭证；不把 logic-only/unavailable 字段写成现场真值。

## 实施入口

S5 变更卡（tdd:深：取证程序交叉编译验证 + 校验脚本三坏样本 RED + 文档评审）→ 基线冻结 → 独立评审 → 用户开工授权 → 工具建设 → 交付（真机执行由用户另行授权）。
