## 1. 裁决点 1：P7/P8 字段不全 → measured 口径

**用户裁决**：增加机器判据——声明**豁免字段白名单**（`unavailable_exempt`），机器可验证地置 P7/P8 measured；独立评审后作为契约变更留痕。**不是手填假绿**——白名单须有权威文档依据、可机检。

**工程化规则映射**：
- 防假绿：现状 `check_release_conditions.py:38-90` 只验 status/fields 非空/文件存在，**不验字段名完整性**——这是流程漏洞；靠漏洞放行等于"把侥幸固化为机器流程"。决议用**显式白名单 + 机器校验**替代隐式漏洞。
- 战略驱动：13 号 §11.1 冻结字段名是权威；白名单只允许列入**已被 13 号裁决确认产品语义不足/现场不可得**的字段（`deny_non_loopback`: server 仅绑 loopback；`join_triggers_full`: 无真实 WAL 出口），且须逐字段带 reason + 证据文件路径。
- 延迟处理：白名单变更走 SDD 变更卡 + 两轮独立评审（契约变更），不是改数字了事。

**实施约束**：
- 台账 `v3.12-B段数字落库.json` 增 `unavailable_exempt` 结构：`{item, field, reason, evidence}`；
- `check_release_conditions.py` 增校验：字段缺失仅当命中白名单且 reason/evidence 齐全才不算 FAIL；白名单本身须经 `check_review_evidence` 第二签（禁止自审自批）；
- P7/P8 置 measured 时 `verified_by` 仍须指向合规独立复验证据（当前用户自签文件不满足 `require_second=True`，须另出独立签）。

## 2. 裁决点 2：P10/P11 全量应用路径 vs S3"不落 shm"

**用户裁决**：**rtdbd 内部应用接口，不动 lib API**——在 rtdbd cluster 模块新增"点集快照→本机点集原子替换"内部函数，走 VSOA `/sync/snapshot` 交付、rtdbd 内应用；通过现有 `h_write_quality_ts`/`h_write_range_*` 逐点替换 + **epoch 栅门**保证语义原子（读侧 sees epoch 才可见）；不改 lib API/117/UDS opcode/ABI。S3 的"不落 shm"收窄升级为"rtdbd 内受控应用"，走契约变更评审。

**工程化规则映射**：
- 整洁架构：全量应用通过 rtdbd 内部接口隔离，业务不直接戳 shm、不新增 lib API；
- SemVer：排除了破 117 计数的 Major 路径（v4.0），保持 v3.12 正式版可达；
- 需求冻结/契约变更：S3 收窄的升级须评审留痕，S3 卡与 13 号 §8.3-1 补注记（git revert 可回滚）。

**实施约束**：
- 内部函数放 `rtdbd/src/cluster/`（如 `rtdbd_snapshot_apply.c/.h`），链入 rtdbd target，**不进 libindurtdb public 头**；
- 原子性靠"epoch 栅门"：应用期间读侧按旧 epoch 可见、应用完成推进全局 epoch 后才见新值（S1 `rtdbd_epoch` 原语复用），需单测可证伪（并发读不看到半应用状态）；
- 不改 UDS opcode/ABI/117 计数/POD；`check_api_count.py` 与 `check_dispatch_boundary.py` 必须仍绿；
- P10/P11 现场独立采集（6 板、非空点集 F4、同 epoch 双写注入）仍按 S5 既有流程；空表 F4 弱证据不得冒充收敛。
