## 一、工业边缘实时数据的体验之痛

在 BAS 楼宇控制、DDC 控制器、PLC 边缘网关里，温度、压力、风机状态、阀门开度这类实时数据无时不在流动。但一线开发者使用它们时，长期被三种糟糕的体验困扰：

1. **上手门槛高** —— 多进程共享内存要自己处理同步、对齐、崩溃恢复；一个不慎就是数据撕裂或段错误。本应写业务逻辑的工程师，被迫成了底层机制的修补匠。
2. **延迟不确定** —— 锁竞争、动态内存、异常路径带来不可预测的抖动。在毫秒级闭环控制里，一次偶发卡顿就可能导致调节超调。
3. **语义缺失** —— 拿到的只是裸数值，没有质量位、时间戳、单位、访问权限。上层各自重复造轮子，数据的可信度与可追溯性无从保障。

InduRTDB 的存在，就是为了把这三种糟糕的体验，变成简单、确定、语义完备的好体验。

## 二、产品定位

> **InduRTDB 是工业边缘控制系统的共享内存实时数据层——让确定性、可靠性与简洁性回归工业软件的本质。**

它是纯 C11 实现的超低延迟、多进程共享、语义完备的实时数据库，以静态库（`.a`）形式直接链接进你的程序，无独立进程、无网络开销、零外部依赖。四大设计原则贯穿始终：

- **确定性优先** —— 性能可预测，执行时间确定
- **可靠性至上** —— 7×24 稳定运行，进程崩溃也能自愈
- **简洁性核心** —— 单一头文件、26 个函数，几乎零学习成本
- **平台无关性** —— 纯 C 无 C++ 运行时，Linux / SylixOS 双平台

它专注**共享内存内的实时数据层**：南向采集由驱动层负责，北向 OPC UA 与持久化由 node-server 提供，InduRTDB 不重复造轮子。

## 三、用户体验五要素

### 3.1 学习体验 —— 5 分钟看懂全部 API

- **单一头文件**：整个公共 API 浓缩在 `indurtdb.h`，约 100 行、26 个函数，一页看完。
- **命名即文档**：`indurtdb_write_double` / `indurtdb_read_point` / `indurtdb_subscribe`，函数名直接说明行为，无需翻手册就能猜对用法。
- **无模板无泛型**：写什么类型就调什么函数（`write_bool` / `write_int32` / `write_double` / `write_string`），没有 C++ 模板的心智负担。

### 3.2 开发体验 —— 10 行代码完成集成

- **显式类型函数**：类型在编译期就确定，错误调用当场报错，不把 bug 留到运行期。
- **跨语言原生兼容**：纯 C API 可被 C++、Python（ctypes）、Rust（FFI）、Go（cgo）直接调用，无需桥接层。
- **批量与订阅内置**：`read_range` / `write_range_*` 一次搬运成百上千点位；`subscribe` 注册回调即得变更通知。
- **配置驱动**：`load_config` 从 YAML 加载点位名称/类型/单位/权限，改配置不改代码。

### 3.3 性能体验 —— 确定性的低延迟

- **无锁读**：Seqlock 序列锁，读路径完全无锁、无死锁。
- **零堆分配**：运行期不 `malloc`，无内存碎片，无分配抖动。
- **共享内存直达**：多进程读写同一片物理内存，无序列化、无网络往返。
- 基准数据（x86 实测：写 P99 0.386μs、读 P99 0.068μs、peek P99 0.062μs）见 [`01-产品白皮书.md`](./01-产品白皮书.md) 第 5 节。

### 3.4 运维体验 —— 自诊断、自愈

- **崩溃恢复**：持有者进程崩溃后，接入者自动检测并接管所有权；写锁内崩溃遗留的异常序列号也会被自动纠正，共享内存不留"脏状态"。
- **超时检测**：`check_timeouts` 批量扫描，把长时间未更新的点位标记为 `TIMEOUT` 质量（best-effort，遇写冲突会跳过该点）。
- **心跳 + 僵尸清理**：异常退出的订阅者自动回收，不泄漏槽位。
- **可观测**：`get_write_count` / `get_timeout_count` 统计，`get_last_error` 线程安全错误信息，运行状态一目了然。

### 3.5 移植体验 —— 平台无关、SylixOS 友好

- **纯 C 无 C++ 运行时**：不依赖 STL / 异常 / RTTI / 虚表，规避 SylixOS 对 C++17（尤其 `stdatomic`）支持不完整的问题，全部使用 `__atomic` 内建。
- **OSAL 双轨**：POSIX 与 SylixOS 各一个 OSAL 实现文件，核心代码 100% 平台无关。
- **布局稳定**：共享内存布局与 v2.x 逐字节兼容；v3.3 及之前保持 ABI 不变，升级不破坏既有数据约定。

## 四、能力边界（诚实声明）

InduRTDB 只把一件事做到极致——**边缘内存内的实时数据共享**。我们如实声明边界，帮你判断契合度：

| 支持 | 不支持 |
|------|--------|
| 内存点位读写（bool / int32 / double / string） | SQL 查询、关系模型 |
| 多进程共享内存协作 | 磁盘持久化、掉电恢复 |
| **进程内**点位变更订阅（回调） | **跨进程**变更通知（当前需轮询） |
| 初始化时固定容量（`max_points`） | 动态扩容、在线改容量 |
| **单进程单实例** | 同进程多实例 |
| 数字点位 ID（0..max_points-1） | 字符串键 / 按名查找（规划中，v4.0） |
| 静态 `access` 只读标记 | 进程级鉴权、加密、审计 |

> **四条使用约束**（详见 [`01-产品白皮书.md`](./01-产品白皮书.md) 第 6 节）：
> ① `peek()` 是**单拷贝**（拷贝到线程本地缓冲，下次 `peek` 覆盖），需长期持有请用 `read_point()`；
> ② **单进程单例**，切换实例须先 `shutdown()`；
> ③ 多写者并发冲突时 `write_*` 返回 **`-2`（busy）**，不重试，调用方自行处理；
> ④ `check_timeouts()` 为 best-effort，遇写冲突跳过该点。
>
> 性能指标（P99 ≤10μs）为设计目标，x86 已实测通过，ARM 实测待目标环境到位后补证。

## 五、典型应用场景

以**地铁车站 BAS 环控系统**为例：驱动进程经 Modbus / OPC UA 采集温湿度、CO₂、风机状态并写入 InduRTDB；联动控制逻辑快速读取这些点位，在毫秒内完成判断并写回控制指令；HMI 画面实时刷新设备状态。三类进程共用同一片共享内存——没有序列化、没有网络开销，一个车站的环控闭环由此在确定性时延内完成。上送 SCADA 与历史落盘由 node-server 承担。

其它典型场景：**设备驱动中枢**（驱动与控制逻辑的高速数据交换）、**HMI 实时展示**（高频画面刷新）、**边缘闭环控制**（确定性时延保障回路时序）。

## 八、决策者常见问题

**Q：它足够成熟、能用于工业现场吗？**
A：v3.x 已完成纯 C 重写，共享内存布局与 v2.x 逐字节兼容，具备崩溃自愈能力；gtest 26 套件 / 126 用例（ctest 注册 16 个：15 单元 + 1 多进程 fork 集成）全部通过，构建零警告，并有 soak 长稳与故障注入验证。ARM / SylixOS 实测仍在补证中，我们如实标注，不以外推数据充当实测。

**Q：会引入额外的依赖负担吗？**
A：不会。静态库（`.a`）交付，零第三方依赖，纯 C 实现无 C++ 运行时，链接即用。

**Q：与自研共享内存相比，价值在哪？**
A：自研意味着自行处理进程同步、内存对齐、崩溃恢复与语义字段。InduRTDB 把这些全部封装，并补齐工业语义（质量/时间戳/单位/权限），将集成成本从数周降到数小时。

**Q：许可与自主可控如何？**
A：MIT 许可，完全开放，无私有协议锁定；纯 C 源码易于审计、移植与二次开发。

**Q：需要跨主机、持久化或对外协议怎么办？**
A：核心库聚焦单机内存内实时共享，不重复造轮子：北向 OPC UA、持久化/历史、集群由框架内的 node-server（BAS Edge Data Hub）承担，InduRTDB 作为它的底层数据层。详见 [`01-产品白皮书.md`](./01-产品白皮书.md) 第 2 节。

**Q：升级会不会被迫重编？**
A：v3.3 及之前承诺 **ABI 保持不变**（共享内存布局与 C API 均不变）。v4.0 涉及布局变更，会配套迁移工具与向前兼容方案，并提前公告。

## 九、5 分钟快速体验

```c
#include <indurtdb/indurtdb.h>

int main(void) {
    indurtdb_initialize("hvac_system", 10000, 32);

    indurtdb_write_double(1001, 23.5);           /* 写入温度 */

    double t = 0.0;
    indurtdb_read_double(1001, &t);              /* 读取 */

    /* 快速读：单拷贝到线程本地缓冲，下次 peek 覆盖；长期持有请用 read_point */
    const indurtdb_point_t* p = indurtdb_peek(1001);
    (void)p;

    indurtdb_shutdown();
    return 0;
}
```
