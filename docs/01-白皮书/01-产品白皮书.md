## 1. 执行摘要

InduRTDB 是一个**纯 C11 实现的共享内存实时数据层**：它把工业现场的点位（测点/标签）放在一段跨进程共享的内存里，让驱动、控制逻辑、HMI 像访问全局变量一样读写同一份数据，并获得**微秒级、可预测**的访问延迟。

它不是一整条数据链路，而是链路**中间的实时热数据层**：

- **向下**：由框架驱动层（Modbus / OPC UA / S7 等）采集后写入；
- **向上**：由 [node-server](https://github.com/acoinfo/edge-framework)（BAS Edge Data Hub）复用其既有的 **OPC UA Server（北向）** 与 **SQLite（持久化/历史）** 能力对外供给。

**一句话**：InduRTDB 负责"在内存里把实时数据存好、共享好、语义带全"，其余交给它所在的框架。

## 2. 定位与边界

### 2.1 做什么 / 不做什么

| 做 | 不做 |
|---|---|
| 跨进程共享内存点位存储（低延迟、确定性） | 南向设备接入（Modbus / OPC UA / S7 驱动） |
| 工业语义（quality / timestamp / unit / access / name） | 北向 SCADA 对接（OPC UA Server / MQTT 上送） |
| 多进程读写、进程内订阅、崩溃自愈 | 持久化 / 历史库 / 归档查询 |
| 作为库被集成（find_package / pkg-config / FetchContent） | 集群 / 跨节点同步 / 高可用 |
| 嵌入式形态交付（静态库 `.a`，零第三方依赖） | 鉴权 / 加密 / 审计（由上层与 OS 承担） |

> 划到"不做"的能力并非不重要，而是**由 node-server 或框架其它组件承担**，InduRTDB 不重复造轮子。

### 2.2 与 node-server 的关系

| 能力 | InduRTDB | node-server | 处置 |
|---|---|---|---|
| 实时点位存储 | 跨进程 shm、数字 ID、Seqlock、无锁读 | 进程内 sharded map、string 键 | **互补**：InduRTDB 承担多进程共享场景 |
| 北向 OPC UA | 无 | ✅ 已有 Server（open62541） | 复用 node-server |
| 持久化 / 历史 | 无 | ✅ SQLite | 复用 node-server |
| 工业语义 | quality / unit / access / timestamp_ns | ts / driver / device | InduRTDB 语义更全，映射传递 |
| IPC | 共享内存 | SSN IPC | 互补 |

## 3. 架构

```
┌─────────────────────────────────────────────────────────┐
│  上层应用：node-server（OPC UA 北向 / SQLite 持久化）      │
│  驱动层：Modbus / OPC UA / S7（采集后写入）                │
├─────────────────────────────────────────────────────────┤
│  include/indurtdb/indurtdb.h   唯一公共头文件（26 函数）   │
│  src/api/indurtdb.c            单例外观层                 │
├──────────┬──────────┬──────────────┬────────────────────┤
│ irt_shm  │ irt_pm   │ irt_sub      │ irt_config         │
│ 段管理   │ 点位读写 │ 订阅/心跳    │ key=value + YAML    │
├──────────┴──────────┴──────────────┴────────────────────┤
│  src/internal  共享内存布局 irt_types.h + Seqlock 原语     │
│  src/osal      POSIX / SylixOS 双轨（时间 + 共享内存）     │
├─────────────────────────────────────────────────────────┤
│  共享内存段 /indurtdb_<instance_id>                       │
│  Header(64B) + Points(N×128B) + Subscriber 心跳(M×16B)    │
└─────────────────────────────────────────────────────────┘
```

**依赖方向严格单向**：`api → core → internal / osal`，核心层不反向依赖上层。

## 4. 核心能力

### 4.1 存储模型

| 项 | 说明 |
|---|---|
| 段 | `/indurtdb_<instance_id>`，一段连续共享内存 |
| 布局 | `Header 64B` + `点位 N×128B` + `订阅心跳 M×16B` |
| 点位结构 | `indurtdb_point_t`（128B，`packed, aligned(128)`）：value 联合体 + `timestamp_ns` + `type` + `quality` + `unit` + `access` + `name[64]` |
| 数据类型 | `bool` / `int32` / `double` / `string`（31 字符 + 结束符） |
| 工业语义 | `quality`（GOOD / BAD / TIMEOUT / SUBSTITUTED）、纳秒时间戳、工程单位、读写权限、点位名 |
| 布局锁定 | 编译期 `IRT_STATIC_ASSERT` 校验 64 / 128 / 16 字节；与 v2.x 逐字节兼容 |

### 4.2 并发模型

- **全局单 Seqlock**（`header->write_seq`）：写端 CAS 切奇偶，读端重试循环，**读路径完全无锁、无内核锁、无系统调用**。
- **运行期零堆分配**：全定长数组与栈缓冲，无 `malloc`/`free`，7×24 运行无内存碎片。
- 原子操作统一使用 `__atomic_*` builtins（不使用 `stdatomic.h`，适配 SylixOS）。
- Seqlock 临界区内不调用外部回调。

### 4.3 可靠性

| 机制 | 说明 |
|---|---|
| owner 崩溃自愈 | 接入方通过 `kill(pid, 0)` 存活检查发现 owner 已死，调用 `irt_shm_os_claim_ownership()` 接管 |
| Seqlock 奇数恢复 | attach 时若发现遗留奇数 `write_seq`（写锁内崩溃）自动推进到偶数，恢复一致性 |
| fork 安全 | 通过 `owner_pid != getpid()` 识别子进程并清除 owner 标记，避免子进程 `shm_unlink` 误删父进程段 |
| 超时检测 | `check_timeouts(ns)` 将超期未更新点位标记为 `QUALITY_TIMEOUT` |

### 4.4 集成方式

静态库 + ALIAS 目标 `InduRTDB::indurtdb`，三条消费路径均已回归验证（`scripts/verify_consume.sh`）：

| 方式 | 说明 |
|---|---|
| `find_package(InduRTDB)` | 安装导出 Config / Version / Targets |
| `pkg-config` | `indurtdb.pc`（含 prefix 一致性校验） |
| FetchContent / add_subdirectory | 源码内嵌；自动子项目隔离（默认不构建 tests/examples、不安装） |

## 5. 实测性能

**x86_64，Release `-O2`**（`tests/bench/` + `scripts/run_bench.sh`）：

| 操作 | P50 | P99 | 吞吐 |
|------|-----|-----|------|
| write_int32 | 0.156 μs | 0.386 μs | 5.2M op/s |
| read_int32 | 0.062 μs | 0.068 μs | 16.2M op/s |
| peek（单拷贝） | 0.057 μs | 0.062 μs | 17.7M op/s |
| read_range（100 点） | 2.893 μs | 2.992 μs | 35.5M pt/s |
| write_range（100 点） | 12.459 μs | 17.911 μs | 8.1M pt/s |
| mixed_rw | — | — | 16.3M op/s |

> 设计目标 **P99 ≤ 10 μs**，x86 实测全部通过。**ARM / SylixOS 平台实测尚未完成**，目标环境到位后补证并更新本节（不以外推数据充当实测）。

## 6. 能力边界与已知约束（诚实声明）

本节是选型依据，请务必连同第 2 节一起阅读。

| 支持 | 不支持 |
|---|---|
| 内存点位读写（bool / int32 / double / string） | SQL 查询、关系模型 |
| 多进程共享内存协作 | 磁盘持久化、掉电恢复 |
| **进程内**点位变更订阅（回调） | **跨进程**变更通知（当前只能轮询） |
| 初始化时固定容量（`max_points`） | 动态扩容、在线改容量 |
| **单进程单实例**（一个进程内一个 RTDB 实例） | 同进程多实例 |
| 数字点位 ID（`0..max_points-1`） | 字符串键 / 按名查找（规划中，v4.0） |
| 静态 `access` 只读标记 | 进程级鉴权、加密、审计 |

**四条必须知道的行为约束**：

1. **`peek()` 是单拷贝，不是零拷贝**：数据经 Seqlock 拷贝到 `_Thread_local` 缓冲后返回其指针，**同线程下一次 `peek()` 即覆盖**。需长期持有请用 `indurtdb_read_point()` 拷贝到自管理缓冲。
2. **单进程单例**：`indurtdb_initialize()` 在同一进程内只能持有一个实例；切换实例须先 `indurtdb_shutdown()`。不同 `instance_id` 的跨进程隔离正常。
3. **写冲突不重试**：多写者并发时，若 Seqlock 处于写中状态，`write_*` 直接返回 **`-2`（busy）**，不阻塞、不重试。调用方需自行处理重试（该语义将在 v3.3 确定化）。
4. **超时检测是 best-effort**：`check_timeouts()` 扫描时若遇写冲突会跳过该点位，因此单次调用不保证覆盖全部点位。

**安全说明**：库本身不提供网络服务、鉴权与加密。共享内存的访问控制依赖操作系统文件权限（`/dev/shm` 下的 uid/gid）；点位 `access` 字段是**静态只读标记**，用于拒绝写入，**不是访问控制机制**。对外认证、加密、审计由上层 Bridge / node-server 承担。

## 7. 典型应用

**地铁车站 BAS 环控系统**（与 node-server 配合的完整链路）：

```
现场设备 ──驱动层采集──► InduRTDB（共享内存实时层）
                             ▲  │
              控制逻辑读/写 ──┘  ├──► node-server OPC UA Server ──► SCADA / ISCS
              HMI 读/订阅 ───────┘ └──► node-server SQLite ──► 历史归档
```

- 驱动进程采集后写入 InduRTDB；
- 联动控制逻辑毫秒内读取、判断并写回控制指令；
- HMI 画面读取/订阅刷新；
- 上送 SCADA 与历史落盘由 node-server 承担。

其它场景：DDC 控制器内部数据交换、设备驱动中枢、边缘闭环控制、HMI 高频刷新。
