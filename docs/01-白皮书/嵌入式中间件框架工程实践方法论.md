# 嵌入式中间件框架工程实践方法论

> **版本**: 1\.0 \| **日期**: 2026\-08\-11 \| **基于**: VSOA Framework v1\.5\.x 全流程实践
> 
> 



## 1\. 概述



本文档提炼自 VSOA Framework 从 v1\.4\.0 到 v1\.5\.1 的完整开发、测试、发布实践，总结为一套可复用的工程方法论。适用于 C/C\+\+ 嵌入式中间件框架及同类系统软件项目。



### 1\.1 适用场景



- 多平台（Linux/SylixOS/QNX/Windows）C/C\+\+ 中间件框架

- 带有预编译闭源 SDK 依赖的项目

- 需要服务端/客户端双态交付的通信框架

- 团队规模 3–10 人，需要规范化流程但不过度工程化

    

### 1\.2 核心原则



```Plain Text
质量内建 > 事后检查
自动化 > 手动化
文档即接口 > 文档是负担
工具即产品 > 脚本是临时代码
```

## 2\. 分支模型



### 2\.1 分支层级



```Plain Text
main ────────────────────────────── 发布分支（保护，禁止 push）
  │
  ├── V1.5.0 ───────────────────── 版本分支（保护，仅 cherry-pick 修复）
  │     │
  │     └── feature/v1.5.1-* ──── 特性分支（开发主线）
  │           │
  │           └── fix/v1.5.0-* ── 修复分支
  │
  └── V1.6.0 ───────────────────── 下一版本分支
```



### 2\.2 规则



|规则|说明|
|---|---|
|每次变更新建分支|从当前版本分支创建 `feature/*` 或 `fix/*`，完成后合回|
|发布分支只进不出|main/V1\.x\.0 禁止直接 push，只通过 MR 或 cherry\-pick 合入|
|删除已合入分支|合入后立即删除源分支，保持仓库整洁|
|cherry\-pick 修复到历史版本|关键 bug 修复同步搬运到受影响的版本分支|

## 3\. 提交规范



```Plain Text
<type>(<scope>): <简短描述>

<详细说明（可选）>
```



|type|用途|示例|
|---|---|---|
|`feat`|新功能|`feat(sdk): 订阅者诊断 API GetSubscriberUrlInfo`|
|`fix`|缺陷修复|`fix(servermgr): reload 两阶段安全重载`|
|`docs`|文档|`docs(servermgr): reload 行为文档化`|
|`test`|测试|`test(servermgr): reload 行为失败测试（RED）`|
|`refactor`|重构|`refactor(sdk): 提取 parseConfigDirectory 纯函数`|
|`chore`|工程化|`chore: v1.5.0-rc armory 制品更新`|
|`perf`|性能优化|`perf(shmemq): 减少 memcpy 次数`|
|`ci`|CI/CD|`ci: GitLab CI 门禁配置`|

## 4\. TDD 循环（铁律）



```Plain Text
┌──────────────────────┐
         │   ① RED: 写失败测试   │
         │   测试先行，确认失败   │
         └──────┬───────────────┘
                │
                ▼
         ┌──────────────────────┐
         │   ② GREEN: 最小实现  │
         │   让测试通过，不过度  │
         └──────┬───────────────┘
                │
                ▼
         ┌──────────────────────┐
         │   ③ REFACTOR: 重构   │
         │   改善质量，保测试绿  │
         └──────────────────────┘
```



### 4\.1 测试分层



|层级|框架|位置|触发|
|---|---|---|---|
|模块内建测试|自建 `TestResult` / GTest|`src/<模块>/`（BUILD\_TESTS 门控，如 vsoa\_master 全部套件）|`ctest --test-dir build`（BUILD\_TESTS=ON）|
|跨模块/集成测试|GTest \+ 真实进程|`tests/`（镜像 src 结构，独立 CMake 工程）|Linux CI（MR 触发）|
|冒烟测试|Python 脚本|`scripts/smoke/`|发布前|



> **双轨定位**（2026\-08\-22 如实化修订）：模块内建与跨模块两套并存是既成事实，
> 
> 新增测试按所属模块就近归入既有套件，禁止在两树间复制分叉；统一收敛挂
> 
> v1\.7\.0 注册中心重构周期。
> 
> 



### 4\.2 测试要求



- 每个公开 API 必须有对应的测试用例

- 测试用例验证真实行为（不用 mock 替代关键依赖）

- 修复 bug 时，先写复现 bug 的测试（RED），再修复（GREEN）

- CI 中 `ctest --output-on-failure` 失败则禁止合入

## 5\. 代码审查



### 5\.1 审查时机



- 每个功能/修复完成后（合入前）

- 每个 MR 至少一人审查

    

### 5\.2 严重级分类



|级别|含义|行动|
|---|---|---|
|Critical|安全漏洞、数据丢失风险、死锁|立即修复，禁止合入|
|Important|架构问题、遗漏功能、错误处理缺失|合入前修复|
|Minor|代码风格、优化建议、文档润色|可延迟到后续迭代|

### 6\.1 组织结构



```Plain Text

├── 02-需求与设计/        ← 总体设计、子系统设计、打包规范

├── 05-开发指南/         ← SDK、核心组件、编码规范
├── 06-API参考/          ← 接口文档、错误码、配置参考
```

### 6\.2 规则



- 文件夹/文件名使用中文 \+ 数字前缀（排序友好）

- 文档与代码同步更新——**代码变更 = 文档变更**

- 每个公开 API 必须有文档条目

- 每个操作必须有代码示例

- 定期运行 `doc-freshness-check.py` 检测腐败

## 7\. 交付自动化



### 7\.1 工具链全景



```Plain Text
开发 → pre-commit 检查 → commit → push → MR → CI(编译+测试) → 评审
                                                              │
                                                              ▼
                                                         合入主分支
                                                              │
                                                              ▼
                                               release.sh ─ 打包 → 冒烟 → armory → tag
```



### 7\.2 核心工具



|工具|用途|触发时机|
|---|---|---|
|`pre-commit-check.sh`|格式/调试代码/TODO 检查|`git commit` 前|
|`verify.sh`|编译 \+ 测试 \+ 报告|本地验证|
|`package-sdk.py`|双包打包（runtime\+devel）|发布前|
|`smoke/servermgr_smoke.py`|servermgr API 全量冒烟|打包后|
|`release.sh`|一键发布（打包\+冒烟\+armory\+tag）|发布时|
|`cherry-pick-to-release.sh`|提交搬运到发布分支|修复回合|
|`doc-freshness-check.py`|文档腐败检测|定期 / MR 中|
|`.gitlab-ci.yml`|MR 门禁（编译\+测试）|MR 创建时|

## 8\. 多平台策略



### 8\.1 平台分层



|层级|平台|交付形式|
|---|---|---|
|完整支持|Linux x86\_64/aarch64|编译\+测试\+打包\+冒烟|
|交叉编译|SylixOS \(10架构\)|交叉编译\+打包（测试在目标板上）|
|阶段移植|QNX / Windows|基础编译验证，功能逐步对齐|



### 8\.2 原则



- 主开发平台（Linux x86\_64）承担全量测试

- 交叉编译平台保证编译通过

- 平台差异用 `#ifdef` \+ CMake toolchain 隔离，禁止业务逻辑中散落平台判断

    

---



## 9\. 安全与合规



- 禁止硬编码密钥、密码（使用环境变量或配置文件）

- 禁止 `strcpy`/`sprintf`（使用 `strncpy`/`snprintf`）

- 禁止 `printf`/`cout` 残留（使用日志框架）

- 第三方依赖通过 armory 管理版本，禁止源码内 vendoring 未审计代码

- C\+\+ 资源管理统一 RAII（`unique_ptr`/`shared_ptr`）

## 10\. SDD 规格驱动开发（铁律）



> 2026\-08\-20 项目负责人确认：**文档先行，设计评审通过才能动手实现**。
> 
> 适用于所有功能开发、重构、接口变更（bug 修复的最小改动可简化，但涉及公共接口/架构必须走完整流程）。
> 
> 



### 10\.0 流程分级



|档位|适用条件|要求|
|---|---|---|
|**完整流程**|新特性 / 公共接口变更 / 架构调整 / 影响跨模块|九章设计文档 \+ 设计评审 P0/P1 清零|
|**轻量流程**|缺陷修复的最小改动；或影响面 ≤ 单模块且不涉及公共接口签名、线程模型、协议格式|简化设计说明（至少含：概述与目标、测试计划、影响面三部分）随 MR 提交，由代码评审覆盖|



> 判定存疑时按完整流程执行（分级只升不降）。反例警示（2026\-08 复盘）：
> 
> v1\.6\.0 的 Stream/datagram/DataMode 三特性未经 SDD 即发布，交付时零单元
> 
> 测试，事后以整轮测试补账偿还——轻量档不是豁免档，测试计划不可省略。
> 
> 



### 10\.1 核心理念



```Plain Text
需求请求（问题/目标） → 设计文档（规格） → 设计评审（门槛） → TDD 实现 → 代码评审 → 合入
     ↑___________________________|                    ↑
     不满足则打回重写              评审通过才允许动代码       实现必须符合设计，变更设计需再评审
```



- **文档先行**：任何实现开始前，先有设计文档（规格）

- **评审门槛**：设计评审通过（P0/P1 清零）才允许进入编码阶段

- **TDD 承接**：设计文档的"测试计划"章节直接作为 RED 用例的来源

- **变更回环**：实现中发现设计缺陷，修改设计文档 → 再评审 → 再实现

    

### 10\.2 设计文档要求



**位置**：`docs/02-需求与设计/`（子系统级）或功能目录下（如 `docs/04-使用指南/` 对应章节），文件名中文 \+ 语义化（如 `Monitor可观测性设计.md`）。



**必含章节**（模板）：



|章节|内容|
|---|---|
|1\. 概述|背景、目标、范围、非目标|
|2\. 架构|组件图、数据流、模块职责、依赖关系|
|3\. 接口|公共 API/配置/端点，含签名与语义（**ABI 兼容性分析**）|
|4\. 数据模型|结构体/字段/派生指标|
|5\. 配置|配置文件 schema、默认值、校验|
|6\. 线程模型与生命周期|线程、锁、停止顺序、资源释放（**长稳：内存/句柄/竞态**）|
|7\. 测试计划|单元/集成/冒烟用例清单（对应 TDD 的 RED）|
|8\. 影响面与兼容性|平台、ABI、既有调用方、迁移路径|
|9\. 已知局限|未决问题、后续工作|



### 10\.3 评审流程



1. **设计评审**：设计文档完成 → 评审（遵循 §5 代码审查标准，P0/P1 清零）→ **通过后才允许写实现代码**

2. **实现评审**：TDD 实现完成 → 代码评审（§5）→ 合入

3. 涉及公共接口/架构变更的设计，评审必须包含 **ABI 兼容分析**（规则 13）与**长稳分析**（规则 14）

    

### 10\.4 与既有规则的衔接



- **需求来源**：需求请求可放 `.superpowers/`（如 `vsoa-fw-request-01.md`），或 `docs/02-需求与设计/需求分析.md`

- **TDD**（§4）：设计文档 §7 测试计划 = RED 用例

- **分支**（§2）：设计评审通过后从版本分支建 `feature/*`

- **文档同步**（§6）：实现完成必须更新设计文档到最终状态（文档即唯一对外接口）

## 11\. 附录：快速启动清单



### 新成员入职



1. 阅读 `README.md` → 了解项目结构和构建方式

2. 阅读本文档 → 了解开发流程和方法论

3. 配置开发环境 → `docs/03-概览与快速开始/环境搭建.md`

4. 运行 `./scripts/verify.sh` → 确认编译和测试通过

5. 浏览 `docs/04-使用指南/` → 了解框架功能

    

### 新功能开发



1. 从当前版本分支创建 `feature/<描述>` 分支

2. **写设计文档**（§10：docs/02\-需求与设计/，含架构/接口/数据模型/配置/测试计划/影响面）

3. **设计评审通过**（P0/P1 清零）→ 才允许写实现代码

4. 在 `tests/` 下写失败测试（RED，对应设计文档测试计划）

5. 实现功能让测试通过（GREEN）

6. 重构优化（保持测试绿色）

7. 同步更新文档（设计文档 \+ 使用指南 \+ API 参考）

8. 创建 MR → CI 通过 → 代码评审 → 合入
