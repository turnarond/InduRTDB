## 一、工业边缘的实时数据之痛

在智慧地铁 BAS、DDC 控制器、PLC 边缘网关里，实时数据无时无刻不在流动：温度、压力、风机状态、阀门开度。但工业边缘开发者在处理这些数据时，长期被三个顽疾困扰：

1. **接入门槛高** —— 多进程共享内存编程复杂，进程间同步、内存对齐、崩溃恢复都要自己造轮子，稍有不慎就是数据撕裂或段错误。本应服务于业务的工程师，把大量时间耗在了底层机制上。
2. **延迟不确定** —— 锁竞争、动态内存分配、异常处理带来不可预测的抖动，让毫秒级的闭环控制变成赌博。在实时性要求苛刻的控制回路里，一次偶发的几十毫秒卡顿就可能造成调节超调。
3. **语义缺失** —— 拿到的只是裸数值，没有质量位、时间戳、单位、访问权限。上层业务只能各自重复实现、各自踩坑，数据的可信度和可追溯性无从保障。

InduRTDB 为根治这三痛而生。

## 二、产品定位

> "让工业边缘开发者像访问全局变量一样简单、安全、高效地使用实时数据。"

InduRTDB 不是"另一个数据库"，而是面向工业边缘控制场景（BAS / DDC / PLC）的**超低延迟、多进程共享、语义完备**的实时数据库。四大设计原则贯穿始终：

- **确定性优先** —— 性能可预测，执行时间确定
- **可靠性至上** —— 7×24 小时稳定运行，无内存泄漏
- **简洁性核心** —— 代码简洁，避免过度设计
- **平台无关性** —— Core 层 100% 平台无关，OSAL 层隔离系统差异

## 三、工作原理（一页读懂）

- **数据放在一块共享内存里**：通过 POSIX 共享内存（`shm_open` + `mmap`）创建一段所有进程共同映射的物理内存。读写不经过网络、不经过内核协议栈，进程间交换数据就像读写同一片内存。
- **每个点位是一个 128 字节定长结构**：除了数值本身，还携带数据类型、质量位、纳秒时间戳、单位、访问权限。数据的工业语义与数据同行，上层无需自行拼装。
- **写用 Seqlock，读完全无锁**：写者开始时把序列号置为奇数、结束时恢复偶数；读者看到奇数就重试。于是读者永远能读到一条完整、一致的点位，而读路径上没有任何锁。这正是超低延迟与确定性的来源。
- **订阅表与心跳也在共享内存中**：订阅关系、进程心跳都记录在共享内存里，配合僵尸清理机制，即便某个进程异常退出也不会留下脏状态。

## 四、用户体验五要素

### 4.1 开发体验 —— 像访问全局变量一样简单

- **单例 API**：`rtdb.write(id, 23.5)`、`rtdb.read(id, p)`、`rtdb.peek(id)`，一行读写，无样板代码。
- **编译期类型分发**：写 `bool/int32/double/string` 由模板在编译期校验，类型错误根本编译不过，把 bug 拦在运行之前。
- **零拷贝读取**：`peek()` 直接返回共享内存指针，高频读取零拷贝开销。
- **C++ / C 双 API**：C ABI 17 个函数，兼容 C / Python / Rust 集成。

### 4.2 性能体验 —— 确定性的超低延迟

- **无锁读**：Seqlock 算法，读路径完全无锁。
- **全局写同步**：写路径由单一序列锁保护，行为可预测。
- **零动态内存**：运行期无 `malloc`/`new`，无分配抖动。
- **零异常 / 零 STL**：`-fno-exceptions -fno-rtti`，执行时间确定。

### 4.3 部署体验 —— 开箱即用

- **静态库交付**（`.a`），零第三方依赖，无运行时依赖地狱。
- **单文件 YAML 点位配置**，自研轻量解析器，改配置不改代码。
- **多进程共享**：POSIX 共享内存，多进程协作零网络开销。

### 4.4 运维体验 —— 语义完备、可自诊断

- **每点质量位**（quality）：GOOD / BAD / TIMEOUT / SUBSTITUTED。
- **每点纳秒时间戳**、单位、访问权限，工业语义随数据同行。
- **订阅心跳 + 僵尸清理**：异常退出的订阅者自动回收，不留脏状态。
- **写入 / 超时统计**：运行状态可观测。

### 4.5 集成体验 —— 平台无关的分层架构

- **Core 层 100% 平台无关**，OSAL 层隔离操作系统差异。
- **Linux（POSIX）已实现**，SylixOS 接口就绪、待平台验证。
- **API / Core / OSAL 三层清晰分层**，依赖单向，替换平台不动业务。

## 五、方案对比

| 方案 | 延迟 | 多进程 | 工业语义 | 集成成本 |
|------|------|--------|---------|---------|
| 自研共享内存 | 低 | 需自建 | 无 | 高（同步/对齐/崩溃自理） |
| 网络 IPC（Socket/MQ） | 毫秒级 | 支持 | 部分 | 中（协议开销） |
| 通用数据库（SQLite/Redis） | 毫秒级 | 支持 | 无 | 中（非实时设计） |
| **InduRTDB** | **微秒级** | **原生** | **完备** | **低（单一 API）** |

InduRTDB 的价值，在于把"自研共享内存"的低延迟与"成熟中间件"的低集成成本合二为一，并补齐二者都缺失的工业语义。

## 六、能力边界（诚实声明）

InduRTDB 只把一件事做到极致——**边缘内存内的实时数据共享**。我们如实声明边界，帮你判断它是否契合场景：

| 支持 | 不支持 |
|------|--------|
| 内存点位读写（bool/int32/double/string） | SQL 查询、关系模型 |
| 多进程共享内存协作 | 磁盘持久化、掉电恢复 |
| 点位变更订阅（回调） | 分布式、跨主机复制 |
| 初始化时固定容量（max_points） | 动态扩容、在线改容量 |
| 数字点位 ID（0..max_points-1） | 字符串键查找 |

> 说明：写路径由全局 Seqlock 保护，极高并发写场景下写冲突返回 `false`，调用方需重试。性能指标（P99 ≤10μs）为设计目标，目标硬件实测见第八节路线图。

## 七、典型应用场景

以**地铁车站 BAS 环控系统**为例：驱动进程从 Modbus / OPC UA 设备采集温湿度、CO₂、风机状态，写入 InduRTDB；联动控制逻辑通过零拷贝 `peek()` 读取这些点位，在毫秒内完成判断并写回控制指令；HMI 画面实时刷新各设备状态。三类进程共用同一片共享内存——没有序列化、没有网络开销、没有数据搬运，一个车站的环控闭环由此在确定性时延内完成。

其它典型场景：

- **设备驱动中枢**：驱动与控制逻辑间的高速数据交换。
- **HMI 实时展示**：零拷贝支撑高频画面刷新。
- **边缘闭环控制**：确定性延迟保障控制回路时序。

## 十、5 分钟快速体验

```cpp
#include <indurtdb.hpp>

auto& rtdb = indurtdb::InduRTDB::instance();
rtdb.initialize("hvac_system", 10000, 32);

rtdb.write(1001, 23.5);            // 写入温度
indurtdb::PointData p;
rtdb.read(1001, p);                // 读取（带拷贝）
const auto* pp = rtdb.peek(1001);  // 零拷贝读取

rtdb.shutdown();
```
