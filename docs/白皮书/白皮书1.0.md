## 1. 执行摘要

在工业边缘控制（BAS、DDC、PLC）场景中，传统方案大量依赖 **Modbus** 进行数据采集与交换。Modbus 虽然简单，但存在致命缺陷：**无认证、无加密、无授权，任何接入网络的设备均可读取全部寄存器数据**。同时，传统 IT 数据库（如 SQLite、Redis）无法满足控制层对 **μs 级确定性延迟、多进程零拷贝共享、工业语义（质量戳/时间戳）** 的严苛要求。

**InduRTDB** 是一款专为工业边缘控制器打造的 **超低延迟、多进程共享、语义完备** 的实时数据库。它提供：

- **P99 ≤ 10 μs 的写入延迟**，满足硬实时控制周期；
- **进程间零拷贝共享内存**，使驱动、控制逻辑、HMI 如同访问全局变量；
- **内建工业语义**（质量、工程单位、访问权限等），让数据不再是裸数；
- **通过可选的 OPC UA Bridge 提供安全、加密、细粒度授权的对外接口**，从根本上替代裸奔的 Modbus。

本文档阐述 InduRTDB 的设计哲学、技术架构、安全体系及与工业标准的融合路径，旨在帮助用户和集成商构建 **确定性、安全、开放** 的边缘智能系统。

## 2. 问题陈述：为什么 Modbus 不够，传统数据库也不行

### 2.1 Modbus 的安全黑洞

Modbus RTU/TCP 是工业领域应用最广的通信协议，但其设计之初完全没有安全考虑：

- **无身份认证**：任何能 ping 通设备的节点都能读写所有寄存器。
- **无加密**：数据明文传输，轻易被嗅探、篡改。
- **无授权粒度**：无法针对不同点位设置不同用户的读写权限。
- **无审计追踪**：谁在何时写入了某个寄存器，无从知晓。

在智能制造、关键基础设施（楼宇自控、水务、电力）的网络边界日趋模糊的今天，这种“全裸”的数据接口已成为重大安全风险。

### 2.2 传统数据库的实时鸿沟

边缘控制器要求极严格的时间确定性：1 ms 的控制周期内，写数据、读反馈、执行逻辑必须全部完成。普通文件数据库或关系型数据库：

- 引入系统调用、缓存、锁竞争，延迟在数百微秒至毫秒级，且不可预测。
- 缺乏多进程高效共享机制，增加 IPC 开销和拷贝成本。
- 数据缺乏工业上下文（如传感器故障标识、校准状态），需额外处理。

**结论**：工业边缘急需一种 **在操作系统层面天然安全隔离、提供极低确定延迟、并具备工业数据语义** 的基础设施。

## 3. InduRTDB 解决方案概览

InduRTDB 是部署在边缘控制器上的 **实时数据核心**，所有本地控制应用（驱动、控制逻辑、人机界面）直接通过 API 操作共享内存中的数据，获得全局一致的实时视图。对外，通过部署 **OPC UA Bridge** 将安全标准协议暴露给上层系统，实现纵深防御。

```
┌──────────────────────────────────────────┐
│              云平台 / SCADA              │
└───────────────┬──────────────────────────┘
                │ OPC UA (加密, 证书认证, 权限控制)
┌───────────────┴──────────────────────────┐
│             OPC UA Bridge                │
│   (使用 InduRTDB C API 读写共享内存)     │
└───────────────┬──────────────────────────┘
                │ 进程间共享内存 (mmap)
┌───────────────┴──────────────────────────┐
│            InduRTDB 实时数据库            │
│  ┌──────────────────────────────────┐   │
│  │ PointManager (Seqlock 无锁读写)  │   │
│  │ SubscriptionMgr (变更推送)       │   │
│  │ 工业语义 (quality/unit/ts)       │   │
│  └──────────────────────────────────┘   │
│  共享内存段 (Header + 点数组)            │
└──────────────────────────────────────────┘
        │ C/C++ API      │ C/C++ API
┌───────┴───────┐  ┌─────┴──────┐
│ 驱动 (Modbus  │  │ 控制逻辑    │
│ 采集/PLC IO)  │  │ (PID/逻辑) │
└───────────────┘  └─────────────┘
```

- **底层驱动**：仍可采集 Modbus 设备，但只内部写入 InduRTDB，不暴露网络端口。
- **控制逻辑**：直接从数据库读写，获得最新实时值，无 IPC 延迟。
- **对外服务**：所有上云或上位机请求均由 OPC UA Bridge 代理，实施认证、加密和节点级访问控制。**不再直接暴露任何 Modbus 端口。**

## 4. 架构设计

InduRTDB 严格遵循 **确定性、可靠性、简洁性、平台无关性** 四大设计原则，分为三层：

### 4.1 核心层 (Core) —— 平台无关

- **PointManager**：直接操作共享内存点数组，使用 **Seqlock（序列锁）** 保证写操作无锁、读操作无阻塞且数据一致。所有数据为 POD 类型，无指针、无虚表。
- **SubscriptionMgr**：固定大小槽位数组，用于通知进程数据变更，极简高效。
- **SharedMemorySegment**：基于 `shm_open` + `mmap(MAP_SHARED)`，管理 Header（版本、点数、占用大小）和点数组的初始化与持久化。
- **ConfigLoader**：自研轻量 YAML 解析器，零第三方依赖，确定性地加载点位配置。

### 4.2 操作系统抽象层 (OSAL)

抽象 `ISharedMemory`、`ITime`、`IThreading`、`INotification` 等接口，目前已实现 POSIX (Linux) 版本，SylixOS 实现已预留。Core 层 100% 通过 OSAL 调用平台服务，确保跨平台移植仅需实现对应接口。

### 4.3 API 层

- **纯 C11 API**：单一头文件 `<indurtdb/indurtdb.h>`，24 个函数，`extern "C"` 包裹；
- 提供 `indurtdb_write_*()`（4 类型）、`indurtdb_read_*()`（4 类型）、`indurtdb_peek()`（零拷贝）、`indurtdb_subscribe()`、`indurtdb_load_config()` 等；
- 易于被 C++、Python、Rust、Go 等通过 FFI 调用，为 OPC UA Bridge 提供最轻量接入。

```c
#include <indurtdb/indurtdb.h>

int main() {
    indurtdb_initialize("hvac", 10000, 32);
    indurtdb_write_double(1001, 23.5);
    indurtdb_write_bool(2001, true);
    indurtdb_write_string(3001, "Pump_01");

    double temp;
    indurtdb_read_double(1001, &temp);
    const indurtdb_point_t* p = indurtdb_peek(1001);  // 零拷贝

    indurtdb_shutdown();
    return 0;
}
```

## 5. 核心特性：确定性、实时性、工业语义

### 5.1 超低且可预测的延迟

| 指标 | 目标 | 说明 |
|------|------|------|
| 写入延迟 (P99) | ≤ 10 μs | ARM Cortex-A53，10k 点，Seqlock 无锁写 |
| 读取延迟 (P99) | ≤ 5 μs | 零拷贝 `peek`，直接返回指针 |
| 写入吞吐量 | ≥ 50k 点/秒 | 多线程并发，共享内存直接操作 |

通过避免系统调用、锁争用和动态内存分配，确保控制周期内的时间确定性。

### 5.2 多进程零拷贝共享

数据完全存储在 POSIX 共享内存中，所有进程直接映射同一物理内存区域。读取操作无需数据拷贝，仅需 Seqlock 读重试机制确保一致性。这使得驱动、控制、HMI 之间数据交换延迟接近访存级别。

### 5.3 内建工业语义

每个数据点不仅是裸值（int/float/string/bool），还携带：

- **quality**：质量戳（Good / Uncertain / Bad），符合 OPC 质量体系。
- **timestamp**：精确时间戳，记录最后一次更新时刻。
- **unit / access / description**：工程单位、读写权限、描述，便于 HMI 和上层系统自动解析。

这些语义确保数据在工业上下文中具备完整意义，为后续的高级分析、告警判断提供基础。

## 6. 安全体系：纵深防御，取代裸 Modbus

InduRTDB 本身是一个**进程内/进程间数据核心**，不直接提供网络服务，因此不受网络攻击面影响。其安全体系通过以下三层实现：

### 6.1 操作系统级隔离

- 共享内存区域可限制为特定用户组或通过文件权限（`/dev/shm/` 下）控制访问。
- 无网络端口，杜绝远程未授权读写。

### 6.2 OPC UA Bridge —— 安全的对外接口

项目架构中明确预留 **OPC UA Bridge** 应用。该桥接进程：

- 使用 InduRTDB C API 读写共享内存，作为唯一的对外数据网关。
- 对外提供 **OPC UA (IEC 62541)** 标准服务，支持：
  - **用户/密码 + X.509 证书认证**；
  - **通信加密**（Basic256Sha256 等安全策略）；
  - **地址空间节点级访问控制**（可为不同角色设定不同点位的读写权）；
  - **审计日志**，记录连接、读取、写入事件。
- 完全隐藏底层 Modbus 设备，任何远程系统只能通过经过认证和加密的 OPC UA 通道访问被授权的数据子集。

### 6.3 与 IEC 62443 对齐

整体部署符合 **IEC 62443 “分区与管道”** 模型：InduRTDB 位于受保护的“控制区”内，OPC UA Bridge 作为“管道”连接上层，防火墙策略只允许 OPC UA 端口（如 4840）通过，物理或网络层面切断直接 Modbus 访问。这样构建了一条从现场到云的纵深防御链。

## 7. 性能验证与确定性

InduRTDB v2.1.0 已通过 59 个单元测试和集成测试，其中包含 6 个多进程 `fork` 测试，验证了共享内存的并发正确性。下一步将在目标硬件（ARM Cortex-A53，≥64 MB RAM）上测量实际 P99 延迟与吞吐量，验证下表指标。

| 测试项 | 方法 | 目标 |
|--------|------|------|
| 单点写入延迟 | 高精度时钟循环写入 10k 点，取 P99 | ≤ 10 μs |
| 多进程并发读 | 10 个进程循环 `peek`，测延迟 | ≤ 5 μs |
| 连续 24 小时稳定性 | 压测下监控内存、延迟、正确性 | 无泄漏，无数据错误 |
| 订阅推送延迟 | 写入至通知到订阅进程的时间 | ≤ 50 μs |

## 8. 与工业标准的融合路径

InduRTDB 不作为孤立产品存在，而是开放的标准体系中的一环：

- **OPC UA (IEC 62541)**：通过 OPC UA Bridge 成为标准 OPC UA 服务器，可被任何 SCADA、MES、云平台集成。
- **MQTT + Sparkplug B (可选)**：同样可通过桥接将指定点位发布到 MQTT Broker，适应 IIoT 场景。
- **IEC 61131-3 / PLCopen**：控制逻辑可直接在 C/C++ 中编写，使用 InduRTDB API 作为数据交换通道。
- **边缘计算框架 (如 EdgeX, KubeEdge)**：可将 InduRTDB 作为设备服务的数据缓存层，提供实时的南向数据支撑。

这种 **“实时数据库内核 + 标准协议网关”** 的分离式设计，既保证了极致性能，又获得了无限的上层互操作性。

## 9. 典型应用场景

**场景一：智能楼宇 DDC 控制器**
- 控制器内部：Modbus 驱动采集温湿度、CO₂ 传感器 → 写入 InduRTDB。
- 控制逻辑（PID）从 InduRTDB `peek` 当前值和设定值，计算后写回控制输出点。
- HMI 面板进程直接 `subscribe` 变更，实时更新显示。
- 楼宇上位系统通过 OPC UA 安全读取特定楼层数据，进行能耗分析，无法触及核心控制回路。

**场景二：PLC 边缘计算单元**
- 在开放式的 Linux 实时内核上运行 InduRTDB，替代传统的封闭 PLC 数据区。
- 逻辑用 C/C++ 实现复杂算法（如预测性维护），直接操作共享内存，实现 1 ms 控制周期。
- 通过 OPC UA 无缝对接工厂 MES，且只暴露必要数据，确保产线安全。

在工业自动化向开放、互联、智能演进的浪潮中，InduRTDB 提供了那份最底层的、值得信赖的确定性。
